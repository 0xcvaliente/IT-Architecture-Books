# 13 Data movement, write fencing and recovery

## Learning objectives

After this chapter you should be able to:

- Design an initial load and change data capture that share one consistent boundary, and calculate the catch-up time.
- Turn replication lag measurements into a cutover precondition, distinguishing the applier's row rate from its transaction rate.
- Implement a daily dual-run reconciliation that compares key sets and values up to the position the target has reached.
- Implement a write fence that the destination enforces with an authority epoch on every replicated table.
- Compare recovery before and after customer writes reach the new system.

## Load once, then follow the log

**Change data capture (CDC)** reads committed changes from the source database's transaction log and applies them to a target. Because it reads the log, it sees every writer that commits to the database, including partner accounts and forgotten scripts.

The initial load and the change stream must meet at one boundary. Orion takes a consistent snapshot of the legacy database at log position P0, loads it into the new store, and starts CDC from P0. A snapshot taken at one moment and a stream started at an unrelated later moment can lose the changes made in between.

Changes keep arriving during the load. In rehearsal, loading 12 million orders took 6 hours 40 minutes, or 24,000 seconds. At about 1,500,000 / 86,400 ≈ 17.4 row changes per second, about 417,000 changes queue up. The applier commits once per source transaction, so that an order and its lines always appear together, and that commit sets its speed. For ordinary transactions of about three rows, the applier manages about 280 row changes per second; inside one large transaction, which commits only once, it reaches about 1,200 rows per second. Ordinary traffic dominates the queue, so with the drain model from Chapter 2 it clears in about 417,000 / (280 − 17.4) ≈ 1,590 seconds, or 26 minutes. On the clouds, Azure Database Migration Service and AWS Database Migration Service can play the applier's role for supported source and target pairs; support varies by source, target and online or offline mode {REF:azdatabase}.

## Measure lag where it matters

**Replication lag** is the time between a change committing in the source and the same change being applied in the target. Orion replicates all three order tables through one subscription, which applies transactions in their commit order, so one lag figure describes the whole stream: a change to `orders` cannot overtake a large transaction on `status_history` ahead of it. Orion measures that lag with a heartbeat: every five seconds, a job writes a timestamped row to a replicated heartbeat table, and the target records when the row arrives. The servers' clocks agree within a few milliseconds, which is small compared with lags measured in seconds. Over a four-week dual run, the measurements were:

| Period | p50 lag | p95 lag | p99 lag | Maximum lag |
|---|---|---|---|---|
| Ordinary business days | 0.8 s | 2.9 s | 7 s | 46 s |
| The month-end day | 1.1 s | 4.2 s | 12 s | 8 min 40 s |
| All four weeks | 0.8 s | 3.0 s | 8 s | 8 min 40 s |

The typical figures look excellent. The maximum came from the finance month-end job, which updates 600,000 rows of `status_history` in a single transaction that the applier must apply whole: at about 1,200 rows per second that takes 500 seconds, and every change committed after the job waits behind it, so the whole stream fell about eight and a half minutes behind. Orion turns this into a precondition: start the cutover only when the stream's lag has stayed below 10 seconds for thirty minutes, and never within 24 hours after the month-end job.

## Map meaning, not columns

A mapping can copy every row successfully and still change what the data means. Two examples from Orion show how:

- **VAT totals.** The legacy platform rounds VAT on each order line and stores the sum, while the new service rounds VAT once per order, so totals can differ by a cent or more. Customers were invoiced the legacy totals, so mapping version 2 copies historical totals exactly as recorded, and the new rule applies only to new orders.
- **Promised dates.** The legacy `promised_date` is a local date with no time. Converting it to a timestamp at midnight would invent precision and could shift the date across time zones, so the target keeps it as a date.

Record the mapping version used for each record. For example, if a customer later queries an old invoice total, the record shows that mapping version 2 copied it unchanged.

## Run both systems side by side

During a four-week **dual run**, the legacy platform stays authoritative and CDC keeps the new store current. The new order service runs in shadow: it receives a mirrored copy of every order request, computes its own prices, VAT and warehouse assignment, and stores the result where no customer sees it. Each day, one comparison checks the replicated data against the legacy data, and another checks the shadow results against the legacy results.

The product owner kept the stock-first rule for the first release.

### The reconciliation query

The daily comparison checks key sets and values, not just counts, and it must respect the replication boundary. Each legacy order records the log position of its last change, and the target knows the position up to which the applier has committed changes. An order changed after that position will differ in the target for a few seconds without anything being wrong. The listing runs the comparison in SQLite on five legacy orders. The target has applied the log up to position 1000:

~~~
import sqlite3

db = sqlite3.connect(':memory:')
db.executescript("""
CREATE TABLE legacy_order (order_id TEXT PRIMARY KEY, status TEXT,
                           total_cents INTEGER, last_lsn INTEGER);
CREATE TABLE target_order (order_id TEXT PRIMARY KEY, status TEXT,
                           total_cents INTEGER);
INSERT INTO legacy_order VALUES ('O-201', 'shipped', 12500, 880),
    ('O-202', 'open', 4999, 905), ('O-203', 'open', 800, 910),
    ('O-204', 'packed', 2300, 1003), ('O-206', 'open', 1500, 1004);
INSERT INTO target_order VALUES ('O-201', 'shipped', 12500),
    ('O-202', 'open', 5000), ('O-204', 'open', 2300), ('O-205', 'open', 800);
""")
RECONCILE = """
SELECT 'missing in target' AS issue, l.order_id
FROM legacy_order AS l LEFT JOIN target_order AS t ON t.order_id = l.order_id
WHERE t.order_id IS NULL AND l.last_lsn <= :applied
UNION ALL
SELECT 'extra in target', t.order_id
FROM target_order AS t LEFT JOIN legacy_order AS l ON l.order_id = t.order_id
WHERE l.order_id IS NULL
UNION ALL
SELECT 'values differ', l.order_id
FROM legacy_order AS l JOIN target_order AS t ON t.order_id = l.order_id
WHERE (l.status IS NOT t.status OR l.total_cents IS NOT t.total_cents)
  AND l.last_lsn <= :applied
ORDER BY 1, 2
"""

def reconcile(label: str, applied: int) -> None:
    issues = db.execute(RECONCILE, {'applied': applied}).fetchall()
    later = db.execute('SELECT count(*) FROM legacy_order WHERE last_lsn > ?',
                       (applied,)).fetchone()[0]
    print(f'{label}: {len(issues)} differences, {later} orders left for the next run')
    for issue, order_id in issues:
        print(f'  {order_id}: {issue}')

reconcile('ignoring the CDC position', applied=10**9)
reconcile('up to applied position 1000', applied=1000)
~~~

It prints:

~~~
ignoring the CDC position: 5 differences, 0 orders left for the next run
  O-205: extra in target
  O-203: missing in target
  O-206: missing in target
  O-202: values differ
  O-204: values differ
up to applied position 1000: 3 differences, 2 orders left for the next run
  O-205: extra in target
  O-203: missing in target
  O-202: values differ
~~~

Without the boundary, two of the five differences are false: O-204 was packed and O-206 created after position 1000, so the target has not applied them yet. With the boundary, three real differences remain. O-205 is a smoke-test order that reached the target by another route, O-203 was lost, and O-202's total differs by one cent. The two deferred orders are compared in the next run, once the applier has passed their positions. SQLite's `IS NOT` compares values safely when either side is null; in PostgreSQL the same comparison is written `IS DISTINCT FROM`. In production the query also applies the recorded mapping version to the legacy values before comparing them.

## Fence every writer, at the destination

A **write fence** stops an old authority from changing data after authority has moved. Orion's fence has two halves.

On the legacy side, the cutover begins by revoking insert, update and delete rights on the order tables from the application, partner, batch and support accounts and ending their open sessions. A probe write is then attempted with each account and must fail, and only then is the final log position recorded. Blocking the web shop alone would leave the partner, the support script and the month-end job free to write.

On the destination side, the new store must accept writes from exactly one authority at a time: the CDC applier before cutover and the new order service after it. Orion enforces this with an **authority epoch**, a number that increases each time authority moves. Privileges come first. A dedicated role, `orion_fence`, owns the order tables, the authority table and the check; the writers, `orion_applier` and `orion_service`, receive only row privileges on the order tables:

~~~
-- Run by an administrator. orion_fence owns the tables and the fence;
-- writers get row privileges on the order tables and nothing on the fence.
CREATE ROLE orion_fence NOLOGIN;
CREATE ROLE orion_applier LOGIN;
CREATE ROLE orion_service LOGIN;
GRANT CREATE ON SCHEMA public TO orion_fence;
GRANT pg_create_subscription TO orion_applier;
ALTER ROLE orion_applier SET orion.writer_epoch = '7';   -- read by the apply worker
~~~

A trigger written in PL/pgSQL, PostgreSQL's procedural language, then checks the epoch on every row written. CDC writes order lines and status history as well as orders, so the triggers are attached to all three replicated tables:

~~~
-- Run as orion_fence, which owns the order tables created beforehand.
CREATE TABLE write_authority (
  domain text PRIMARY KEY,
  epoch  integer NOT NULL
);
INSERT INTO write_authority VALUES ('orders', 7);    -- 7 = replication from legacy
REVOKE ALL ON write_authority FROM PUBLIC;           -- writers cannot touch it

CREATE FUNCTION check_writer_epoch() RETURNS trigger
LANGUAGE plpgsql
SECURITY DEFINER                   -- reads the fence as orion_fence, not as the writer
SET search_path = public, pg_temp  -- apply workers run with an empty search_path
AS $$
DECLARE
  active integer;
BEGIN
  SELECT epoch INTO active FROM write_authority
  WHERE domain = TG_ARGV[0]
  FOR SHARE;                       -- an epoch change waits for this transaction
  IF current_setting('orion.writer_epoch', true) IS DISTINCT FROM active::text THEN
    RAISE EXCEPTION 'writer epoch % rejected on %; active epoch is %',
      current_setting('orion.writer_epoch', true), TG_TABLE_NAME, active;
  END IF;
  IF TG_LEVEL = 'ROW' THEN
    RETURN COALESCE(NEW, OLD);     -- let the checked row through
  END IF;
  RETURN NULL;
END $$;
REVOKE ALL ON FUNCTION check_writer_epoch() FROM PUBLIC;

DO $$
DECLARE
  t text;
BEGIN
  FOREACH t IN ARRAY ARRAY['orders', 'order_lines', 'status_history'] LOOP
    -- Row triggers: logical replication apply workers fire row triggers only.
    EXECUTE format('CREATE TRIGGER %I BEFORE INSERT OR UPDATE OR DELETE ON %I
                    FOR EACH ROW EXECUTE FUNCTION check_writer_epoch(%L)',
                   t || '_epoch_fence', t, 'orders');
    EXECUTE format('CREATE TRIGGER %I BEFORE TRUNCATE ON %I
                    FOR EACH STATEMENT EXECUTE FUNCTION check_writer_epoch(%L)',
                   t || '_epoch_truncate', t, 'orders');
    -- ALWAYS: fire even when the applier sets session_replication_role = replica
    EXECUTE format('ALTER TABLE %I ENABLE ALWAYS TRIGGER %I', t, t || '_epoch_fence');
    EXECUTE format('ALTER TABLE %I ENABLE ALWAYS TRIGGER %I',
                   t, t || '_epoch_truncate');
    EXECUTE format('GRANT SELECT, INSERT, UPDATE, DELETE ON %I
                    TO orion_applier, orion_service', t);
  END LOOP;
END $$;
~~~

Each writer declares its epoch in its session. The new order service runs `SET orion.writer_epoch = '8'` when it connects. An applier that cannot run its own commands, such as PostgreSQL's logical replication apply worker, gets the setting from its role, as in the first listing; a worker reads it when it starts. The subscription is owned by `orion_applier` and created with `run_as_owner = true`, so changes are applied with the applier's own row privileges instead of the table owner's {REF:pglogsec}. At cutover, an operator acting as `orion_fence` runs `UPDATE write_authority SET epoch = 8 WHERE domain = 'orders'` and revokes the applier's row privileges. Because every write holds a share lock on the authority row, the update waits until in-flight applier transactions finish.

The check function is `SECURITY DEFINER`, so it reads and share-locks the authority row with `orion_fence`'s rights. A locking read such as `FOR SHARE` needs update rights on the table, so a check running with the writer's own rights would force Orion to give every writer, stale ones included, the power to change the epoch. Instead the writers hold no rights on `write_authority` at all, and `REVOKE ... FROM PUBLIC` keeps it that way. The pinned `search_path` puts `pg_temp` last, so a writer cannot plant a temporary table named `write_authority` for the definer's function to read, and only `orion_fence` may create objects in the schema.

Three more details come from how PostgreSQL's logical replication apply worker behaves:

- It runs with `session_replication_role` set to `replica`, so that ordinary triggers do not fire a second time on the copy {REF:pglogrepl}. A trigger enabled with `ENABLE ALWAYS` fires whatever the replication role {REF:pgaltertable}.
- It fires row-level triggers but not statement-level ones, so the fence on inserts, updates and deletes must be `FOR EACH ROW` {REF:pglogrepl}. `TRUNCATE` has only a statement-level trigger, which is kept for the other writers.
- It runs with an empty `search_path`, a security measure introduced in 2020 {REF:pgemptypath}. In the test, every replicated write failed until the function pinned its own `search_path`, because `write_authority` could not be found.

Tested in PostgreSQL 18 with a real publication on a second instance and the subscription owned by `orion_applier`, the apply worker replicated inserts and updates to all three tables at epoch 7 and was stopped once the epoch became 8. An earlier version of the fence with statement-level triggers let the same stale change through. Both writer roles were refused when they tried to update `write_authority` or lock it with `FOR SHARE`. Further sessions on the new store showed the rest of the behaviour:

- before cutover, a session with epoch 7 wrote to all three tables, and the new service with epoch 8 was rejected on each;
- the epoch change waited for the applier's open transaction to commit;
- after cutover, epoch 7 was rejected and the new service wrote;
- a session that declared no epoch was always rejected, and so was a `TRUNCATE` from a stale writer;
- a stale writer that set `session_replication_role` to `replica` was still rejected; with the trigger merely enabled, the same write was accepted.

This is Kleppmann's fencing token, checked by the system that stores the data {REF:kleppmann}. The epoch stops delayed or forgotten writers acting on old authority, but it cannot stop a misconfigured writer from declaring the new epoch. The applier and the new service therefore also use separate database roles, and the applier loses its write privilege at cutover. If an applier cannot declare an epoch at all, enforce the check in the applier's own configuration and rely on the revoked privilege. The partner's side of the fence is the epoch on dispatch commands agreed in the contract.

## Recovery before and after customer writes

The point of no easy return comes when customers start writing to the new system, so Orion delays it. During the cutover, public routing stays on the legacy platform, which keeps serving order status, while the new service accepts only smoke-test orders for a test tenant through an internal route. If the go/no-go decision is "no", the reverse path takes six minutes:

1. as `orion_fence`, raise the target's epoch to 9, set `orion_applier`'s role setting to epoch 9 and restore its row privileges on the order tables;
2. restart the subscription, with `ALTER SUBSCRIPTION ... DISABLE` and then `ENABLE`, so that a new apply worker starts with the new setting;
3. restore the legacy accounts' write privileges, so the legacy platform is authoritative again;
4. let CDC resume from the final log position, and delete the test-tenant orders from the target in an operator session that declares epoch 9.

After public routing switches, customer orders exist only in the new store. Routing back would hide them and restoring a backup would delete them. Orion therefore runs reverse CDC for fourteen days after the switch, replicating every change from the new store back into the legacy database, while the two new order states stay disabled by a feature flag so that every order can be represented in the legacy schema. If a severe defect appears, Orion can fence the new store and return authority to the legacy platform without losing an order. On day fifteen, reverse CDC stops, the new states are enabled, and recovery means fixing forward.

The way back has a price. About 300 orders a week need "awaiting customs"; for fourteen days the customs desk tracks them with the legacy "on hold" status and a note, at about ten extra minutes per order, or 100 hours in total. Orion chose fourteen days because the dual run found its last new defect on day 12. A shorter period would save desk time but leave part of the first fortnight in production without a tested way back.

> **Common mistake.** Promising "rollback" without saying what happens to orders created after the switch. Rolling back routing, restoring a database and returning authority with its data are three different operations with different losses.

## Key points

- A snapshot and a change stream must share one log position, and the catch-up time follows from the drain model.
- Lag maxima, not averages, set the cutover preconditions, and a large transaction delays every change behind it in the stream.
- A dual run with daily key-set and value reconciliation finds mapping and scope defects before customers do.
- The destination must enforce the fence: an authority epoch checked by the store rejects stale writers, alongside revoked privileges.
- Keeping customers on the old system until go/no-go, and replicating back for a fixed period afterwards, keeps a tested way back.
