# 3 Integration studio brief and boundary design

## Learning objectives

After this chapter you should be able to:

- Explain why a shared portal can promise durable receipts but not one duplicate-prevention guarantee across three different CRMs.
- Model handoff state separately from business case state, using a fixed set of handoff states.
- Design a routing rule that keeps each accepted request with one business unit's CRM.
- Compare three integration alternatives for isolation, operation and cost.

## The Meridian portal in brief

> **Building on Book 1.** Book 1 designed Meridian's portal around a single CRM: a durable receipt, a transactional outbox whose handoff records move through five states, idempotency keys scoped to tenant and user, and a recovery estimate for a thirty-minute outage. This studio gives each business unit its own CRM with a different contract for creating cases, adds a product recall that concentrates load on one of them, and asks what the portal can still promise.

Meridian maintains equipment for 600 customer organisations, each of which is a **tenant** of its service portal. Three internal business units employ 40 service agents. Customers use the portal to submit service requests, attach files and follow progress.

The submission path is settled: the API stores each submission and its handoff record in one transaction, the **transactional outbox** pattern {REF:outbox}, returns a receipt, and a worker delivers the handoff later, possibly more than once.

Ownership is divided by fact. The portal owns the receipt and the status that customers see. The CRM owns the service case once the handoff is confirmed. The ERP system owns assets, contracts, entitlements, inventory and work orders.

## The studio assignment

In this studio, each of Meridian's three business units runs its own CRM, called CRM A, CRM B and CRM C, and they will stay separate for at least eighteen months. Twelve engineers work on the portal, two of them on integration. The workload and targets are:

- 100,000 service requests a year, about 0.0032 per second on average;
- an exceptional peak of 20 valid submissions per second for ten minutes, with files of up to 10 MB;
- receipts for 95 percent of valid submissions within one second, excluding upload, and 99.9 percent monthly success for eligible requests;
- status changes visible to customers within one minute under normal conditions;
- no accepted request lost when one CRM is unavailable for thirty minutes.

The sponsor adds a recall scenario. A safety notice for one product line, serviced by business unit B, drives 5 submissions per second to CRM B for two hours. The sponsor wants a published recovery objective for the case where CRM B fails during that surge, and a slow CRM must not exhaust the workers or database connections that serve the other two business units.

Staff access follows a fixed rule. A staff member may read a request only with the service-agent role, membership of the request's business unit and an authorised scope that includes the request's tenant. Staff often serve several tenants, so the scope is a set, never a single tenant ID. Customers read their own requests; reading every request of their organisation needs an explicit delegation.

## Three CRM contracts

An interface investigation found three different contracts for creating a case:

| CRM | Create request | Effect of repeating it | Finding an earlier result |
|---|---|---|---|
| A | Carries an external reference that CRM A keeps unique | Returns the existing case | Exact lookup by external reference |
| B | Has no unique reference | Creates a second case | Search on a reference field whose index lags, usually by under five minutes, with no stated maximum |
| C | Carries an `Idempotency-Key` header | Returns the earlier result for 24 hours | A status lookup by key for the same 24 hours |

CRM C follows the pattern of the `Idempotency-Key` header described in an IETF Internet-Draft, which expired without becoming a standard {REF:idemkey}. The portal sends the submission ID as the key. For 24 hours after first use, a repeat with the same key and body returns the first response; a repeat with a different body is rejected with status 422, and one that arrives while the first is still running is rejected with 409. After 24 hours CRM C forgets the key, so a repeat would create a new case. The status lookup has the same 24-hour lifetime, so one window governs both retries and lookups.

CRM B allows 15 create calls per second, and its searches use a separate allowance in the current contract.

## What the portal can promise

The portal controls its own database, so it can promise durable acceptance: once a receipt is issued, the submission and its handoff record exist. Duplicate prevention depends on each CRM's contract. CRM A makes repeats harmless, CRM C makes them harmless for 24 hours, and CRM B makes them dangerous. A common API should therefore expose common states while keeping each CRM's uncertainty visible behind them.

### Handoff state

Every handoff record is in exactly one of the five states, with `retry_due` defined more sharply than before:

- `pending`: stored and not yet attempted.
- `in_flight`: a worker holds a time-limited lease on the record and is calling the CRM.
- `confirmed`: the CRM case exists and its case ID is recorded.
- `retry_due`: the last attempt failed or its outcome is unknown, and the next action that the CRM's contract allows, a resend or a lookup, is scheduled for a recorded time.
- `manual_review`: the system cannot settle the outcome safely by itself, so a person decides.

A handoff that cannot be completed automatically waits in `manual_review` with an owner; nothing is dropped silently. Customers see a simpler picture:

| Situation | Customer-visible status |
|---|---|
| `pending`, `in_flight` or `retry_due`, for up to one minute | Received |
| Any unconfirmed state for longer than that, including `manual_review` | Received, awaiting service team |
| `confirmed` | The CRM's case status, for example "In progress" or "Resolved" |

Business state is separate. A service case moves from "In progress" to "Resolved" in the CRM, independently of any handoff attempt, so the two kinds of state live in different fields. A late delivery retry must never overwrite the CRM's newer status. The portal's status projection stores the CRM case ID, the CRM status and the version the CRM supplies with it.

## Route each request to one authority

The ERP service contract for each tenant names the business unit that serves it. At acceptance, the portal stores that business unit with the submission, and every later delivery uses the stored value.

For example, customer T042 moves from business unit B to business unit A on 1 March. A request accepted on 28 February stays with CRM B, even if its handoff is still pending on 2 March. Moving it would need an explicit transfer that closes the case in one CRM and creates it in the other; without one, a request could be created twice or not at all.

## Isolate the business units

Logical isolation comes first: each worker selects work for one business unit, each path has its own concurrency limit and rate limiter, and alerts are raised per business unit. For example, the portal might allow at most eight simultaneous calls to CRM B, so that if CRM B slows down, only those eight calls wait.

Shared resources still need care. A worker must never hold a database transaction open while it calls a CRM. If each call to CRM B suddenly takes 20 seconds while holding a connection, eight stuck calls tie up eight connections and can drain the pool for everyone. The safe pattern is to claim work in a short transaction, commit, call the CRM, and record the result in a second short transaction.

Separate deployments give stronger isolation at extra cost, and a specific failure should justify them. If CRM B sometimes returns responses so large that they exhaust the worker's memory, running B's adapter in its own process confines the crash. A shared database outage affects every path however the workers are deployed.

## Three credible alternatives

The studio compares three designs, none of which removes the need to understand each CRM's create semantics:

- **Option A** is a relational outbox with one adapter per CRM; workers poll the handoff table.
- **Option B** adds a message broker; a relay publishes outbox records, and the adapters consume them.
- **Option C** uses an integration platform with CRM connectors and a durable workflow engine.

| Option | Main strength | Main cost or uncertainty |
|---|---|---|
| Outbox with polling adapters | Few moving parts and explicit local atomicity | Polling load, fair work selection and replay must be built |
| Outbox plus broker | Independent consumers and buffering | Another durability boundary to operate and reason about |
| Integration platform | Managed workflow, timers and connector operations | Connector retry semantics, licence cost and export of history |

A broker helps when several consumers need independent progress or retained delivery. The database and the broker cannot commit atomically, so Option B still needs the outbox and a relay that may publish a record twice.

## Key points

- A shared portal can promise durable acceptance, while duplicate prevention depends on each CRM's contract.
- Five handoff states, `pending`, `in_flight`, `confirmed`, `retry_due` and `manual_review`, keep every request accounted for.
- Handoff state and business case state are separate, and a retry must never overwrite the CRM's newer status.
- The business unit is stored at acceptance, so an in-flight request keeps one authority unless an explicit transfer moves it.
- Isolation is designed against named failures, and manual work is sized like any other capacity.
