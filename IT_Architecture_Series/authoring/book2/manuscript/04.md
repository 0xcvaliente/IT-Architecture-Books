# 4 Integration contracts and competing designs

## Learning objectives

After this chapter you should be able to:

- Design a duplicate-safe submission contract with a scoped idempotency key and a payload check.
- Implement an outbox schema and a claim query that lets several workers share work safely.
- Use the attempt number as a fencing token, and explain why a worker lease protects the local record but not the CRM.
- Analyse an unknown handoff outcome under each CRM contract and choose the next safe action.
- Compare polling, a broker and a workflow platform as ways to deliver handoffs.

## The submission contract

A submission passes through four steps. The portal authenticates the caller and establishes their tenant and role. It validates the request and reads the business unit assigned to the tenant, then checks the idempotency key. Finally, it stores the submission and its handoff record in one transaction and returns a receipt.

An **idempotency key** is a client-chosen identifier that lets the server recognise a repeated request. The client sends it in an `Idempotency-Key` header. The header is widely used but not yet standardised: the IETF Internet-Draft that described it has expired without becoming an RFC {REF:idemkey}. As in Book 1, Meridian scopes the key to the tenant and the submitting user and stores a digest of the request body beside it: the same key and body return the stored receipt, a different body is rejected with status 422, and keys are kept for seven days.

The portal returns 201 Created, because the receipt is a new resource. HTTP defines the meaning of the status codes {REF:http}; the business meaning of the receipt is Meridian's to define. The receipt says that Meridian has durably stored the request and taken responsibility for the handoff. The CRM case comes later and has its own identifier.

A repeated request must pass the current access checks again, because the key identifies a request and grants no rights. For example, if user u7 leaves tenant T042, a retry carrying u7's old key must be refused rather than answered with the stored receipt.

### The outbox schema

The following PostgreSQL schema holds submissions and their handoff records. The unique constraint enforces the key scope, and the check constraint fixes the five handoff states from Chapter 3. A small policy table records what may follow an unknown outcome at each business unit's CRM, and how long to wait first. CRMs A and C may receive the same create again after a minute. CRM B needs a lookup after fifteen minutes. Each handoff carries its own `next_action`, `send` or `lookup`. The `uuid`, `timestamptz` and `interval` types, partial indexes, `ON CONFLICT`, data-modifying `WITH` clauses and `FOR UPDATE SKIP LOCKED` used in this chapter are PostgreSQL features; other databases express the same ideas with different syntax.

~~~
CREATE TABLE submission (
  submission_id   uuid PRIMARY KEY,
  tenant_id       text NOT NULL,         -- customer organisation
  submitted_by    text NOT NULL,
  business_unit   text NOT NULL CHECK (business_unit IN ('A', 'B', 'C')),
  idempotency_key text NOT NULL,
  payload_digest  text NOT NULL,
  received_at     timestamptz NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, submitted_by, idempotency_key)
);

CREATE TABLE crm_policy (           -- ADR-M03: the next action after an unknown outcome
  business_unit text PRIMARY KEY,
  after_unknown text NOT NULL CHECK (after_unknown IN ('send', 'lookup')),
  wait          interval NOT NULL
);
INSERT INTO crm_policy VALUES ('A', 'send', '1 minute'),
  ('B', 'lookup', '15 minutes'), ('C', 'send', '1 minute');

CREATE TABLE handoff (
  submission_id   uuid PRIMARY KEY REFERENCES submission,
  business_unit   text NOT NULL REFERENCES crm_policy,
  state           text NOT NULL DEFAULT 'pending' CHECK (state IN
                  ('pending', 'in_flight', 'confirmed', 'retry_due', 'manual_review')),
  next_action     text NOT NULL DEFAULT 'send'
                  CHECK (next_action IN ('send', 'lookup')),
  attempts        integer NOT NULL DEFAULT 0,
  first_attempt_at timestamptz,           -- set by the first claim
  next_attempt_at timestamptz NOT NULL DEFAULT now(),
  lease_owner     text,
  lease_until     timestamptz,
  last_outcome    text,                   -- for example 'timeout' or 'created'
  crm_case_id     text
);

CREATE INDEX handoff_due ON handoff (business_unit, next_attempt_at)
  WHERE state IN ('pending', 'retry_due');
~~~

The partial index covers only the rows that workers look for, so the confirmed handoffs that soon fill the table stay out of it. One statement writes the submission and its handoff record, so they commit or fail together:

~~~
WITH s AS (
  INSERT INTO submission (submission_id, tenant_id, submitted_by, business_unit,
                          idempotency_key, payload_digest)
  VALUES ($1, $2, $3, $4, $5, $6)
  ON CONFLICT (tenant_id, submitted_by, idempotency_key) DO NOTHING
  RETURNING submission_id, business_unit
)
INSERT INTO handoff (submission_id, business_unit)
SELECT submission_id, business_unit FROM s
RETURNING submission_id;
~~~

If the statement returns no row, the key already exists. The portal then reads the stored submission and compares digests: a match returns the stored receipt and a mismatch returns 422. Two identical requests that race are also safe, because PostgreSQL makes the second insert wait for the first and then skip.

## Workers claim work with leases

Several workers share the handoff table. Each claims a small batch for one business unit:

~~~
WITH due AS (
  SELECT submission_id
  FROM handoff
  WHERE business_unit = $1
    AND state IN ('pending', 'retry_due')
    AND next_attempt_at <= now()
  ORDER BY next_attempt_at
  LIMIT $2
  FOR UPDATE SKIP LOCKED
)
UPDATE handoff AS h
SET state = 'in_flight',
    attempts = h.attempts + 1,
    first_attempt_at = coalesce(h.first_attempt_at, now()),
    lease_owner = $3,
    lease_until = now() + interval '2 minutes'
FROM due
WHERE h.submission_id = due.submission_id
RETURNING h.submission_id, h.attempts, h.next_action;
~~~

`FOR UPDATE SKIP LOCKED` locks the selected rows and skips any row that another transaction has already locked, instead of waiting for it {REF:pgselect}. For example, worker 1 claims the two oldest handoffs for business unit B; worker 2 runs the same query a moment later and immediately receives the third and fourth.

The worker commits the claim, then performs the handoff's `next_action` outside any database transaction: it sends the create request, or, for a CRM B handoff with an unknown outcome, searches for the submission ID. Each claim increases `attempts`, and the claim returns that number to the worker. The worker passes it back with its result, so the number acts as a **fencing token**: an update succeeds only for the attempt that currently holds the lease. Four statements record results and enforce the time limits:

~~~
-- Confirm. The attempt number returned by the claim is the fencing token.
UPDATE handoff
SET state = 'confirmed', crm_case_id = $4, last_outcome = 'created',
    lease_owner = NULL, lease_until = NULL
WHERE submission_id = $1 AND state = 'in_flight'
  AND lease_owner = $2 AND attempts = $3;

-- Unknown outcome: schedule the next action that the CRM's contract allows.
UPDATE handoff AS h
SET state = 'retry_due', last_outcome = $4,
    next_action = p.after_unknown, next_attempt_at = now() + p.wait,
    lease_owner = NULL, lease_until = NULL
FROM crm_policy AS p
WHERE p.business_unit = h.business_unit
  AND h.submission_id = $1 AND h.state = 'in_flight'
  AND h.lease_owner = $2 AND h.attempts = $3;

-- Sweep expired leases. The abandoned call's outcome is unknown as well.
UPDATE handoff AS h
SET state = 'retry_due', last_outcome = 'lease_expired',
    next_action = p.after_unknown, next_attempt_at = now() + p.wait,
    lease_owner = NULL, lease_until = NULL
FROM crm_policy AS p
WHERE p.business_unit = h.business_unit
  AND h.state = 'in_flight' AND h.lease_until < now();

-- CRM C forgets keys after 24 hours: hand over to a person after 20.
UPDATE handoff
SET state = 'manual_review', last_outcome = 'key_window_closing'
WHERE business_unit = 'C' AND state = 'retry_due'
  AND first_attempt_at < now() - interval '20 hours';
~~~

The second and third statements give `retry_due` its meaning: the next action allowed by the CRM's contract is scheduled for a recorded time. For example, worker w1 sends a create for request R17 to CRM B as attempt 1 and stalls. Its lease expires, and the sweep moves the handoff to `retry_due` with `next_action = 'lookup'` and `next_attempt_at` fifteen minutes ahead, so no worker can claim it earlier. Tested in PostgreSQL 18, a claim made straight after the sweep returned nothing, and a claim made after the wait returned attempt 2 with the action `lookup`. A definite failure, such as a create that CRM B throttled before processing it, is recorded with `next_action = 'send'` and an increasing backoff, because nothing was created.

The fourth statement applies ADR-M03's limit for CRM C, using the `first_attempt_at` value set when the handoff was first claimed. A lookup that finds exactly one matching case is recorded with the confirm statement. A lookup that finds no match or several moves the handoff to `manual_review`, using the same guard on owner and attempt number.

### A lease protects the record, not the CRM

A lease can expire while its worker is still alive, for example during a long garbage-collection pause. The sweep then moves the handoff to `retry_due`, and a later claim takes it as the next attempt. When the first worker wakes, the attempt number stops it from overwriting the record. A check on `lease_owner` alone would not be enough: a worker process that restarts, or runs several threads, under the same owner ID would pass it. In the same test, a confirm carrying the stale attempt 1 changed no row, while the confirm for attempt 2 succeeded. Nothing, however, stops the call that the first worker already sent.

A fencing token protects a write only when the system receiving the write checks it and rejects older numbers {REF:kleppmann}. The portal database checks the attempt number, so the local record is safe. None of the three CRMs checks such a token, so each CRM's own contract decides whether a second call is harmless. Chapter 13 returns to fencing in a case where the organisation controls the receiving system.

## When the outcome is unknown

A timeout describes what the worker observed, not what the CRM did. {FIG:uncertainty_trace} traces request R17 through CRM B. The worker sends a create request; CRM B commits case C91, but the reply is lost, so the worker records a timeout. A search for R17 returns nothing, because the search index has not caught up. Two histories fit these observations: the case exists but is not yet visible, or the create never happened.

FIGURE uncertainty_trace | A lost reply and a lagging search index leave the outcome of a CRM B create unknown.

Retrying blindly may create a second case, while treating the timeout as a failure may lead an agent to act on a false status. Helland describes the general principle: messages get retried, so the receiver must make processing a repeat have the same effect as processing it once {REF:helland2012}. CRM A provides that property permanently and CRM C for 24 hours; CRM B does not provide it.

Decision record ADR-M03 therefore sets a separate policy for each CRM:

| CRM | Next action after an unknown outcome | Normal path | Goes to `manual_review` when |
|---|---|---|---|
| A | After one minute, send the create again with the same external reference | `retry_due`, then `confirmed` | The returned case belongs to a different submission |
| B | After fifteen minutes, look up the submission ID | `retry_due`, then `confirmed` if exactly one case matches | The lookup finds no match or more than one |
| C | After one minute, send again with the same key, or query the key's status | `retry_due`, then `confirmed` | The outcome is still unknown 20 hours after the first attempt |

CRM C's limit is 20 hours rather than 24 so that an agent has four hours to settle the case while lookups still work. For CRM B, a negative search never justifies a new create, because the index has no stated maximum lag. Routing every CRM B handoff to agents instead is ruled out by the recall: 36,000 requests at three minutes each would need 1,800 agent hours. Automatic search with a bounded manual queue is the feasible choice until CRM B offers a unique reference.

### Resolve a manual review safely

Each record in `manual_review` keeps the submission ID, tenant, business unit, CRM, payload digest, time of first attempt, last outcome, candidate case IDs and resolution history, and nothing more than recovery and audit need. The agent's decision is applied as a guarded update that moves the record to `confirmed` with the chosen case ID only if it is still in `manual_review`. A late reply from an old attempt is compared with the recorded case ID and logged; it never replaces the decision.

Status updates flowing back from a CRM need ordering too. Clocks on different machines disagree, so timestamps from different systems cannot reliably order events {REF:lamport}. Use the CRM's own version number for each case: if version 7, "Resolved", arrives before version 6, "In progress", the projection keeps version 7.

## Compare the implementation choices

**Polling outbox.** Workers query the partial index in bounded batches, so the database carries both transaction load and work-selection load; test the two together at the peak. At Meridian's volumes the extra load is modest, for example eight indexed queries per second from eight workers polling once a second.

**Outbox plus broker.** A relay reads the outbox, publishes to the broker and records its progress. If it crashes after the broker accepts a message but before it records progress, it publishes that message again, so consumers must deduplicate by submission ID. RabbitMQ distinguishes publisher confirms, which mean the broker has taken responsibility for a message, from consumer acknowledgements, which mean a consumer has finished with it {REF:rabbit}. Neither says that a CRM case exists.

**Workflow platform.** A workflow engine provides timers, retries and history. Ask of each connector whether it reuses the same idempotency key on every retry, whether an operator can pause retries for one CRM, and whether the history can be exported for reconciliation.

Decision record ADR-M02 chooses the polling outbox for the first release, because each receipt has one delivery path and the team already operates PostgreSQL. Its review trigger: a second consumer needs to replay handoffs, polling uses more than 10 percent of database CPU at peak, or any business unit's oldest pending handoff exceeds its target at the agreed peak.

### Mapping the roles to Azure and AWS

Each option needs the same few runtime roles, and both major clouds offer managed services for them. Microsoft's comparison pages pair the services as follows {REF:azcompute,azdatabase,azmessaging}:

| Role in Meridian's design | Azure | AWS |
|---|---|---|
| Portal API and workers in containers | Azure Container Apps | Amazon ECS on AWS Fargate |
| PostgreSQL for submissions and handoffs | Azure Database for PostgreSQL | Amazon RDS for PostgreSQL |
| Queue for the broker option | Azure Service Bus queues | Amazon SQS |
| Durable workflow for the platform option | Azure Durable Functions or Logic Apps | AWS Step Functions |

Each pair fills the same role, but limits, pricing, failover behaviour and delivery guarantees differ, so check the decisions that depend on them, such as the database's failover and the queue's duplicate handling. Both managed database services run PostgreSQL, so the SQL in this chapter applies to either within their supported versions. The other studios add only a few roles, noted where they arise.

> **Common mistake.** Treating a broker acknowledgement as delivery to the CRM. Each boundary, from local commit to broker to CRM, makes its own promise, and the design must connect them explicitly.

## Exercises

4.1 Worker process w3 runs several threads under one owner ID. Thread 1 claims a CRM C handoff as attempt 4 and stalls; the lease expires, the sweep runs, and thread 2 of w3 claims the same handoff as attempt 5 and sends the create again. Thread 1 then receives CRM C's reply to attempt 4 and runs the confirm statement. Trace what happens if the guard checks only `lease_owner`, and what happens with the attempt number added. Can CRM C end up with two cases?

4.2 An agent reviewing a CRM B handoff finds two candidate cases. Design the resolution transition. State what the system must avoid claiming and what happens to a late reply from an earlier attempt.

4.3 Write an ADR that compares the polling outbox with an outbox plus broker for Meridian. Include the context, alternatives, consequences and a measurable review trigger.

4.4 CRM B times out after a create. Five minutes later, before the scheduled lookup, an impatient agent searches CRM B by hand, finds no match and asks for the create to be sent again. Give two histories consistent with this evidence and defend the next action under ADR-M03.

4.5 The claim query lets any number of workers take CRM B handoffs at once. Change the design so that at most eight CRM B handoffs are `in_flight` at any time. Explain how your change behaves when two workers claim at the same moment.

## Key points

- An idempotency key scoped to tenant and user, plus a payload digest, makes repeated submissions safe without weakening access checks.
- One statement stores the submission and its handoff record, so neither can exist alone.
- `FOR UPDATE SKIP LOCKED` lets workers share a queue table without blocking each other.
- The attempt number returned by the claim is a fencing token for the local record; only the receiving system can reject a stale write, so each CRM's contract decides what is safe after a timeout.
- After an unknown outcome, `retry_due` schedules the next action that the CRM's contract allows: a resend for CRMs A and C, a delayed lookup for CRM B.
- Each delivery boundary makes its own promise, and the design must state how they connect.
