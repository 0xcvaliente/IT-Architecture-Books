# 6 Transaction studio brief and business invariants

## Learning objectives

After this chapter you should be able to:

- Define transaction correctness as business invariants, and state when the message "Your order is confirmed" is true.
- Design a reservation request that returns the same result however often it is repeated.
- Calculate the utilisation of the hottest record and its throughput ceiling from the lock-hold time.
- Explain how a conditional stock update behaves under PostgreSQL's READ COMMITTED, REPEATABLE READ and SERIALIZABLE isolation levels.
- Compare a modular single-database design with separate inventory and order services.

## Aster launches a limited-stock event

> **Building on Book 1.** Book 1 introduced Aster at an everyday peak of 50 checkout attempts per second, protected its stock with one conditional update and handled uncertain payments with a saga. This studio raises the peak tenfold for a limited-stock event, so the questions become how busy one stock row can get, which isolation level to use, how to admit customers fairly and how to share stock with a partner.

Aster Retail sells physical goods through its website. Its everyday traffic is modest, but this studio sets a harder problem, a limited-stock sales event for a heavily promoted product:

- a peak of 500 checkout attempts per second for ten minutes, with 70 percent of attempts aimed at the promoted product;
- 2,000 units of that product allocated to the online event, and no confirmed sale beyond the allocation;
- a checkout response target: 95 percent of checkout submissions receive a final answer or an explicit pending status within five seconds;
- a payment provider that accepts an operation ID, offers an outcome lookup and honours repeated requests with the same ID for 24 hours;
- payment authorisation that usually takes a few seconds but can take up to thirty, with a timeout leaving the outcome unknown;
- reservations that expire after five minutes unless the order is confirmed.

Aster's two warehouses keep their own physical stock records. The 2,000 units are a selling allowance agreed with them for the event, so the event system controls the allowance, not the shelves.

The team's first proposal draws six services: catalogue, cart, order, inventory, payment and notification. The product manager wants one simple message at the end of checkout: "Your order is confirmed." Before accepting the diagram, define what must be true for that message to be correct.

## Derive the invariants

An **invariant** is a condition that must hold after every transaction. Let A be the units still available, R the units held by active reservations, C the units committed to confirmed orders and L the allocation of 2,000. With no replenishment during the event, A + R + C = L, with each quantity at or above zero. A reservation moves one unit from A to R; confirmation moves it from R to C; release or expiry moves it back from R to A.

FIGURE inventory | Reservation, confirmation and release move units between three quantities whose sum stays fixed at the event allocation.

{FIG:inventory} shows these movements. Aster's invariants for the event are:

- **I1.** A + R + C = 2,000, and A, R and C are never negative.
- **I2.** Each reservation is in exactly one state: active, committed, released or expired.
- **I3.** A reservation operation changes the stock at most once, however often it is repeated.
- **I4.** An order is confirmed only when its reservation is committed and its payment authorisation is verified.
- **I5.** Every admitted checkout ends confirmed, rejected, or in a visible pending state with an owner.

I4 answers the product manager. "Your order is confirmed" is true only when I4 holds; before that, the correct message is "We have your order and are confirming payment."

## Find the contention point

Seventy percent of 500 attempts per second, 350 per second, target the single allocation row of the promoted product. For example, spreading the catalogue across ten database servers leaves that row exactly as busy as before, so contention must be analysed at the invariant itself.

### The reservation statement

The following PostgreSQL schema keeps the available count on one row per product, and one row per reservation:

~~~
CREATE TABLE stock (
  sku       text PRIMARY KEY,
  available integer NOT NULL CHECK (available >= 0)
);

CREATE TABLE reservation (
  reservation_id uuid PRIMARY KEY,         -- the client's operation identity
  order_id       uuid NOT NULL,
  sku            text NOT NULL REFERENCES stock,
  state          text NOT NULL CHECK (state IN
                 ('active', 'committed', 'released', 'expired')),
  expires_at     timestamptz NOT NULL
);
~~~

Here A is the `available` column, while R and C are the counts of active and committed reservations. One statement decrements the stock and records the reservation:

~~~
-- Step 1: reserve. A returned row is a new reservation.
WITH taken AS (
  UPDATE stock SET available = available - 1
  WHERE sku = $1 AND available >= 1
  RETURNING sku
)
INSERT INTO reservation (reservation_id, order_id, sku, state, expires_at)
SELECT $2, $3, sku, 'active', now() + interval '5 minutes' FROM taken
RETURNING reservation_id, state, expires_at;
~~~

The heart of it is the conditional update `UPDATE stock SET available = available - 1 WHERE sku = $1 AND available >= 1`. When a unit remains, the statement takes it and returns the new reservation. When none remains, nothing changes and the statement returns no row.

### Make a repeated request return the same answer

A client that loses the reply resends its request with the same `reservation_id`. The first statement alone cannot answer that repeat correctly, and the failure appears exactly at sell-out. Suppose a customer reserves the last unit and the reply is lost. The retry finds `available` at zero, so the update matches no row, the insert adds nothing, and the customer who holds the unit is told "sold out". While units remain, the retry fails differently: the update takes a second unit, the insert fails with a unique-key violation, SQLSTATE 23505, and the whole statement rolls back, including the decrement.

Both outcomes therefore need a second step, a lookup by the same identifier:

~~~
-- Step 2: only after no row or SQLSTATE 23505, look up the same ID.
SELECT order_id, sku, state, expires_at
FROM reservation
WHERE reservation_id = $2;
~~~

The service applies one rule:

1. If step 1 returns a row, answer with the new reservation.
2. If step 1 returns no row or fails with 23505, run step 2.
3. If step 2 finds the reservation with the same order and product, answer with it. If it finds the identifier with a different order or product, reject the request as a reused identifier.
4. If step 2 finds nothing, answer "sold out". This answer changes no data, so a later retry with the same identifier is simply a new attempt.

Step 2 always sees the earlier reservation when there is one. A concurrent duplicate waits for the first transaction's row lock or unique-index entry, and that wait ends only when the first transaction commits or aborts. If it commits, step 2 is a new statement, so under READ COMMITTED it reads the committed row; if it aborts, the duplicate simply proceeds as a new reservation. Run against PostgreSQL 18, the rule gave these results:

| Situation | Step 1 | Answer | Stock afterwards |
|---|---|---|---|
| Retry of the winning request after sell-out | No row | The existing reservation | 0, one reservation |
| Retry while units remain | 23505, rolled back | The existing reservation | Unchanged |
| Two copies at once for the last unit | Second waits, then no row | The existing reservation | 0, one reservation |
| Another customer at once for the last unit | Second waits, then no row | Sold out | 0, one reservation |
| Same identifier sent for a different product | 23505, rolled back | Rejected | Unchanged |

Invariant I3 holds in every case: a reservation changes the stock at most once, however often it is repeated.

### What the isolation level changes

Suppose two transactions, T1 and T2, reserve the same product at the same moment. T1 updates the row first and holds its row lock until it commits. What T2 does next depends on the isolation level {REF:isolation}:

- **READ COMMITTED**, PostgreSQL's default: T2 waits for T1 to commit, then re-evaluates its `WHERE` clause against the newest version of the row. If a unit is still available, T2 takes it; if not, T2 updates nothing. There is no error and no retry, and `available >= 1` alone prevents overselling.
- **REPEATABLE READ** or **SERIALIZABLE**: T2 waits for T1 to finish. If T1 commits, T2 fails with "could not serialize access due to concurrent update", a serialization failure with SQLSTATE 40001, and the application must retry the whole transaction {REF:serialfail}. Only if T1 rolls back does T2 continue.

The second behaviour surprises many teams. With two units in stock, T2 fails under both stricter levels even though a unit is still available.

How often would that happen? The answer comes from the row's **utilisation**: the fraction of time its lock is held, equal to the arrival rate multiplied by the lock-hold time. At 350 reservations per second and a lock held for 1 millisecond, the row is locked 350 × 0.001 = 0.35 of the time. With random arrivals, an attempt finds the row locked with that same probability, so under REPEATABLE READ about one attempt in three would wait and then fail. If each failed attempt retries until it succeeds, the database handles about 350 / (1 − 0.35) ≈ 540 attempts per second to complete 350 reservations, and every failed attempt holds a connection while it waits. Each retry also adds waiting, and when the retries pile up faster than the row clears them, the result is a **retry storm**. For this statement, READ COMMITTED is both correct and much cheaper.

### Estimate the hot-row ceiling

A row lock is held from the moment the update runs until the transaction commits. If that **lock-hold time** is h seconds, the row can serve at most about 1 / h reservations per second, however many servers sit in front of it, and its utilisation at an arrival rate λ is λ × h. For example:

- sent as the single statement above, in one network round trip, h may be about 1 millisecond, giving a ceiling near 1,000 per second;
- sent as `UPDATE`, `INSERT` and `COMMIT` in three round trips of about 1 millisecond each, plus 1 millisecond to flush the commit, h is about 4 milliseconds and the ceiling falls to about 250 per second.

At 250 per second against 350 offered, the utilisation would be 1.4, which is impossible to sustain: the 2,000 units sell out in 8 seconds while about 100 attempts per second pile up in the lock queue. Roughly 800 transactions are then waiting, each holding a database connection, and if the pool runs dry, checkouts for every other product stall too. Waiting grows sharply well before utilisation reaches 1, so a row run at 0.9 already queues badly. These are estimates; Chapter 8 measures h directly. The design consequences are:

- keep the lock short, with one statement and one round trip;
- cap the waiting, for example at 50 reservation attempts in flight for the hot product, and send the rest a "high demand, please try again" page or a queue;
- once `available` reaches zero, answer requests with a new reservation ID from a cached sold-out flag, answer a repeated ID with the step 2 lookup, which reads the reservation table and never locks the stock row, and clear the flag when an expiry returns a unit;
- leave this statement at READ COMMITTED;
- split the row into allocation buckets if one row cannot keep up, as Chapter 7 develops.

## Two first designs

**Design A** keeps orders and the event allocation in one modular application with one transactional database. The payment call stays external and is coordinated through durable state, and the stock invariant needs no distributed transaction.

**Design B** gives inventory and orders their own services and databases. A reservation then becomes an explicit contract with a reservation ID, quantity, owner, expiry, version and final outcome. Helland describes this style: each entity lives inside one transactional scope, and entities cooperate through messages that must be processed idempotently {REF:helland2007}.

Separate ownership, or an inventory capability shared with stores and marketplaces, can justify that extra protocol. Without such a need, Design B adds a network boundary to every reservation and gains nothing for the event.

Both designs need payment idempotency and reconciliation, bounded admission and a way to explain each customer's outcome after a crash. The choice is about where the stock authority lives and what it costs to operate. On either cloud, Design A runs on the managed PostgreSQL and container services mapped in Chapter 4; Design B would add a queue between the services, such as Azure Service Bus or Amazon SQS {REF:azmessaging}.

## Key points

- Transaction design starts from business invariants, and invariant I4 decides when "confirmed" is true.
- A popular product concentrates load on one row, so contention must be analysed at that row, not across the catalogue.
- Under READ COMMITTED, a conditional update waits, re-checks and never oversells; under REPEATABLE READ or SERIALIZABLE it fails with SQLSTATE 40001 and must be retried.
- A row's utilisation is its arrival rate times its lock-hold time; its throughput is limited to about one divided by the lock-hold time, so short transactions and bounded admission matter more than server count.
- A repeated reservation must find the original result, which needs a lookup by reservation ID whenever the reservation statement returns no row or a unique-key violation.
- Splitting inventory into its own service replaces a local transaction with a protocol that must be designed and operated.
