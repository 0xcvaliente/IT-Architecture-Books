# 8 Transaction experiments and failure review

## Learning objectives

After this chapter you should be able to:

- Design correctness tests that exercise invariants under adverse orderings before any load test.
- Explain how a small state model exposes missing transition rules, and extend one.
- Evaluate admission policies with customer-outcome measures as well as latency.
- Calculate why stage means add on a serial path while stage percentiles do not.
- Evaluate a change card that adds a second sales channel, and record the response in a decision record and a decision brief.

## Test the boundary before the throughput

Start with tiny, exact tests. With one unit in stock, send two concurrent reservations and require exactly one success. Repeat the winning request with the same reservation ID, once while units remain and once after the product has sold out, and require the same answer with no second decrement both times. Release the reservation twice and require the second release to change nothing. Then inject failures at the dangerous points:

- a crash after the provider authorises the payment but before Aster records it;
- a duplicate payment callback;
- expiry before the callback arrives;
- a failure while voiding a payment.

For each, state the expected stock invariant and the customer-visible status in advance. A test passes when it accounts for the allocation, the reservation, the order and the payment; "no exception was thrown" proves very little.

### Check histories, not just final counters

A concurrent test produces a **history**: the start and end of each operation, with its result. **Linearizability** gives a precise standard for judging it: each operation must appear to take effect at a single instant between its start and its end, in an order that the object's sequential specification allows {REF:linearizability}. For a reservation, that specification is short. A new reservation ID takes a unit if one remains. A repeated ID that already holds a reservation returns that reservation, even after the product has sold out. A release returns a held unit at most once.

For example, consider one unit and two overlapping reservations that both return success. No sequential order can explain two successes for one unit, so the history is invalid even if the final counter reads zero. A lost update, where both transactions read 1 and both write 0, produces exactly that picture, so compare the returned reservation IDs and committed obligations as well as the counter. Two identity checks complete the set: the same reservation ID sent twice at once must produce one reservation, and an ID reused with a different product or quantity must be rejected.

## A state model for event orderings

A small executable model can expose missing rules before any database is involved. The listing models one unit of stock and one order. Every permitted transition is an explicit rule, any event without a rule raises an error, and each event carries an ID so that a repeated request or a redelivered message has no effect.

~~~
class IllegalTransition(Exception):
    """An event that the state model does not allow in the current state."""

# (reservation, payment, event) -> (new reservation, new payment, stock change)
RULES = {
    ('none', 'none', 'reserve'): ('active', 'pending', -1),
    ('active', 'pending', 'authorise'): ('active', 'authorised', 0),
    ('active', 'authorised', 'confirm'): ('committed', 'authorised', 0),
    ('active', 'pending', 'expire'): ('expired', 'pending', +1),
    ('committed', 'authorised', 'expire'): ('committed', 'authorised', 0),
    ('expired', 'pending', 'authorise'): ('expired', 'void_requested', 0),
    ('expired', 'void_requested', 'void_confirmed'): ('expired', 'voided', 0),
}

def run(events: list[tuple[str, str]]) -> str:
    reservation, payment, available, seen = 'none', 'none', 1, set()
    for name, event_id in events:
        if event_id in seen:
            continue                     # a repeated request or message changes nothing
        key = (reservation, payment, name)
        if key not in RULES:
            raise IllegalTransition(f'{name} while {reservation}/{payment}')
        reservation, payment, change = RULES[key]
        available += change
        seen.add(event_id)
        held = reservation in ('active', 'committed')
        assert available >= 0 and available + held == 1   # one unit in total
    return f'{reservation}/{payment}, available={available}'

R, A, X = ('reserve', 'r1'), ('authorise', 'p1'), ('expire', 'x1')
C, V, A2 = ('confirm', 'c1'), ('void_confirmed', 'v1'), ('authorise', 'p2')
for title, events in [('confirm before expiry', [R, A, C, X]),
                      ('reservation repeated after the sale', [R, A, C, R]),
                      ('late authorisation after expiry', [R, X, A, V]),
                      ('duplicate callback after void', [R, X, A, V, A]),
                      ('confirm after expiry', [R, X, C]),
                      ('new authorisation after void', [R, X, A, V, A2])]:
    try:
        print(f'{title}: {run(events)}')
    except IllegalTransition as error:
        print(f'{title}: rejected ({error})')
~~~

The model runs six fixed schedules and prints:

~~~
confirm before expiry: committed/authorised, available=0
reservation repeated after the sale: committed/authorised, available=0
late authorisation after expiry: expired/voided, available=1
duplicate callback after void: expired/voided, available=1
confirm after expiry: rejected (confirm while expired/pending)
new authorisation after void: rejected (authorise while expired/voided)
~~~

Each line tests one rule. A late expiry after confirmation changes nothing. A repeated reservation after the unit is sold changes nothing either, because its ID has been seen; in the database, the step 2 lookup from Chapter 6 plays that part and returns the stored reservation. A late authorisation leads to a void, and the unit stays available for other customers. The duplicate callback after the void is ignored because its event ID has been seen. Confirmation after expiry is rejected rather than consuming a released unit. A genuinely new authorisation after the void is also rejected, which raises a question for the business: should a customer who pays again for a cancelled order start a new order?

The model implements the simpler late-authorisation policy, in which a late result always leads to a void; Chapter 7's fresh-reservation path is left as an exercise. With one unit, one thread and no database, it checks the transition table rather than concurrency, which the database tests above cover.

## Admission is a business control

When demand exceeds useful capacity, unbounded pending work makes every customer's outcome worse. Aster can reject new checkouts with a clear message, accept them into a bounded pending state, or place customers in a waiting room with a stated admission rule. A fast rejection is not a sale, so measure the journey with separate indicators: storefront availability, valid checkouts admitted, confirmed orders, payments still unresolved, and time from checkout to a final outcome.

The following results are invented teaching data for the full ten-minute peak of Chapter 6: 500 attempts per second for 600 seconds, or 300,000 attempts. In every row, confirmed orders, unresolved payments and unsold units add up to the 2,000 allocated units.

| Policy | Admitted attempts | Confirmed orders | Unresolved payments at cutoff | Units unsold at cutoff | p95 time to final or pending answer |
|---|---|---|---|---|---|
| Unbounded admission | 300,000 | 1,942 | 58 | 0 | 7,900 ms |
| Bounded: 50 in flight for the hot product | 24,000 | 1,988 | 12 | 0 | 620 ms |
| Strict: close admission for good once every unit is reserved | 2,400 | 1,981 | 4 | 15 | 410 ms |

Unbounded admission misses the five-second target and leaves the most payments unresolved, because the provider was flooded with slow requests. Strict admission answers fastest but leaves 15 units unsold: admission closed for good once every unit was reserved, so when some of those reservations later expired, nobody was admitted to take the returned units. Bounded admission sells the most.

FIGURE admission | Admission control protects the transaction path while keeping rejected and pending outcomes explicit.

The table alone cannot select a winner. Reviewers should ask whether admitted attempts include duplicates, how many distinct customers they represent, what rejected customers did next, and how many unresolved payments completed after the cutoff. {FIG:admission} shows the paths that each count must cover. The next experiment should investigate the 15 unsold units, for example by reopening admission whenever a unit returns, and the 58 unresolved payments; repeating the benchmark on larger hardware would answer neither question.

## Tail latency on a serial path

Dean and Barroso explain why rare slow responses dominate when one request depends on many components {REF:tail}, so Aster keeps optional catalogue enrichment and notifications off the confirmation path.

For a serial path, the end-to-end time is the sum of the stage times. Means therefore add exactly: by linearity of expectation, the mean of a sum equals the sum of the means, whether or not the stages are correlated. Three stages with means of 50, 100 and 200 milliseconds give an end-to-end mean of 350 milliseconds.

Percentiles do not add. Suppose each of two independent stages takes 10 milliseconds with probability 0.96 and 1,000 milliseconds with probability 0.04. Each stage's p95 is 10 milliseconds, so the sum of the p95 values is 20 milliseconds. But both stages are fast together only with probability 0.96 × 0.96 = 0.9216, which is below 0.95, so the end-to-end p95 is 1,010 milliseconds. The error can also run the other way: if each stage is slow with probability 0.10, each p95 is 1,000 milliseconds and their sum is 2,000, while the end-to-end p95 is 1,010. Measure the whole journey, and use stage timings to diagnose it.

Timeouts follow the customer promise. A single payment authorisation can take thirty seconds, longer than the five-second checkout target, so after about four seconds the checkout returns "payment pending" and the coordinator continues in the background. Retrying the authorisation inside the request could never fit within five seconds.

> **In practice.** Set each timeout by working backwards from the customer promise and the recovery design. A library's default timeout reflects nobody's business requirement.

## Measure the lock-hold time

Chapter 6 estimated the lock-hold time h at about 1 millisecond for the single-statement reservation. The hot-row experiment measured it. Run alone, with no competing clients, the reservation statement took a mean of 1.4 milliseconds on the database server from the start of the update to the end of the commit, with a p99 of 3.0 milliseconds. Running alone matters, because under contention the measured time also includes waiting for the lock. With h = 1.4 milliseconds, the row's ceiling is about 1 / 0.0014 ≈ 714 reservations per second, and at 350 attempts per second its utilisation is 350 × 0.0014 = 0.49. One row is enough for Aster's own checkout, and buckets are not yet needed.

## A change card: a marketplace partner joins

Four weeks before the event, Aster receives this change card.

| Field | Content |
|---|---|
| Card | CC-A1, marketplace partner joins the event |
| New fact | The supplier raises the event allocation from 2,000 to 3,000 units if Aster's marketplace partner also sells the product. The partner's checkout expects to reserve up to 150 units per second at the peak and retries a request that gets no reply within 2 seconds |
| Source | Supplier agreement, confirmed by the partner's integration lead |
| Assumptions affected | A-A1: "only Aster's checkout reserves event stock"; A-A2: "the stock row receives at most 350 attempts per second" |
| Decisions affected | ADR-A01, one stock row at READ COMMITTED; ADR-A02, bounded admission with 50 reservations in flight |
| Question | How should the partner draw on the stock, and what does each choice change for customers? |

Three responses keep every unit sold at most once:

1. **Share the stock row through Aster's reservation API.** The partner reserves each unit with its own reservation ID. Sold-out is exact across both channels and nothing is stranded. The row's utilisation rises to 500 × 0.0014 = 0.70, which calls for two buckets (0.35 each). The partner's checkout depends on Aster's API at the busiest moment of the year, and its retries must reuse the reservation ID, because a retry with a new ID after a lost reply takes a second unit.
2. **Split the allocation: 2,000 units for Aster and 1,000 for the partner.** Nothing changes at Aster's row, which stays at a utilisation of 0.49, and there is no runtime coupling. If the partner's demand fades, or many of its reservations expire unpaid, its unsold units stay idle while Aster's customers are told "sold out"; moving them later needs a transfer protocol anyway.
3. **Allocate to the partner in blocks of 100 units.** The partner requests a block when its own stock runs low, and each block moves through the transfer protocol from Chapter 7. Aster debits its allocation into an in-transit record with a transfer ID, the partner credits the block once, and a lost reply is settled by asking about the transfer ID. About ten transfers cover the event, so Aster's row barely notices them. The partner holds at most two unsold blocks at a time, and returns unsold units through the same protocol when its sale closes.

| Option | Aster's row utilisation | Units that can be stranded | Runtime coupling | Aster engineering effort |
|---|---|---|---|---|
| 1. Shared row | 0.70, or 0.35 per bucket with two | None | Partner calls Aster for every unit | About 20 days |
| 2. Fixed split | 0.49 | Up to the partner's whole unsold share | None | About 3 days |
| 3. Blocks of 100 | 0.49 | At most 200 held by the partner | About ten transfers per event | About 12 days |

Aster's invariant gains a term in options 2 and 3. Seen from Aster, available plus reserved plus committed plus in transit plus units held by the partner equals 3,000; the partner keeps the same equation for its own units.

### Decision record

**ADR-A03: Share event stock with the marketplace partner in blocks.** Status: accepted. Amends ADR-A01 and ADR-A02.

- **Context.** CC-A1 raises the allocation to 3,000 units on condition that the partner also sells. The measured lock-hold time is 1.4 milliseconds, so Aster's own 350 attempts per second use 0.49 of the row.
- **Decision.** Allocate to the partner in blocks of 100 units through a transfer API with transfer IDs and an in-transit state. The partner may hold at most two unsold blocks and returns unsold units at its close. Aster's checkout keeps one stock row at READ COMMITTED and bounded admission.
- **Alternatives.** A shared row with per-unit reservations, rejected because it couples the partner's checkout to Aster's peak and needs buckets; a fixed split, kept as the fallback.
- **Consequences.** At most 200 units can be held unsold by the partner at any moment. Each event ends with a reconciliation of transfers and returns. The partner owns its customers' payments and confirmations.
- **Evidence.** The utilisation figures in this chapter; joint test X-A5, in which the reply to a block transfer is lost and the partner retries with the same transfer ID.
- **Review triggers.** The partner asks for per-unit reservations; measured h exceeds 2 milliseconds, which would put Aster's own row above 0.7; a second partner joins; or more than 100 units remain stranded at a close.

### Decision brief

**Decision needed two weeks before the event, from Aster's head of e-commerce:** how to share the event stock with the marketplace partner.

**What changed.** The supplier adds 1,000 units if the partner also sells. The partner's checkout expects to reserve up to 150 units per second at the peak.

**What stays the same.** In every option, no unit is sold twice, and Aster's own checkout keeps its admission rule and customer messages.

**Options.**

1. Let the partner reserve every unit through Aster's systems: no unsold units, about 20 days of work, and the partner's sale depends on Aster's systems at the peak.
2. Give the partner a fixed 1,000 units: about 3 days of work, but units can sit unsold on one channel while the other has sold out.
3. Give the partner blocks of 100 units on request: about 12 days of work, and at most 200 units can sit with the partner unsold.

**Recommendation.** Option 3, with option 2 as the fallback if the partner cannot pass the joint lost-reply test four weeks before the event.

**Risks and conditions.** The partner must implement transfer IDs correctly; a partner retry with a new transfer ID would move a second block.

## Studio assessment

Submit a transaction dossier with the invariants, the reservation rule and its tests, the state model, the admission experiment, the lock-hold measurement and your response to CC-A1. One sound worked conclusion keeps the order and allocation in one local transaction (ADR-A01) and adds buckets only if the measured lock-hold time requires them. It coordinates payment through durable states, applies bounded admission with a reviewed pending message (ADR-A02), and shares stock with the partner in blocks (ADR-A03). It postpones a separate inventory service until a multichannel ownership need or a measured contention limit justifies the extra protocol.

A distributed alternative can also pass review if it specifies reservation identity, expiry arbitration, duplicate-safe confirmation, payment reconciliation and observability across every boundary. Reviewers should challenge unsupported guarantees and unexplained operating effort, not mark a design down for differing from the worked one.

## Key points

- Small, exact tests with one unit expose concurrency and identity defects before load testing begins.
- A history is valid only if some sequential order explains every result, so check reservation IDs as well as final counters.
- An explicit transition table turns missing rules into visible errors instead of silent behaviour.
- Admission policy is a business decision, measured by confirmed orders, unresolved payments, unsold units and time to outcome.
- A second channel changes the stock invariant; sharing a row, splitting the allocation and transferring blocks trade utilisation, stranded units and coupling.
- On a serial path, means add exactly but percentiles do not, so measure the whole journey.
