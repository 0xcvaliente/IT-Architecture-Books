# 10 Pipeline alternatives and versioned publication

## Learning objectives

After this chapter you should be able to:

- Calculate average arrival rates and the processing rate that a batch window requires.
- Compare batch and streaming designs for each of Beacon's three reporting products.
- Design a replay boundary and an idempotent rule for source identity, version and content.
- Implement a publication ledger that explains both current and past results, including restated means.

## Design A: a governed batch platform

A batch design lands consistent extracts or source-supported incremental changes in restricted storage, validates them, transforms them into curated tables and computes the daily report under a run identifier. The report is published only after the required checks pass; if a run fails, the previous valid report stays visible with its timestamp.

Volume figures need care. Ten million records a day is an average arrival rate of 10,000,000 / 86,400 ≈ 115.74 records per second, which says little about batch capacity. If the nightly window is six hours, processing ten million records within it needs at least 10,000,000 / 21,600 ≈ 462.96 records per second on average, before joins, retries and checks.

Batch fits when the daily deadline and the source extract contracts dominate. It gives clear, reproducible boundaries and is simple for a small team to run, although it still needs correction handling, idempotent reruns, access control and reconciliation.

## Design B: continuous ingestion with versioned publication

A streaming design ingests change streams continuously, records each source's position, validates events and updates curated state as they arrive. The daily dashboard can still be published as a versioned snapshot, because freshness of internal state and stability of a published decision product are separate properties.

Kafka's documentation describes ordering within each partition, and transactions that let a read-process-write cycle within Kafka achieve exactly-once results {REF:kafka}. A pipeline that also writes to an external warehouse must examine that warehouse's own transaction and replay contract, because the broker's guarantee stops at its boundary. Streaming also adds continuous operation, state recovery, schema evolution and a late-data policy, and it cannot make a once-daily extract any fresher. The fair comparison is product by product:

| Product | Design A, batch | Design B, streaming |
|---|---|---|
| Daily dashboard | Fits the 07:00 deadline | Fits; published as a daily snapshot |
| Monthly snapshot | Fits; a formal close is natural | Fits, with the same close process |
| Intraday operations view | Cannot provide it | Provides it for the three streaming sources |

Many teams choose a hybrid: streaming for the sources and products that benefit, batch for the daily extracts. On Azure, Event Hubs can carry the change streams, Azure Data Factory the extracts and Fabric Data Warehouse the curated tables; on AWS, Amazon Kinesis Data Streams, AWS Glue and Amazon Redshift fill the same roles {REF:azanalytics}.

Decision record ADR-B01 chooses the hybrid for Beacon's first release. The three sources with change streams are ingested continuously, the two extract sources nightly, and the late-arriving source through the stream with a seven-day restatement window. Every product passes one publication gate and is recorded in one publication ledger, described below. The intraday view covers only the streaming sources and says so on screen. Its review triggers are: an extract source starts offering a change stream; a product needs extract data fresher than the nightly run; or restatements affect more than 5 percent of published days in a month.

## Define a replay boundary

Record the extraction or change position that each batch of input came from. When a snapshot is combined with a change stream, both must share a documented boundary, because an arbitrary file export followed by a stream started at an unrelated time can leave a gap or apply some changes twice.

Transformations must also tolerate reruns. For example, take an event with identity E:

- replaying version 3 of E must not add its measure a second time;
- a late copy of version 2 must not overwrite version 3, under a contract in which versions only increase;
- two records with the same identity and version but different content are a conflict, to be quarantined or settled by an approved rule.

Arrival order alone is no evidence of which record is right. A deletion marker needs a defined meaning too: it may mean that the source entity was deleted, that an erroneous event was withdrawn, or that a copy of personal data must be removed, and these affect the accounts differently.

## Worked publication history

Beacon's daily measure, time to first closure, is a mean, so a restatement can change both the value and the number of requests behind it. The listing keeps a **publication ledger**: each publication is appended with an identifier, its value, the exact record versions it used and the publication it supersedes, and no entry is ever edited. On day 1, two requests close at first: r1 after 4 hours and r2 after 10. A third, r3, closed after 1 hour, arrives late. The source then replays r1 unchanged, and later corrects r2's start time, so version 2 of r2 records 16 hours.

~~~
Record = tuple[str, int, int, float]      # (request, version, day, hours to close)

def latest(records: list[Record]) -> dict[str, Record]:
    """Highest version of each request; a replayed copy changes nothing."""
    best: dict[str, Record] = {}
    for r in records:
        if r[0] not in best or r[1] > best[r[0]][1]:
            best[r[0]] = r
    return best

ledger: list[dict] = []                   # publications are appended, never edited

def publish(records: list[Record], day: int, reason: str) -> None:
    rows = [r for r in latest(records).values() if r[2] == day]
    inputs = sorted((r[0], r[1]) for r in rows)
    before = next((p for p in reversed(ledger) if p['day'] == day), None)
    if before and before['inputs'] == inputs:
        print(f'{reason}: inputs unchanged, no new publication')
        return
    mean = sum(r[3] for r in rows) / len(rows)
    entry = {'id': f'P{len(ledger) + 1}', 'day': day, 'mean': mean,
             'inputs': inputs, 'supersedes': before['id'] if before else None}
    ledger.append(entry)
    note = f", supersedes {entry['supersedes']}" if before else ''
    print(f"{entry['id']} day {day}: mean {mean:.1f} h over {len(rows)} "
          f"requests{note} ({reason})")

feed = [('r1', 1, 1, 4.0), ('r2', 1, 1, 10.0)]
publish(feed, 1, 'first run')
feed.append(('r3', 1, 1, 1.0))            # a day-1 closure that arrives late
publish(feed, 1, 'late arrival of r3')
feed.append(('r1', 1, 1, 4.0))            # the source replays r1
publish(feed, 1, 'replay of r1')
feed.append(('r2', 2, 1, 16.0))           # the source corrects r2's start time
publish(feed, 1, 'correction of r2')
first, last = ledger[0], ledger[-1]
print(f"{first['id']} and {last['id']} both show {first['mean']:.1f} h:")
print(f"  {first['id']} used {first['inputs']}")
print(f"  {last['id']} used {last['inputs']}")
~~~

It prints:

~~~
P1 day 1: mean 7.0 h over 2 requests (first run)
P2 day 1: mean 5.0 h over 3 requests, supersedes P1 (late arrival of r3)
replay of r1: inputs unchanged, no new publication
P3 day 1: mean 7.0 h over 3 requests, supersedes P2 (correction of r2)
P1 and P3 both show 7.0 h:
  P1 used [('r1', 1), ('r2', 1)]
  P3 used [('r1', 1), ('r2', 2), ('r3', 1)]
~~~

Three things follow:

- The replay produces no publication, because the inputs did not change, so reruns are idempotent at the level of publications as well as records.
- Each restatement names its reason and the publication it replaces, so the dashboard can show "restated from 5.0 h: correction of r2".
- P1 and P3 show the same 7.0 hours for different reasons. A reader comparing values would conclude that nothing happened, while the ledger shows a late closure and a correction that happened to cancel out. That is why each publication stores its inputs as well as its value.

The model computes in memory; a real platform also persists the run identity, source positions, metric version, access policy and lifecycle decisions. "Never edited" describes the identity and recorded value of a publication; it grants no right to keep the underlying personal data indefinitely, as Chapter 11 discusses.

## Publication failure and partial data

When a critical source is missing, the report owner chooses between blocking the publication, publishing a clearly marked partial report, or keeping the previous version. Decide in advance which sources are mandatory for which measures, so that one late source does not block unrelated products, and make completeness machine-readable, for example with a completeness flag on each published measure.

A quality gate must be able to fail. If every anomaly is downgraded to a warning so that 07:00 is met, the gate protects nothing. Record each exception with its owner, the measures affected and an expiry date; repeated exceptions point to a requirement or source-quality problem that needs a design decision.

> **Common mistake.** Reporting only "pipeline succeeded". The pipeline's success and the report's fitness for a decision are separate claims, and only the second matters to the reader of the dashboard.

## Key points

- An average arrival rate says little about the processing rate that a batch window requires.
- Batch and streaming suit different products, and many platforms combine them.
- Replay needs a recorded source position and rules for identity, version and conflicting content.
- A publication ledger that stores each value with its inputs explains both the current corrected result and what each earlier publication showed.
- A quality gate that can never fail protects nothing, and exceptions need owners and expiry dates.
