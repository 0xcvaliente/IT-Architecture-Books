## Reconciliation beyond counts

Equal row counts can hide offsetting errors. For example, suppose a source and a target each hold three records, but one source record is missing from the target and the target holds one record that the source never sent. The counts match while two records are wrong. Each stronger check covers a different failure and has its own blind spot:

| Check | Finds | Misses |
|---|---|---|
| Key-set comparison | Missing and extra records | Wrong values on matching keys |
| Version comparison | Stale records | Errors in the source's own versioning |
| Relationship check | Orphans, such as a closure without a request | A valid but wrong reference |
| Grouped totals | Some mapping errors, such as a misassigned division | Errors that cancel out within a group |
| Digest of canonical content | Any change in content | Whether an approved transformation has the right business meaning |

Beacon reconciles each source at its declared change position or extract boundary, and the accounting must close: received records equal accepted plus quarantined plus excluded. A record excluded by policy is listed with its reason and the measures it affects. Approved transformations need their own expected values: if a status code is normalised through an approved mapping, generate the expected values from that mapping, and have the business owner review the mapping itself.

Quality rules differ in kind. "Completion time must not be negative" is structural, while "a closure requires an earlier valid receipt" is relational. A sudden shift in a distribution is a reason to investigate, because a real change in the business can also produce unusual values.

## Security follows derived copies

The same information appears in the raw landing area, curated tables, notebooks, dashboard exports and cached query results, and each is a separate place to enforce access. A catalogue label saying "restricted" enforces nothing by itself, and a dashboard filter protects nothing if users can query the unfiltered table directly.

Removing names does not make data anonymous. For example, a report of "service requests from hospitals in one town with more than 50 machines" may describe exactly one customer. Assess the audience and purpose, and apply aggregation, suppression or other approved controls where needed. The GDPR includes purpose limitation, data minimisation, storage limitation and accountability among its principles {REF:gdpr}. Beacon therefore needs a policy owner, an inventory of where data lives, and mechanisms that apply the approved lifecycle across operational and derived stores.

Deletion and recovery must agree. When a deletion or restriction is approved, identify every copy it affects. A later replay or backup restore must not quietly bring the data back, so one design keeps a controlled list of lifecycle decisions and reapplies it during every replay and restore. Some aggregates may be kept under the applicable policy while the identifiable detail behind them is removed; document what that does to reproducibility.

## Two access designs

Beacon's access rule has three parts:

- An ordinary analyst may read detail records of their own division, and only for customer organisations in their approved scope. Some customer contracts restrict who may analyse their records, so each analyst's scope is a set of tenants.
- A group analyst may read only approved consolidated aggregates, never raw detail.
- Only a designated publishing identity may publish aggregates. An export is a new copy with its own audience and lifecycle.

**Alternative A publishes separated data products.** Each division receives a curated product with a narrow audience, and consolidated reporting is a separately approved product. The access boundary is easy to see, at the cost of duplicated processing and the need to carry corrections and deletions into every product.

**Alternative B uses one shared curated store with enforced policies.** Every query carries an independently established identity and resource context, and the data service enforces the policy on every supported path. Shared views reduce duplication, but a misconfigured export identity or a direct table permission can bypass the filter, so the policy engine and the store's configuration become part of what must be assured.

NIST's zero trust architecture argues for explicit access decisions at each resource rather than trust based on network location {REF:zerotrust}, and both alternatives apply that idea at the data boundary.

### Test the policy against a written matrix

A policy test is only as good as its expected results: if the same logic generates both the policy and the expected answers, a mistake in that logic passes its own test. The listing writes the expected reads by hand from the policy statement and compares them with the policy function for every principal and resource.

~~~
PRINCIPALS = {      # authenticated identities with their approved scope
    'ana': {'role': 'analyst', 'division': 'N', 'tenants': {'T1', 'T2'},
            'active': True},
    'sam': {'role': 'analyst', 'division': 'S', 'tenants': {'T1', 'T2', 'T3'},
            'active': True},
    'gita': {'role': 'group', 'active': True},
    'pat': {'role': 'publisher', 'active': True},
}
RESOURCES = {f'{d}{t}': {'kind': 'detail', 'division': d, 'tenant': f'T{t}'}
             for d in 'NS' for t in '123'}
RESOURCES['G1'] = {'kind': 'aggregate'}

def allowed(who: str, what: str, action: str = 'read',
            check_tenant: bool = True) -> bool:
    p, r = PRINCIPALS.get(who), RESOURCES.get(what)
    if p is None or r is None or not p['active']:
        return False                                  # deny by default
    if action == 'publish':
        return p['role'] == 'publisher' and r['kind'] == 'aggregate'
    if action != 'read':
        return False
    if r['kind'] == 'aggregate':
        return p['role'] == 'group'
    return (p['role'] == 'analyst' and p['division'] == r['division']
            and (r['tenant'] in p['tenants'] or not check_tenant))

# Written by hand from the policy statement, not generated from allowed().
EXPECTED_READS = {('ana', 'N1'), ('ana', 'N2'), ('sam', 'S1'), ('sam', 'S2'),
                  ('sam', 'S3'), ('gita', 'G1')}

def failures(**options) -> list[tuple[str, str]]:
    return [(p, r) for p in PRINCIPALS for r in RESOURCES
            if allowed(p, r, **options) != ((p, r) in EXPECTED_READS)]

print('read matrix failures:', failures())
print('publishers of G1:', [p for p in PRINCIPALS if allowed(p, 'G1', 'publish')])
print('unknown action allowed:', allowed('ana', 'N1', 'delete'))
print('division-only policy failures:', failures(check_tenant=False))
PRINCIPALS['sam']['active'] = False                    # access revoked
print('sam after revocation:', [r for r in RESOURCES if allowed('sam', r)])
~~~

It prints:

~~~
read matrix failures: []
publishers of G1: ['pat']
unknown action allowed: False
division-only policy failures: [('ana', 'N3')]
sam after revocation: []
~~~

All 28 read combinations match the written matrix, only the publisher may publish, and an unknown action is denied. The fourth line shows why the tenant field matters. A plausible defect, a policy that checks the division and forgets the tenant scope, lets analyst ana read N3, a record of tenant T3 outside her scope, and the hand-written matrix catches it. After revocation, sam can read nothing. The function models the policy in memory; the same matrix must also be run against each real path: the dashboard, the notebook, a direct query and an export.

Policy changes need the same care. If an analyst loses access, can a cached result or a scheduled export still deliver records to them? Whether a job keeps a durable approval or needs current user authority must be an explicit decision, not something a token copied into a scheduler decides by accident.

## Evaluate an AI explanation feature

Beacon's sponsor asks for an assistant that explains why completion time rose last month. A grounded summary can report that the measure rose, cite its definition and point to the source tables. It should not invent a cause from a correlation, because a change in case mix, a missing source, a policy change and a genuine delay are competing explanations.

Generative AI systems can produce confident but false statements, which NIST's generative AI profile calls confabulation {REF:nist600}. The evaluation must therefore test the actual task:

- each statement is supported by the cited data and metric version;
- important caveats, such as a provisional source, are kept;
- retrieval runs with the same access scope as the user who asks;
- the assistant says so when the evidence is absent;
- a reviewer can trace every consequential statement to approved data.

NIST's AI Risk Management Framework offers a voluntary structure for organising such risks {REF:airmf}. A legitimate first release could provide a controlled metric summary with links to the data and omit causal explanations; a more ambitious feature needs stronger evaluation and clear operating responsibility.

## A change card: a deadline for corrections

Beacon's daily service figures are also sent to the sector regulator. Three months into the first release, Beacon receives this change card.

| Field | Content |
|---|---|
| Card | CC-B1, deadline for published corrections |
| New fact | From 1 July, a correction to any published daily service figure must appear on the dashboard within 24 hours of the corrected record reaching Beacon, with the reason for the restatement |
| Source | Regulator's notice, confirmed by Beacon's compliance officer |
| Assumptions affected | B-A3: "restatements can wait for the next nightly run"; B-A4: "corrections older than seven days go through an exception process with no deadline" |
| Decisions affected | ADR-B01, nightly publication with a seven-day restatement window |
| Question | How should Beacon meet the deadline, and what does each option cost? |

Start with the current design's worst case. The nightly run starts at 01:00 with every record received by then and publishes at 07:00. A corrected record that arrives at 01:01 misses that run, joins the next one 24 hours later and appears at 07:00 the following morning, about 30 hours after it arrived. If that run fails its gate, the previous publication stays visible and the correction waits another day: about 54 hours. Corrections more than seven days old are worse, because the exception process takes a median of three working days. Last quarter, about 3,000 corrected records a day touched published days, and about 40 a month were older than seven days.

The worst case depends on two things: the longest gap between runs and the time a run takes. A run that restates only the days whose inputs changed takes about 40 minutes, against six hours for the full nightly run. Three options meet the deadline when nothing fails:

| Option | Worst case | After one failed run | Extra compute | Engineering |
|---|---|---|---|---|
| 1. A second full run at 13:00 | About 18 hours | About 30 hours | About €2,100 a month | About 1 week |
| 2. Restatement runs at 09:00, 13:00, 17:00 and 21:00 | About 10 hours | About 14 hours | About €960 a month | About 3 weeks |
| 3. Continuous restatement, published hourly | About 2 hours | About 3 hours | About €3,000 a month | About 8 weeks |

Option 1 meets the deadline only if every run succeeds, which ignores the gate that Chapter 10 insisted must be able to fail. Option 3 gives far more margin than the rule needs, and figures that change every hour are harder for managers to read. Option 2 survives two consecutive failed runs at about 18 hours and three at about 22 hours, and its restatements arrive at predictable times.

Old corrections need a separate answer. The deadline applies to the daily service figures, so a correction older than seven days is restated by the next run like any other, and a data owner reviews it the following working day instead of approving it first. The finance monthly snapshot is a different product with its own close: its corrections stay as adjustments in the next month's close, with no change to the closed figures.

### Decision record

**ADR-B02: Meet the 24-hour correction deadline with four-hourly restatement runs.** Status: accepted. Amends ADR-B01.

- **Context.** CC-B1 requires corrections to published daily figures within 24 hours. The nightly-only design takes up to about 30 hours, or 54 hours after one failed run, and the exception process for old corrections has no deadline.
- **Decision.** Add restatement runs at 09:00, 13:00, 17:00 and 21:00 that recompute only days with changed inputs and publish through the same gate and ledger. Restate corrections older than seven days automatically, with review by the data owner on the next working day. Leave the finance snapshot's close unchanged.
- **Alternatives.** A second full run (fails the deadline after one failed run); continuous restatement (more cost and operation than the rule requires).
- **Consequences.** A gate failure during the day needs an owner on duty from 08:00 to 22:00. The ledger records a reason for every restatement. Daily figures may change up to five times a day while corrections arrive.
- **Evidence.** The schedule calculations in this section; a rehearsal in which three consecutive runs are failed on purpose and the correction still appears within 24 hours.
- **Review triggers.** A restatement run exceeds 90 minutes; more than one restatement run fails in a week; the regulator shortens the deadline; or corrections exceed 10,000 records a day.

### Decision brief

**Decision needed by 1 June, from Beacon's head of data:** how to publish corrections to the daily service figures within 24 hours.

**What changed.** The regulator now requires every correction to appear within 24 hours. Today a correction can take 30 hours, or 54 if a nightly run fails.

**What stays the same.** In every option, the 07:00 publication continues, every restatement shows its reason, and the finance monthly snapshot keeps its close.

**Options.**

1. Run the full publication twice a day: about €2,100 a month; meets the deadline only if no run fails.
2. Add four short correction runs during the day: about €960 a month and three weeks of work; meets the deadline even after three failed runs in a row.
3. Publish corrections continuously: about €3,000 a month and eight weeks of work; figures change every hour.

**Recommendation.** Option 2, with a daytime owner for failed runs.

**Risks and conditions.** Correction volume could grow beyond what a 40-minute run handles; the review trigger at 90 minutes catches that early.

## Key points

- Equal counts can hide offsetting errors, so reconcile key sets, versions, relationships and grouped totals, each with known blind spots.
- Access must be enforced on every derived copy and path, including exports, caches and restored backups.
- An access test needs an expected-results matrix written independently of the policy, and it should include the tenant restriction.
- A generative explanation feature must be evaluated for support, omissions, access scope and the handling of missing evidence.
- Deletion, replay and restore must agree, so that recovery never brings removed data back.
- A publication deadline is met by the gap between runs plus their duration, with margin for failed runs, and applies only to the product it names.
