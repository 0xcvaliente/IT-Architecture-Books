# 7 Reservations, payments and coordination

## Learning objectives

After this chapter you should be able to:

- Design guarded state transitions so that exactly one of expiry and confirmation wins.
- Evaluate reserve-first and pay-first orderings, including a late authorisation and a failed compensation.
- Calculate the throughput gain and the end-of-sale cost of splitting a hot stock row into allocation buckets.
- Compare orchestration and choreography for the order lifecycle.

## Model the order as durable progress

The order coordinator records each order's progress in durable states: checkout received, reserved, payment pending, payment unknown, confirmed, cancellation pending, cancelled and rejected. Every transition names the event that triggers it, the guard that must hold, its durable effect, and the operation ID that makes a repeat harmless.

A payment timeout moves the order to payment unknown, never to "declined", because the provider may have authorised the payment. The coordinator keeps the provider's operation ID and queries the outcome within the 24-hour window. Even a confirmed authorisation still needs a usable reservation: a successful payment cannot restore a unit that has already been released.

Garcia-Molina and Salem introduced **sagas**: a long-lived transaction is split into a sequence of smaller transactions, each paired with a compensating transaction that semantically undoes it if the sequence cannot finish {REF:saga}. For Aster, compensation means a business action such as releasing a reservation or voiding a payment authorisation, and a compensation can itself fail or stay pending.

## Let exactly one of expiry and confirmation win

In Design A, confirmation and expiry both act on the reservation row in the same PostgreSQL database, and each statement is guarded by the reservation's state:

~~~
-- Confirm: wins only while the reservation is active and unexpired.
UPDATE reservation SET state = 'committed'
WHERE reservation_id = $1 AND state = 'active' AND expires_at > now()
RETURNING reservation_id;

-- Expire: returns the unit only if this statement wins the same guard.
WITH expired AS (
  UPDATE reservation SET state = 'expired'
  WHERE reservation_id = $1 AND state = 'active' AND expires_at <= now()
  RETURNING sku
)
UPDATE stock SET available = available + 1
FROM expired WHERE stock.sku = expired.sku;
~~~

If confirmation commits first, the expiry statement finds the reservation no longer active and changes nothing. If expiry commits first, confirmation returns no row, and the order takes the late-authorisation path below. When the statements collide, the second waits for the first's row lock and then re-checks `state = 'active'` against the newest row version, as in Chapter 6. The database server's clock decides expiry, so there is one time authority.

Timestamps alone cannot settle the race, because two processes can both read an unexpired reservation and then act; the guard and the state change must happen together at the reservation's owner. In Design B, the inventory service owns that arbitration, and a timed-out confirm call from the order service must be retried with the same reservation ID or followed by a query. Splitting the services adds an uncertain boundary before payment is even considered.

## Late authorisation and payment ordering

Aster can reserve stock before taking payment, or authorise payment before reserving stock. Neither ordering removes partial failure; each chooses which intermediate state the business must own.

| Question | Reserve first | Authorise first |
|---|---|---|
| Is stock held while payment runs? | Yes, for up to five minutes | No |
| Main risk | Abandoned or automated checkouts hold scarce units | A payment is authorised but no unit remains |
| Late or failed outcome | Authorisation after expiry needs a fresh reservation or a void | Sold out after authorisation needs a void |
| Message while waiting | "Reserved, confirming payment" | "Payment authorised, checking stock" |

Aster reserves first, so that customers who pay do not find the product gone. The cost is a careful policy for late results. For example, reservation r1 expires at 12:05:00 and its unit returns to stock. At 12:06 the provider reports that the authorisation sent at 12:04:50 succeeded. The coordinator now:

1. tries a fresh reservation, r2, keeping the same payment operation ID;
2. confirms the order with r2 if a unit is available and the event is still open;
3. otherwise requests a void of the authorisation and moves the order to cancellation pending;
4. moves the order to cancelled only when the provider confirms the void.

A **void** cancels an authorisation before the money is captured; a **refund** returns money already captured. Which one applies depends on the payment's state at the provider. A void request can time out like any other call, and the order then stays in cancellation pending with an owner. The system must never charge again, invent stock, or mark the order cancelled merely because it sent a void.

A stricter policy holds the reservation while the payment outcome is unknown, up to a limit such as ten minutes. That reduces late authorisations but lets slow or malicious checkouts lock scarce stock. Customers need three distinct messages in any case: confirmed, payment pending, and "we are resolving your payment".

## Split the hot row into allocation buckets

Chapter 6 showed that one stock row serves at most about 1 / h reservations per second. One way to raise that ceiling is to divide the allocation across several rows of the same product, called **buckets**. Each reservation picks a bucket at random, runs the same conditional update on that bucket, and records the bucket so that a release returns the unit to it.

With k buckets and evenly spread load, the ceiling rises to about k / h. For example, with h at 4 milliseconds, one row tops out near 250 reservations per second, while eight buckets of 250 units raise the ceiling to about 2,000 per second. The invariant becomes: the sum of `available` across all buckets, plus R, plus C, equals 2,000. Each bucket's conditional update keeps that bucket at or above zero, so the total never goes negative.

Buckets have costs at the end of the sale:

- **Misses.** When units remain in only some buckets, a random pick often finds an empty one. With 30 units left in 3 of 8 buckets, the first pick misses 5 / 8 = 62.5 percent of the time, so the service must try the other buckets before answering "sold out".
- **Fairness.** Arrival order is not preserved across buckets, so a later customer can win a unit an earlier one missed.
- **Rebalancing.** Moving units between buckets in one database is a single local transaction.

Some retailers instead place allocations in separate regional databases, so that each region can keep selling while the regions are disconnected. Moving units then needs a transfer protocol. If West moves 100 units to East, West debits its allocation into a durable in-transit record with a transfer ID, and East credits the units exactly once using that ID. Conservation reads: available, plus reserved, plus committed, plus in transit, equals 2,000. If East's reply is lost, West must ask East about the transfer ID rather than reclaim the units, and a region restored from an old backup must replay the transfer history before it sells again.

Buckets are a throughput tool; regional allocations are an availability tool with a much heavier protocol. Aster's event needs throughput, so buckets fit.

## Orchestration or choreography

A central coordinator makes each order's progress and exceptions explicit, at the cost of one more component to operate. Choreography, in which services react to each other's events, spreads the logic and makes the lifecycle harder to reconstruct. Either can preserve the invariants when contracts and ownership are clear. For this studio a durable order coordinator is a sound start, because payment, expiry and compensation need a visible process. Notifications can consume `OrderConfirmed` events independently, because a failed email should never reverse a valid order.

## Key points

- An order's progress is a durable state machine in which each transition has a trigger, a guard, an effect and an operation ID.
- Guarded updates at the reservation's owner ensure that exactly one of expiry and confirmation wins.
- A late authorisation needs a fresh reservation or a void, and a void that times out stays visible as cancellation pending.
- Buckets raise a hot row's ceiling to about k / h but create end-of-sale misses that the service must handle.
- Allocations in separate regions trade a transfer protocol and harder recovery for the ability to sell while disconnected.
