# 1 Thinking like an architect

## Learning objectives

After this chapter you should be able to:

- Explain what makes a design decision architecturally significant.
- Compare the responsibilities of solution, software, cloud, data and enterprise architects.
- Classify quality requirements with the ISO/IEC 25010 product quality model.
- Write a reviewable architecture decision with a reason, consequences and a review trigger.
- Distinguish definitions, empirical claims, formal results and recommendations in a design argument.

## Architecture as decisions with consequences

An **IT architecture** describes the significant structure of a system or organisation and the reasoning behind it. Structure includes:

- responsibilities and the interfaces between them;
- who owns which data;
- deployment and trust boundaries;
- operational arrangements, such as who deploys changes and who responds to incidents.

The decisions that matter most are the ones that are expensive to reverse or that affect several teams.

Consider Meridian's goal of a single service portal. A developer might start by building a service request form. An architect asks further questions:

- Which system is the authority for a service request, and from what moment?
- How is the same person identified in the portal, the CRM and ERP?
- Can the portal accept requests while the CRM is unavailable?
- Who operates the integration, and who is called when it fails?
- How does a deletion request reach every copy of the data?

Each answer changes responsibilities and failure behaviour.

Architecture exists even when nobody draws it. If every service can modify a shared database, that is an architectural choice. If only one person can deploy to production, that is an operational dependency. The architect makes such choices visible, examines alternatives and helps the team agree on an approach.

A good architectural statement has a reason and a consequence. “Use a queue” is incomplete. Compare it with this: “Store each service request durably and queue the CRM handoff, because a CRM outage must not prevent submission. Run a reconciliation job, and show customers ‘Received’ until the CRM confirms the handoff.” That statement can be reviewed, tested and challenged.

## Architect roles

Several roles share the title of architect. They differ mainly in scope.

| Role | Main focus | Typical Meridian question |
| --- | --- | --- |
| Solution architect | One business outcome across applications, data, infrastructure, security and delivery | How do the parts deliver the portal outcome? |
| Software architect | Application structure, modules, interfaces and maintainability | Where should the CRM adapter boundary sit? |
| Cloud architect | Cloud organisation, networking, identity, deployment and operations | Which networks, zones and accounts does the portal use? |
| Data architect | Information models, ownership, movement, quality and use | Which system owns asset facts, and how fresh is the portal's copy? |
| Enterprise architect | The portfolio: capabilities, duplication, standards and roadmaps | Should other business units reuse this integration? |

The responsibilities overlap. In a small organisation one person may hold several of them; in a large programme the challenge is to connect their decisions. Seniority or access to a diagramming tool does not make someone an architect. The role rests on the ability to explain how the problem, the design, the expected result and the supporting facts fit together.

## Quality attributes are design inputs

A feature describes something the system does. A **quality attribute** describes how well it does it, or under what conditions. For example:

- Searching for service requests is a feature.
- Returning search results within two seconds at a stated workload is a performance requirement.
- Showing results only to authorised service agents is a security requirement.
- Restoring service after a database failure is a reliability requirement.

The international standard ISO/IEC 25010 gives a shared vocabulary for these properties. Its 2023 product quality model has nine characteristics, each refined into sub-characteristics {REF:iso25010}. The table illustrates each one with a Meridian requirement.

| Characteristic | Meridian example |
| --- | --- |
| Functional suitability | A receipt identifies the submission and the asset |
| Performance efficiency | 95 percent of receipts within one second at peak |
| Compatibility | Portal and CRM exchange cases through an agreed contract |
| Interaction capability | Customers can submit using only a keyboard |
| Reliability | A thirty-minute CRM outage loses no accepted request |
| Security | Agents see only their authorised customer organisations |
| Maintainability | A CRM field rename changes only the CRM adapter |
| Flexibility | The portal can move to another hosting region |
| Safety | A work order always shows the asset's hazard warnings |

Use the model as a checklist when you gather requirements. It helps you notice a missing concern, such as compatibility with the CRM. It does not rank the characteristics; the business context does that.

Quality attributes often conflict:

- Stronger isolation between tenants usually costs more.
- Immediate consistency across remote systems can reduce availability during a network fault.
- Highly flexible configuration makes testing harder.

Naming a fashionable pattern does not remove a trade-off. The architect makes each trade-off explicit and agrees it with the people who bear its cost.

Cloud providers publish review frameworks built around similar concerns. The AWS Well-Architected Framework has six pillars: operational excellence, security, reliability, performance efficiency, cost optimisation and sustainability {REF:awswa}. The Azure Well-Architected Framework has five: reliability, security, cost optimisation, operational excellence and performance efficiency {REF:azurewa}. Use them as prompts for review questions. A design can answer every prompt and still be wrong for the business.

## A decision loop

Most architecture work follows a loop:

1. Start with the outcome and the constraints.
2. Identify the riskiest unknowns.
3. Form two or three credible options, including a simple one.
4. Compare the options against measurable requirements.
5. Reduce the biggest uncertainty with a small experiment: a prototype, a data sample, a stakeholder interview or a recovery test.
6. Record the decision and the conditions that would justify revisiting it.

For Meridian, the riskiest unknown may be how the CRM API behaves when it receives the same submission twice. Do not start by building an integration platform. Read the CRM contract and run a controlled test with test records. If the CRM honours an idempotency key, or an upsert keyed on an external reference, the design stays simple. If it offers only a plain create operation, the design needs a stronger reconciliation strategy.

> **Common mistake.** Starting from a technology (“we need an event streaming platform”) and then looking for a problem it solves. Start from the outcome and the riskiest unknown; a technology must then earn its place against a simpler option.

Treat architecture as a sequence of decisions held at different levels of confidence, and label each assumption. A useful architecture document can say that a dependency's rate limit is still unconfirmed and that the release depends on confirming it. An attractive diagram that hides this uncertainty is less useful.

## Worked example: find where the problem arises

Meridian considers three options: build a custom portal, buy the CRM vendor's portal, or keep the current forms and improve integration. The business goal is fewer duplicate records and less manual follow-up.

The architect traces twenty recent duplicate records. Most arise after approval: a service agent copies the approved service case into ERP by hand, and sometimes does it twice. A better form would leave that step untouched. The design therefore adds three elements:

- the CRM emits a `ServiceCaseApproved` event when an agent approves a case;
- a work-order integration consumes the event and creates the ERP work order, using the service case ID as the idempotency key, so a repeated event cannot create a second work order;
- the integration is monitored and has a named owner.

A custom portal may still be justified for accessibility or customer experience, but that needs its own case. This is architectural leverage: understanding where the problem arises changes what must be built.

## Your first architecture decision record

An **architecture decision record** (ADR) captures one significant decision. Nygard's format has four parts: context, decision, status and consequences {REF:adr}. Many teams add the alternatives considered and the tests or data behind the choice. Keep each ADR to one decision.

A first Meridian ADR might read:

- **Context.** Customers need a receipt even when the CRM is down. The CRM remains the system of record for service cases.
- **Decision.** The portal owns the submission receipt and the status customers see before handoff. The CRM owns the service case once it confirms the handoff.
- **Status.** Accepted.
- **Consequences.** The team maps CRM case statuses to customer-visible statuses, shows “Received, awaiting service team” while a handoff is delayed, and reconciles handoffs that stay unconfirmed.
- **Review trigger.** Revisit if the CRM cannot store a stable external reference for each submission.

A review trigger keeps a decision adaptable without making it vague. An ADR should never leave two systems owning the same status without saying how conflicts are resolved.

## Separate kinds of claim

Architecture arguments mix four kinds of statement. Keep them apart, because none can stand in for another:

- A **definition** fixes your model: “A deployment unit contains these modules.”
- An **empirical claim** reports an observation under a workload: “The service handled 200 requests per second in this test.”
- A **formal result** holds under stated assumptions: “While a majority of servers keep their stored logs, this algorithm never loses a committed entry.”
- A **recommendation** argues from the other three to a choice in context: “Choose this design.”

For example, the claim “an asynchronous handoff lets customers submit during a CRM outage” is conditional. It holds only if the portal's own database stays available, the backlog fits the available capacity, and the business accepts that case creation is delayed. The recommendation also depends on who operates the worker and what reconciliation costs. Check these premises before arguing about products. A source can establish a mechanism and still leave the decision for your context to you.

A decision ledger keeps the reasoning visible:

| Claim | Basis | Assumption | Confidence | Revisit if |
| --- | --- | --- | --- | --- |
| The CRM idempotency key prevents duplicate cases for 24 hours | Contract review and a duplicate-key test in the vendor sandbox | Production API behaves like the sandbox | High | Vendor releases a new API version |
| The CRM external reference is unique | Vendor documentation is silent | None yet | Low | Vendor confirms uniqueness in writing |
| Peak is 20 submissions per second | Logs from two past equipment incidents | Incidents stay a similar size | Medium | Customer count rises by 25 percent |

State the basis of each confidence level, and keep low-confidence claims out of the design's guarantees until they are confirmed. “Verified with a duplicate-key test in the vendor sandbox” tells a reviewer far more than “90 percent confident”.

## Exercises

1.1 Explain why choosing PostgreSQL is an architectural decision in one project but a routine implementation choice in another.

1.2 Write a five-sentence problem brief for Meridian. Include an outcome, a current obstacle, two constraints and one unknown. Do not name a solution.

1.3 A stakeholder asks for microservices because the platform “must be modern”. Write a response that respects the concern and sets up a decision process.

1.4 Classify each Meridian requirement by its ISO/IEC 25010 characteristic: (a) the receipt API answers 95 percent of valid submissions within one second; (b) a thirty-minute CRM outage loses no accepted request; (c) an agent sees only authorised customer organisations; (d) a CRM field rename changes only one module. Then name one pair that may conflict and explain why.

1.5 Critique this decision statement and rewrite it as a reviewable decision: “We will put all integrations on an event streaming platform to future-proof the architecture.”

## Key points

- Architecture is the set of significant decisions about structure and responsibility, together with the reasons for them.
- Quality attributes are design inputs. ISO/IEC 25010 names them; the business context ranks them, and they often conflict.
- Find where a problem actually arises before deciding what to build.
- Record decisions in ADRs with consequences and review triggers.
- Keep definitions, observations, formal results and recommendations separate in every argument.
