# 6 Databases and transactional data design

## Learning objectives

After this chapter you should be able to:

- Design a normalised relational schema with tenant-qualified keys and constraints that protect business facts.
- Compare the silo, bridge and pool tenancy models, and enforce the pool model with row-level security.
- Explain what each isolation level permits, including write skew under snapshot isolation.
- Design a concurrency control for an invariant that spans several rows.
- Evaluate range, hash and directory partitioning by their effect on queries and transactions.

## Begin with business facts

A data model records what the organisation considers true. For Meridian:

- a customer organisation registers many assets;
- an asset can have many service requests over its lifetime;
- each service request names one asset and the user who submitted it.

Identify the **entities** (customer organisation, asset, service request), their **attributes**, the **relationships** between them, their **identifiers** and their **lifecycle**. Choose identifiers with care. For example, an email address is an attribute that can change, so it makes a poor global identifier. Use a stable internal identifier and manage external identifiers explicitly.

## Relational reasoning and normalisation

Codd's relational model separates the logical meaning of data from its physical storage {REF:codd}. Applications state which facts they want, and the database decides how to find them, so adding an index changes speed without changing meaning. The lesson for architects is to model business facts first and treat retrieval mechanisms as a separate concern.

**Normalisation** removes avoidable duplication and the anomalies it causes. Consider a single wide table of requests:

| tenant | request | asset | asset_type | contract | contract_expiry | submitted_at |
| --- | --- | --- | --- | --- | --- | --- |
| t-017 | r-1 | a-204 | Pump | k-55 | 2027-03-31 | 2026-09-02 |
| t-017 | r-7 | a-204 | Pump | k-55 | 2027-03-31 | 2026-10-05 |
| t-017 | r-9 | a-311 | Valve | k-55 | 2027-03-31 | 2026-10-06 |

The business declares three **functional dependencies**, meaning that one set of values determines another:

- (tenant, asset) determines asset_type and contract;
- (tenant, contract) determines contract_expiry;
- (tenant, request) determines asset and submitted_at.

Repeating these facts on every request causes three anomalies:

- **Update anomaly.** Extending contract k-55 means changing three rows; missing one leaves the data contradicting itself.
- **Deletion anomaly.** Deleting request r-9 also deletes the only record that a-311 is a valve.
- **Insertion anomaly.** A new asset cannot be recorded until someone submits a request for it.

Decompose the table into Asset (tenant, asset, asset_type, contract), Contract (tenant, contract, expiry) and ServiceRequest (tenant, request, asset, submitted_at), each with its tenant-qualified key. Every non-key attribute then depends on the whole key of its own table, and each fact is stored once. Joining the three tables on the full tenant-qualified keys reconstructs the original rows exactly. A join on the contract number alone would invent false rows if two tenants reuse the same number.

Normalisation does not force every historical value to follow the current master record. The contract terms that applied when a request was approved are a different fact from the contract's current state. Model that snapshot explicitly, with its time and meaning. Deliberate denormalisation can help reporting or performance, but then the design needs a refresh and consistency strategy.

In Meridian, ERP owns assets and contracts. The portal keeps a cached read model of those facts, labelled with the source version and its freshness, and the same decomposition applies to it.

## Keys and constraints

Constraints let the database protect facts on every write path {REF:constraints}:

- A **primary key** identifies a row.
- A **unique constraint** enforces uniqueness for another candidate key.
- A **foreign key** requires a referenced row to exist.
- A **check constraint** restricts the allowed values.
- `NOT NULL` states that a value must be present.

In a database shared by many tenants, include the tenant in the keys and relationships. A foreign key on `asset_id` alone proves that some asset exists, but not that it belongs to the same tenant as the request. The schema below makes the pair (tenant, asset) the reference instead.

Two identifiers describe each submission, and they do different jobs:

- The **submission key** is chosen by the client, such as a random value the browser creates when the form opens. It travels in the `Idempotency-Key` header and lets the API recognise a retry. Keys are scoped to the tenant and the submitting user, so two users who happen to choose the same key create two separate requests.
- The **submission ID** is a UUID that the portal assigns when it stores the request. It identifies the request in the receipt and the status URL, and the handoff worker sends it to the CRM as the idempotency key and external reference.

~~~sql
CREATE TABLE asset (
    tenant_id TEXT NOT NULL,
    asset_id  TEXT NOT NULL,
    title     TEXT NOT NULL,
    PRIMARY KEY (tenant_id, asset_id)
);

CREATE TABLE customer_user (
    tenant_id TEXT NOT NULL,
    user_id   TEXT NOT NULL,   -- subject from the identity provider
    PRIMARY KEY (tenant_id, user_id)
);

CREATE TABLE service_request (
    tenant_id      TEXT NOT NULL,
    submission_id  UUID NOT NULL,
    asset_id       TEXT NOT NULL,
    submitted_by   TEXT NOT NULL,
    submission_key TEXT NOT NULL,
    payload_hash   TEXT NOT NULL,
    received_at    TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (tenant_id, submission_id),
    UNIQUE (tenant_id, submitted_by, submission_key),
    FOREIGN KEY (tenant_id, asset_id) REFERENCES asset (tenant_id, asset_id),
    FOREIGN KEY (tenant_id, submitted_by)
        REFERENCES customer_user (tenant_id, user_id)
);

CREATE TABLE outbox (
    event_id      UUID PRIMARY KEY,
    tenant_id     TEXT NOT NULL,
    submission_id UUID NOT NULL,
    event_type    TEXT NOT NULL,
    state         TEXT NOT NULL DEFAULT 'pending'
        CHECK (state IN ('pending', 'in_flight', 'confirmed',
                         'retry_due', 'manual_review')),
    attempts      INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (tenant_id, submission_id)
        REFERENCES service_request (tenant_id, submission_id)
);
~~~

In PostgreSQL 18 this schema rejects four kinds of bad write:

- a request in tenant `t-017` that names asset `a-9` of tenant `t-023`, because the pair (`t-017`, `a-9`) does not exist in `asset`;
- a request whose submitter is not a customer user of the same tenant;
- a second request from the same user in the same tenant with an already used `submission_key`;
- an outbox state outside the five handoff states, such as `failed`.

A stored `service_request` row means the request is `received`. The `outbox` row tracks delivery to the CRM, and the CRM's own case status is kept separately, as Chapter 10 explains. Storing `payload_hash` with the scoped key lets the API recognise a genuine retry, which repeats the same content, and reject reuse of the key with different content.

The schema protects only part of the model. It cannot authenticate a caller or block every invalid workflow transition. The application must take `submitted_by` from the authenticated identity, never from the request body, and enforce business permissions.

{FIG:erd} adds the surrounding entities to the listing. Read a label such as “1 to 0..many” as a cardinality, not as a data flow. One asset has zero or more service requests, one customer user submits zero or more of them, and each request names one asset and one submitter. Each request has an initial outbox record, and later messages may add more. Attachment metadata references a request and a separately stored object. A production design adds timestamps, attempt history and retention rules, including how long submission keys stay unique.

## Multi-tenant data: silo, bridge and pool

A multi-tenant system must decide how much each tenant's data and resources are separated. Three models are common {REF:tenancy}:

- **Silo.** Each tenant gets its own resources, such as its own database. Isolation is strongest and per-tenant tuning is easy, but cost and operational effort grow with every tenant.
- **Bridge.** Some parts are shared and others are separate. At the data tier, a bridge typically keeps every tenant in one database but gives each tenant its own tables, so their structure can differ {REF:saasstorage}.
- **Pool.** All tenants share the same resources, and every row carries a tenant identifier. Cost per tenant is lowest, but one mistake in a query can expose another tenant's data, and one busy tenant can slow the others.

FIGURE tenancy_models | Silo, bridge and pool tenancy models trade isolation against cost and operational effort.

{FIG:tenancy_models} compares the three. Meridian has 600 tenants, most with modest data, so the pool model fits. A silo would mean running 600 databases. A large customer with a contractual demand for separate storage could still be placed in its own silo, giving a mixed estate.

The pool model needs strong guards against cross-tenant reads. Tenant-qualified keys help, and PostgreSQL's **row-level security** (RLS) adds a second line of defence inside the database {REF:rls}. A policy filters every query on a table, even one that forgets its `WHERE` clause.

~~~sql
ALTER TABLE service_request ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_scope ON service_request
    USING (tenant_id = ANY (string_to_array(
               current_setting('app.tenant_ids', true), ',')))
    WITH CHECK (tenant_id = ANY (string_to_array(
               current_setting('app.tenant_ids', true), ',')));

-- Per transaction, after the application has authorised the caller:
BEGIN;
SELECT set_config('app.tenant_ids', 't-017,t-023', true);
SELECT tenant_id, submission_id FROM service_request;
COMMIT;
~~~

The setting holds a set of tenants because one service agent can serve several customer organisations; a customer's set has one member. The third argument of `set_config` makes the value local to the transaction, so a pooled connection cannot carry one caller's scope into the next request. In PostgreSQL 18 the policy behaves as follows:

- With the setting absent, `current_setting(..., true)` returns null and the query returns no rows. Missing context denies access.
- On a pooled connection where an earlier transaction set the variable, `current_setting(..., true)` returns an empty string rather than null once that transaction ends. `string_to_array('', ',')` is an empty array, so the policy still matches no rows; write `NULLIF(current_setting(...), '')` if you prefer the two cases to look the same.
- With the setting `t-017`, the query returns only `t-017` rows, and an insert for `t-023` fails with a row-level security error.
- Connected as the table's owner, the same query returns every row.

The last result is the most important. Superusers and roles with the `BYPASSRLS` attribute always skip the policies. A table's owner skips them too, unless the table is altered with `FORCE ROW LEVEL SECURITY`. The application must therefore connect as a separate role that owns no tables and has neither attribute. RLS enforces the tenant boundary only. The application still checks the business unit, request ownership and delegation rules described in Chapter 9.

## Transactions and invariants

A **transaction** groups operations into one unit. The four ACID properties describe what a database promises about it:

- **Atomicity**: all of the transaction's changes take effect, or none do.
- **Consistency**: each committed transaction moves the database from one valid state to another, as defined by its constraints.
- **Isolation**: concurrent transactions are protected from each other's intermediate states, to a degree set by the isolation level.
- **Durability**: once committed, changes survive a crash.

Consistency here means respecting the database's own rules. It is a different idea from the consistency of distributed replicas in Chapter 12.

Atomicity helps only when the transaction contains every operation that protects the invariant. Meridian's invariant is that every received request has a durable handoff record. The API therefore inserts the `service_request` row and its `outbox` row in one transaction. Sending to the CRM happens after the commit, because the vendor's system cannot take part in the portal's transaction.

## Isolation levels

**Isolation** determines what concurrent transactions can observe of each other. PostgreSQL offers three distinct levels {REF:isolation}:

| Level | What a transaction sees | Write skew |
| --- | --- | --- |
| Read Committed (default) | A fresh snapshot for each statement | Possible |
| Repeatable Read | One snapshot for the whole transaction; this is snapshot isolation | Possible |
| Serializable | Snapshot isolation plus detection of dangerous patterns of dependencies | Prevented; one transaction is aborted |

Under Repeatable Read and Serializable, a transaction can fail with a **serialisation failure**, SQLSTATE `40001`. The application must catch it and retry the whole transaction. Products differ in what each level name means, so always check the documentation of the database in use.

## Claiming work safely

Two workers poll the outbox and both see event `ev-1` in state `pending`. If each reads the row, decides to send it and then updates it, both send it. This **check-then-act** race happens because reading and writing are separate steps.

A conditional update makes the claim atomic. The `WHERE` clause includes the expected state, so only one worker's update can match. This listing runs the two claims one after the other with SQLite to show the effect:

~~~python
import sqlite3

db = sqlite3.connect(":memory:")
db.execute("""CREATE TABLE outbox (
    event_id   TEXT PRIMARY KEY,
    state      TEXT NOT NULL CHECK (state IN ('pending', 'in_flight',
                   'confirmed', 'retry_due', 'manual_review')),
    claimed_by TEXT)""")
db.execute("INSERT INTO outbox VALUES ('ev-1', 'pending', NULL)")
db.commit()

CLAIM = """UPDATE outbox SET state = 'in_flight', claimed_by = ?
           WHERE event_id = ? AND state IN ('pending', 'retry_due')"""

for worker in ("worker-a", "worker-b"):
    with db:  # one transaction per claim attempt
        claimed = db.execute(CLAIM, (worker, "ev-1")).rowcount
    print(worker, "claimed ev-1" if claimed == 1 else "found nothing to claim")
print(db.execute("SELECT state, claimed_by FROM outbox").fetchone())
~~~

Running it prints:

~~~
worker-a claimed ev-1
worker-b found nothing to claim
('in_flight', 'worker-a')
~~~

When the two updates really are concurrent in PostgreSQL, the second waits for the first's row lock. Under Read Committed it then re-checks the `WHERE` clause against the updated row and changes nothing. A production claim also records a **lease**, a time-limited right to work on the record, so that work held by a crashed worker returns to `retry_due` when the lease expires.

The same idea gives **optimistic concurrency control** for edits. Add a `version` column and make the expected version part of the write condition, as in `WHERE submission_id = ? AND version = 7`. If no row changes, someone else updated first; reread the row and decide again rather than overwriting their change.

Neither technique solves the lost response at the remote system. If the CRM accepts a handoff and the reply is lost, the worker cannot tell whether to resend. It needs an idempotent remote operation, here the submission ID as idempotency key, or a lookup by a stable external reference.

## Write skew: the doctors on call

Some invariants span several rows. The classic illustration is a hospital that must always have at least one doctor on call for each shift {REF:kleppmann}. Two doctors, Ada and Ben, are on call for shift 1234, and each feels unwell. Each opens a transaction that counts the doctors on call and, if the count is at least two, takes themselves off call.

| Step | Transaction A (Ada) | Transaction B (Ben) |
| --- | --- | --- |
| 1 | Begin at Repeatable Read | Begin at Repeatable Read |
| 2 | Count doctors on call: 2 | |
| 3 | | Count doctors on call: 2 |
| 4 | Set Ada off call | |
| 5 | | Set Ben off call |
| 6 | Commit succeeds | |
| 7 | | Commit succeeds |

FIGURE write_skew | Two transactions each preserve the rule in their own snapshot, but their combined writes violate it.

The final state has nobody on call ({FIG:write_skew}). Each transaction made a sound decision in its own snapshot. The two updates touched different rows, so a mechanism that detects only competing writes to the same row sees no conflict. Berenson and colleagues named this anomaly **write skew** and showed that snapshot isolation permits it {REF:berenson}. PostgreSQL's Repeatable Read level is snapshot isolation, so it allows exactly this schedule. A check constraint on each row cannot help either, because each row on its own is valid; the rule concerns the pair.

> **Common mistake.** Assuming that Repeatable Read means serializable. In PostgreSQL it is snapshot isolation, which prevents many anomalies but permits write skew.

### Four ways to protect the rule

There are four defensible fixes.

1. **Use Serializable and retry.** PostgreSQL's Serializable level uses serializable snapshot isolation (SSI), which tracks read–write dependencies between concurrent transactions {REF:cahill,ports}. It detects the dangerous pattern above and aborts one transaction with SQLSTATE `40001`. The application retries the whole transaction, including the count, so the retried decision sees Ada already off call and refuses.
2. **Lock the rows the decision reads.** PostgreSQL does not allow `FOR UPDATE` on an aggregate such as `count(*)`, so select the on-call rows themselves with `FOR UPDATE` and count them in the application, as in the listing below. The second transaction then waits for the first to commit and sees the updated row before it decides. Row locks cover only rows that already exist: a doctor inserted concurrently as a new on-call row is a phantom that this fix does not stop, which is why fixes 3 and 4 lock or update a single shift row instead.
3. **Materialise the conflict.** Create a row that stands for the shift and lock it with `SELECT ... FOR UPDATE` before reading the doctors. Every transaction that changes the roster must follow the same protocol.
4. **Turn the rule into a constraint.** Keep an on-call count in the shift row, protected by `CHECK (on_call_count >= 1)`, and decrement it in the same transaction as the doctor's row. Concurrent decrements of one row are serialised, and the one that would reach zero fails. Every path that changes the roster must maintain the count.

~~~sql
-- Fix 1: let the database detect the conflict, and retry on 40001.
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT count(*) FROM on_call WHERE shift_id = 1234 AND on_call;
-- the application continues only if the count is at least 2
UPDATE on_call SET on_call = false
WHERE shift_id = 1234 AND doctor = 'Ada';
COMMIT;

-- Fix 2: lock every row that the decision depends on.
BEGIN;
SELECT doctor FROM on_call WHERE shift_id = 1234 AND on_call FOR UPDATE;
UPDATE on_call SET on_call = false
WHERE shift_id = 1234 AND doctor = 'Ada';
COMMIT;
~~~

### Retry and test

A retry must repeat the decision as well as the write. Resubmitting only the final `UPDATE` would reuse a premise that is no longer true. Give the retry loop a limit and show the caller a clear outcome when it is exhausted. Keep external actions, such as sending an email or calling a payment provider, outside the retried transaction, behind a durable intent such as an outbox record.

To test any of these fixes, run two sessions and pause both after their reads, using a barrier, before either writes. A serial test cannot reveal write skew. Record the isolation level, which transactions commit or abort, and the final state.

The choice of fix depends on the predicate. Change the rule so that each region must keep one qualified doctor on call, with some doctors covering several regions. A single count per shift no longer represents it. Start from the predicate and who owns it, then choose the mechanism.

## Indexes and query shape

An **index** is an access structure that lets the database find rows without reading the whole table. It uses space and must be updated on every write, so indexing every column is a poor default.

Start from the queries. For example, if service agents often list pending requests for one tenant ordered by time, an index on (`tenant_id`, `received_at`) may serve both the filter and the order. Measure with realistic data, including skew: one tenant with most of the rows behaves very differently from an even spread.

Read the **execution plan** to see how the database intends to find rows. In PostgreSQL, `EXPLAIN` shows the plan, while `EXPLAIN ANALYZE` also runs the statement and reports what happened {REF:explain}. Take care with `EXPLAIN ANALYZE` on statements that change data, because they really execute. Statistics, cache state and concurrent load all affect what the plan shows.

## Partitioning and sharding

When one table or one server becomes too large, split the data. **Partitioning** divides a table into pieces inside one database. **Sharding** places the pieces on separate database servers. Partitioning by key range and by hash of the key are the two classic schemes {REF:kleppmann}, and many systems add a directory:

- **Range.** Each piece holds a range of keys, such as one month of requests. Range scans stay efficient and old months are easy to archive, but all new writes land in the latest range, which can become a hot spot.
- **Hash.** A hash of the key chooses the piece. Load spreads evenly, but a range query must visit every piece.
- **Directory.** A lookup table records which piece holds each key, such as each tenant. Placement is flexible, so a large tenant can be moved on its own, but the directory becomes a critical dependency.

Naive hashing makes growth expensive. The listing assigns Meridian's 600 tenants to shards with `crc32(tenant) mod n`:

~~~python
import zlib

def shard(tenant: str, shards: int) -> int:
    return zlib.crc32(tenant.encode()) % shards

tenants = [f"t-{n:03d}" for n in range(1, 601)]
moved = sum(shard(t, 4) != shard(t, 5) for t in tenants)
print("t-017: shard", shard("t-017", 4), "of 4, shard", shard("t-017", 5), "of 5")
print(f"{moved} of {len(tenants)} tenants move when 4 shards become 5")
~~~

Running it prints:

~~~
t-017: shard 0 of 4, shard 1 of 5
465 of 600 tenants move when 4 shards become 5
~~~

Adding one shard moves more than three-quarters of the tenants. Systems avoid this by creating many more partitions than servers and moving whole partitions, by consistent hashing, or by a directory.

The shard key shapes queries and transactions:

- A query that includes the shard key goes to one shard. Any other query must ask every shard and merge the results.
- A transaction inside one shard keeps its local ACID guarantees. A transaction across shards needs a distributed commit protocol or a redesign.
- A unique constraint is enforced per shard, so a global uniqueness rule must include the shard key.

For Meridian, the tenant is the natural shard key: a request, its asset and its outbox record then share one shard, and the receipt transaction stays local. An agent's work queue that covers several tenants becomes a query across shards. At 100,000 requests a year, however, one database serves Meridian comfortably. Partitioning by month might simplify archiving, and sharding would add cost without benefit.

## Choose a storage model

Different stores suit different access patterns:

- **Relational databases** fit when relationships, constraints and multi-row transactions matter.
- **Document stores** fit aggregate-shaped data with flexible fields.
- **Key-value stores** fit simple access by key.
- **Graph databases** fit traversals across many relationships.
- **Column-oriented analytical stores** fit large scans and aggregations, as Chapter 7 explains.

Choose from access patterns and guarantees rather than from the label SQL or NoSQL. Many products support several models, and many NoSQL databases offer transactions within stated limits, so read the exact contract.

Store large files in object storage and keep controlled references in the operational database. Plan for partial failure: the upload can succeed while the metadata insert fails, or the reverse. A staged state and a clean-up process handle both.

## Backup and recovery

**Replication** copies changes to another server for availability or read capacity. It also copies mistakes: an accidental deletion reaches every replica within seconds. A **backup** is a recoverable historical copy with its own integrity, access and retention rules. Test restoration regularly, in an isolated environment.

Two objectives describe recovery:

- The **recovery point objective** (RPO) is the maximum acceptable data loss, measured back in time from the failure.
- The **recovery time objective** (RTO) is the maximum acceptable time to restore service.

A nightly backup alone cannot meet a five-minute RPO, and a successful backup job does not prove that a two-hour restore is possible. Only a timed restore test shows that.

## Key points

- Model business facts first, normalise to remove anomalies, and qualify keys with the tenant in a shared database.
- Constraints protect facts on every write path; row-level security adds a tenant guard in pooled databases, provided the application never connects as the owner.
- Snapshot isolation, which is PostgreSQL's Repeatable Read, permits write skew. Serializable detects it and aborts one transaction with SQLSTATE `40001`, which the application retries.
- Protect multi-row invariants with Serializable and retry, `FOR UPDATE` on the rows read, a materialised conflict, or a constraint on a maintained count.
- Choose a shard key that keeps each transaction on one shard; range, hash and directory schemes trade query shape against rebalancing cost.
