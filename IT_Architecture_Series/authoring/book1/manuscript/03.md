# 3 Architecture models and technical communication

## Learning objectives

After this chapter you should be able to:

- Explain the ISO/IEC/IEEE 42010 concepts of stakeholder, concern, viewpoint and view.
- Compare the C4 model, the 4+1 view model and the arc42 template.
- Design a context view whose relationships state direction, purpose and ownership.
- Evaluate a set of views for consistency by following one identifier through all of them.
- Critique a diagram or decision record whose meaning is ambiguous.

## One system needs several views

A diagram is a selective model. Different people ask different questions of the same system:

- A business stakeholder wants to know who uses the system and what outcome it supports.
- A developer needs component responsibilities and interfaces.
- An operator needs deployment locations, failure domains, dependencies and recovery paths.
- A security reviewer needs trust boundaries and the flows of sensitive data.

Putting all of this into one diagram makes it hard to read and easy to misinterpret. Give each view a purpose. State its scope, audience and level of detail, and say what the arrows mean. Use the same names for the same things in every view.

## Describing architecture: ISO/IEC/IEEE 42010

The standard ISO/IEC/IEEE 42010 defines what an architecture description should contain, without prescribing a notation {REF:iso42010}. Its core terms give a precise way to talk about views:

- A **stakeholder** is a person or group with an interest in the system, such as Meridian's customers, service agents, operations team or security officer.
- A **concern** is a matter of interest to a stakeholder, such as “Can an agent see another business unit's requests?” or “What happens when the CRM is down?”
- A **viewpoint** sets the conventions for building one kind of view: which concerns it addresses, the notation and model kinds it uses, and how to analyse it.
- A **view** applies a viewpoint to a particular system. A deployment view of the Meridian portal is one example.

For example, the security officer's concern about cross-tenant access is addressed by a data flow view drawn with trust boundaries. The operations lead's concern about CRM outages is addressed by a deployment view and a failure sequence. The standard also asks for **correspondences** between views: explicit rules that say how an element in one view relates to an element in another. These rules make consistency checkable, as the last section of this chapter shows.

## Three common frameworks

Three widely used frameworks put these ideas into practice. They answer different needs and combine well.

| Framework | What it provides | How Meridian might use it |
| --- | --- | --- |
| C4 model | Four zoom levels: system context, containers, components and code | Context and container diagrams for the portal |
| 4+1 view model | Logical, process, development and physical views, tied together by scenarios | Checking that the submission scenario works in every view |
| arc42 | A twelve-section template for the whole architecture document | The structure of the design document |

The **C4 model** describes a system at four levels of zoom: system context, containers, components and code {REF:c4}. In C4, a **container** is a separately runnable or deployable unit, such as a web application, a worker or a database. It need not be a Docker container. Use only the levels that answer a real question.

Kruchten's **4+1 view model** describes software with four views {REF:kruchten}. The logical view shows the functionality that end users need; the process view shows concurrency and synchronisation; the development view shows how the software is organised into modules; and the physical view maps the software onto hardware and shows how it is distributed. The “+1” is a small set of scenarios that runs through all four views and shows that they fit together. Meridian's submission journey is a natural scenario.

**arc42** is a template for architecture documentation by Starke and Hruschka {REF:arc42}. Its twelve sections fall into three groups:

- **The problem**: introduction and goals, constraints, and context and scope.
- **The solution**: solution strategy, and the building block, runtime and deployment views.
- **Supporting material**: cross-cutting concepts, architecture decisions, quality requirements, risks and technical debt, and a glossary.

A team can use arc42 as the document structure, C4 diagrams for its context, building block and deployment sections, and 4+1-style scenarios for its runtime section.

## The context view

The context view places the system of interest among people and external systems. Meridian's portal interacts with customers, service agents, the CRM, an identity provider, ERP and analytics. It needs no subnet names, classes or database indexes.

Label every relationship with a verb and the information exchanged. “Submits service requests” tells the reader much more than “uses”. When two systems exchange data in both directions for different purposes, draw two relationships. The portal sends submissions to the CRM; the CRM sends case status back.

> **Common mistake.** Leaving arrows unlabelled or labelling them “uses”. The reader then cannot tell who calls whom, what information moves, or who is responsible when the exchange fails.

The portal team runs that integration, so it can monitor it and agree an escalation route with the ERP owner. It cannot promise to repair the CRM or ERP themselves.

## Container, deployment, sequence and data flow views

Each further view answers a narrower question.

- A **container view** separates the web interface, application API, background worker, operational database and object storage. It shows the main runtime responsibilities and how they communicate.
- A **deployment view** shows where instances run and how they connect: zones, network boundaries, routing and external dependencies.
- A **sequence diagram** shows an interaction over time. Use it to reason about retries, asynchronous work, failure paths and who responds to whom.
- A **data flow view** shows where information is created, transformed, stored and disclosed. It supports privacy reviews and threat modelling.

For example, three application instances on a deployment diagram look redundant, but they do not make the system resilient if they share hidden dependencies. Show whether they share one database, one network route, one credential or one deployment pipeline, because shared dependencies can defeat apparent redundancy. A deployment view must be concrete enough to test. “Cloud” is too vague for assessing a regional outage; name the regions, the zones, the failover mechanism and the data that is replicated.

A sequence diagram also corrects a common mistake. An identity provider rarely sits in a serial chain between an API and its database. Sign-in, token validation, authorisation and business processing are separate interactions, and the diagram should show them separately.

UML is a family of modelling notations. Architecture work usually needs only a small subset: sequence diagrams for interactions, component diagrams for dependencies and deployment diagrams for placement. A precise model matters more than using every notation feature.

## Say what the diagram cannot show

Accompany each diagram with a short explanation of the requirements it serves, the responsibilities it assigns, its failure behaviour and the open questions. For Meridian, state that a receipt with status `received` means the portal has durably stored the request, and that a handoff in state `confirmed` means the CRM has acknowledged it.

Make the legend explicit. A solid arrow could mean a synchronous request and a dashed arrow an asynchronous message, but only if readers know the convention. Do not use colour as the only carrier of meaning, and keep labels readable in print. Give each diagram a stable identifier, such as D02, a revision date and links to the decisions it reflects. Keep one master copy of each view rather than several copies that drift apart.

## Worked ADR: accept requests during a CRM outage

- **Context.** Customers must receive a receipt during temporary CRM outages. The CRM remains the system of record for service cases. The team can operate a database and a worker, but runs no streaming platform.
- **Decision.** The portal stores each submission and its outbox handoff record in one database transaction and returns a receipt with status `received`. A worker sends the handoff to the CRM, using the submission ID as the idempotency key, and records the result. The handoff state moves from `pending` to `confirmed` when the CRM acknowledges it.
- **Alternatives.** Creating the case synchronously in the CRM is simpler, but it makes every submission depend on CRM availability. A distributed transaction is impossible across the vendor's API. A streaming platform adds operational work that the initial scale does not need.
- **Consequences.** The team must implement duplicate protection, bounded retries, a `manual_review` state for handoffs that keep failing, reconciliation, and a customer-visible “Received, awaiting service team” status. Reports must allow for short differences between portal and CRM data.
- **Review trigger.** Revisit if the CRM cannot store the submission ID as an external reference, or if measured handoff delay exceeds the one-minute target at the permitted worker capacity.

This record contains an argument. A reviewer can dispute an assumption and propose a test. That is far more useful than “we chose event-driven architecture”.

## Present to stakeholders

Tailor the presentation to the audience:

- For a business audience, start with the outcome, cost, delivery sequence and main remaining risks. Use the context view and one decision that explains the design.
- For engineers, show contracts, deployment, data ownership, failure handling and the tests still needed.

When challenged, find out whether the disagreement is about a requirement, a fact, a preference or a tolerance for risk, because each needs a different resolution. A benchmark can settle a question about performance; only the business can decide how much downtime it accepts. End each review with recorded decisions, an owner for each open question, and the tests required before release. Silence in a meeting is not agreement.

## Keep views consistent

Treat a set of diagrams as one model with referential integrity:

- The portal API in the container view must appear in the deployment view.
- A CRM call in a sequence diagram must cross a relationship shown in the context view.
- A table holding tenant data must have a data owner and a place in the data lifecycle analysis.
- The same term must name the same responsibility in every view.

For each relationship, record:

- its source, destination and purpose;
- its protocol and authentication;
- its timeout or acknowledgement rule;
- the classification of the data it carries.

A context view leaves some of these fields out on purpose; their absence there does not mean the design can omit them. Declare what a dashed line means in each figure.

## Key points

- Stakeholders have concerns; a viewpoint defines how to build a view that addresses them (ISO/IEC/IEEE 42010).
- C4 gives zoom levels, 4+1 gives complementary views tied by scenarios, and arc42 gives a document structure. They combine well.
- Label relationships with verbs, information and direction, and show ownership explicitly.
- Each diagram needs prose stating its legend, failure behaviour and open questions.
- Views stay consistent when shared identifiers can be traced through all of them.
