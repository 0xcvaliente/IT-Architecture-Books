# 5 Software foundations for architecture work

## Learning objectives

After this chapter you should be able to:

- Explain cohesion, coupling and information hiding, and use them to place module boundaries.
- Design pure functions and adapters that keep business rules apart from effects and vendor details.
- Classify errors by the response each one needs.
- Design tests that target architectural risks such as duplicate submissions and lost responses.
- Evaluate a module boundary by the changes it absorbs.

## Read code for responsibility

When you review code, first locate four things: the entry point, the business rules, the data access and the external calls. Follow one user request through them. Then find where errors are translated and where transactions begin and end.

A common design problem is one function that validates input, applies policy, writes to a database, calls a vendor API and sends an email. It may be short, but its parts change for different reasons. A vendor outage can then break unrelated business logic, and a unit test may need several live services.

Separate stable business rules from volatile adapters. For example, in Meridian:

- deciding whether an asset is eligible for service is a **domain rule**;
- turning the CRM's reply into an outcome is an **integration** responsibility;
- storing a submission is a **persistence** responsibility.

Boundaries between these responsibilities make tests simpler and change safer.

## Cohesion, coupling and information hiding

**Cohesion** describes how strongly the responsibilities inside a module belong together. **Coupling** describes how much modules depend on each other. A cohesive module handles one coherent concept, and low coupling lets one module change without forcing edits elsewhere.

These are design goals rather than numerical laws. Splitting every class into a separate service may remove some code dependencies while adding network, deployment and operational coupling. A well-structured monolith can have cleaner boundaries than a collection of tightly dependent services.

Parnas gave a sharper criterion in 1972 {REF:parnas}. He compared two ways of splitting a small program that builds a keyword-in-context index. The first made one module per processing step: input, shifting, sorting and output. The second made one module per design decision that was hard or likely to change, such as how lines are stored in memory. The second design absorbed changes far better, because each change touched only the module that hid that decision. This is **information hiding**: base a module boundary on a secret it keeps, rather than on a step in a flowchart. It does not imply that each module becomes a separately deployed service.

Give callers small interfaces that express what they need. A service request workflow might depend on “store submission” and “record handoff”, rather than on every method of a database client. The interface must still reveal the guarantees that callers rely on: whether an operation is atomic, safe to retry, or eventually consistent.

## Keep rules pure and effects at the edges

A **pure function** computes its result from its inputs alone and changes nothing outside itself. It is easy to test and to reason about. The validation rule below is pure: it returns a list of problems instead of raising the first one, so a caller can show all of them at once.

~~~python
from dataclasses import dataclass

@dataclass(frozen=True)
class Submission:
    customer_id: str
    asset_id: str
    description: str

def validate_submission(item: Submission) -> list[str]:
    """Check structure only. Access and eligibility need trusted state."""
    errors = []
    if not item.customer_id or not item.asset_id:
        errors.append("customer and asset are required")
    if not 1 <= len(item.description) <= 2000:
        errors.append("description must have 1 to 2000 characters")
    return errors

print(validate_submission(Submission("c-17", "a-204", "Pump leaks oil")))
print(validate_submission(Submission("c-17", "", "")))
~~~

Running it prints:

~~~
[]
['customer and asset are required', 'description must have 1 to 2000 characters']
~~~

The function checks structure only. It cannot tell whether the signed-in user may submit for customer `c-17`, or whether asset `a-204` is under contract. Those checks need trusted identity and current data, so they belong in other functions with clear names. Naming matters here: a developer who sees `validate_submission` should not mistake it for complete authorisation.

`frozen=True` stops code from reassigning the fields of a `Submission` after creation. It is a guard against accidental mutation; it provides no security, and objects nested inside a frozen instance can still change.

Real systems still need effects, such as database writes and network calls. A useful pattern keeps calculations pure and places effects at a few controlled boundaries.

## Hide the vendor behind an adapter

Apply information hiding to Meridian's CRM integration. The vendor's status codes, field names and error formats are the secret. An adapter translates them into a stable internal outcome, so the rest of the portal never sees them.

~~~python
from enum import Enum

class HandoffOutcome(Enum):
    CONFIRMED = "confirmed"    # the CRM holds the case
    RETRY = "retry"            # not processed this time; retry with the same key
    UNCERTAIN = "uncertain"    # the case may exist; retry with the same key
    REFRESH = "refresh"        # the worker's token expired; renew it, then retry
    REJECTED = "rejected"      # refused; a retry will not help, so a person reviews it

def interpret_crm_reply(status: int | None, body: dict) -> HandoffOutcome:
    """Translate the vendor's codes and field names into a stable outcome."""
    if status is None or status >= 500:
        return HandoffOutcome.UNCERTAIN     # timeout or server error
    if status in (408, 429):
        return HandoffOutcome.RETRY         # the CRM did not process the request
    if status == 401:
        return HandoffOutcome.REFRESH       # authentication failed, nothing created
    if status in (200, 201) and body.get("caseRef"):
        return HandoffOutcome.CONFIRMED
    if status == 409 and body.get("existingCaseRef"):
        return HandoffOutcome.CONFIRMED     # duplicate key: case already exists
    return HandoffOutcome.REJECTED          # 400, 403, 422 or an unexpected reply

replies = [(201, {"caseRef": "C-88"}), (409, {"existingCaseRef": "C-88"}),
           (None, {}), (503, {}), (408, {}), (429, {}), (401, {}), (403, {}),
           (400, {"error": "unknownAsset"})]
for status, body in replies:
    print(status, interpret_crm_reply(status, body).value)
~~~

Running it prints:

~~~
201 confirmed
409 confirmed
None uncertain
503 uncertain
408 retry
429 retry
401 refresh
403 rejected
400 rejected
~~~

Each outcome tells the worker what to do next:

- **Uncertain.** `None` stands for a timeout with no reply at all, and a `5xx` reply may come after the CRM has already stored the case. Either way the case may exist.
- **Retry.** The vendor contract states that a `408` (request timeout) or `429` (too many requests) reply means that the CRM did not process the request, so a later attempt is safe. HTTP itself does not guarantee this, so the adapter relies on the contract.
- **Refresh.** A `401` means that the worker's access token has expired or been revoked, and nothing was created. The worker obtains a new token and retries; if the new token is also refused, it raises an alert, because every handoff will fail until the credential is fixed.
- **Rejected.** A `400`, `403` or `422` will fail again unchanged. A `403` means that the worker's identity lacks a permission, which is a configuration fault to alert on as well as a reason to stop this handoff.

Retry and uncertain lead to the same action today, a retry with the same submission ID as idempotency key, because the CRM contract honours that key for 24 hours (Chapter 8); a later duplicate-key reply still counts as confirmation. Outside that window, or without the key, an uncertain outcome needs a lookup in the CRM before any retry. In terms of the handoff states of Chapter 10, a confirmed outcome leads to `confirmed`, a rejected one to `manual_review`, and the other three, including a credential refresh, to `retry_due`.

> **Check your understanding.** Why does the adapter treat a `401` reply differently from a `403`? A `401` says the credential is no longer valid, which renewing it can fix; a `403` says that a valid identity lacks permission, which no retry will change.

Test a boundary by imagining changes. If the vendor renames `caseRef`, only the adapter changes. If Meridian changes its eligibility policy, the adapter is untouched. If the vendor withdraws idempotency keys, however, the whole retry design must be revisited, because the adapter can hide names but not a lost guarantee. Counting which modules each change touches is a more useful check than claiming that an interface automatically produces low coupling.

## Object orientation and alternatives

Object-oriented design offers three main tools:

- **Encapsulation** groups state and behaviour behind an interface.
- **Polymorphism** lets callers use different implementations through one agreed contract.
- **Inheritance** shares behaviour between classes, but deep hierarchies make changes hard to follow. Composition often assembles capabilities more simply.

Functional techniques emphasise explicit inputs and outputs and avoid hidden mutable state, as in `validate_submission`. An architect need not impose one programming style on every team. The important questions are whether the code expresses the domain, whether dependencies are controlled, and whether the team can change and operate it safely.

## Errors are part of the contract

Different errors need different responses, so the contract should distinguish them.

| Error type | Meridian example | Right response |
| --- | --- | --- |
| Invalid input | Description is empty | Reject; repeating the request will fail again |
| Not authorised | Agent lacks scope for the customer organisation | Deny and record a safe audit event |
| Conflicting state | Request is already closed | Reject with the current state |
| Temporary dependency failure | CRM times out | Retry later with the same idempotency key |
| Internal defect | Unexpected null value | Fail safely, alert and fix the code |

Retrying a temporary failure may succeed, but the caller must first consider whether the earlier attempt already took effect.

Return a stable error code and a correlation identifier to the client. Keep detailed diagnostics in access-controlled logs, without secrets or unnecessary personal data.

Cancellation and timeouts need design too. For example, a customer who closes the browser tab during submission does not cancel the database transaction that is already running. Use request deadlines, bounded work and durable workflow state, and never assume that a disconnected caller undoes the business action.

## Tests as architectural evidence

Four kinds of test reveal different defects:

- A **unit test** checks a narrow behaviour with controlled dependencies.
- An **integration test** checks interaction with a real dependency or a faithful substitute.
- A **contract test** checks that a provider and a consumer agree on an interface.
- An **end-to-end test** checks a complete user journey.

Unit tests can show that a calculation is right for chosen inputs, but they cannot show that a production network route or identity policy works. End-to-end tests cover more, but they are slower and harder to diagnose. Combine them according to risk.

Test the hard cases explicitly:

- the same submission key sent twice, and sent concurrently;
- an agent requesting another business unit's request;
- a database commit whose response is lost before it reaches the client;
- a CRM outage lasting longer than the retry schedule.

These tests reveal architectural behaviour far more clearly than another successful-path demonstration.

## Version control and change

Version control records changes and supports collaboration and recovery. Git stores project history as commits, and branches provide lines of development that are later integrated {REF:git}. Keep commits small enough to review, and explain why each change is needed.

Version more than application code. API specifications, deployment definitions, schema migrations, ADRs and runbooks all shape the system. Keep secrets and private datasets out of the repository. Treat a committed secret as exposed and rotate it, because deleting the latest copy leaves it in the history and in every clone.

## Worked design review: a remote call inside a transaction

A pull request adds a call to the CRM's create-case API inside the database transaction that stores a submission. The happy path works in testing. In production, the CRM call sometimes takes thirty seconds. During that time the transaction holds its locks and its database connection, so a slow CRM slowly starves the portal of connections. If the CRM call succeeds and the commit then fails, the CRM holds a case that the portal has no record of.

A better design stores the submission and a durable handoff record in one short transaction, commits, and lets a worker perform the CRM call afterwards. This is the outbox pattern, which Chapter 10 develops. The choice still depends on the business rule. If an action truly must complete before the customer gets an answer, give it a short deadline and an explicit compensation or reconciliation process.

## Key points

- Place module boundaries around decisions likely to change, so that each change stays local (information hiding).
- Keep business rules pure where possible and put effects, such as database writes and vendor calls, at controlled edges.
- An adapter can hide a vendor's names and formats, but it cannot hide the loss of a guarantee such as idempotency.
- Distinguish invalid input, denied access, conflicting state, temporary failure and internal defects; each needs a different response.
- Test duplicates, concurrency, lost responses and outages explicitly.
