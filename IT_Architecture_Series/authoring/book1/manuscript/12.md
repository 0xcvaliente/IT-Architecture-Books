- Explain linearizability, eventual consistency and session guarantees, and choose one per operation.
- Analyse whether a register history is linearizable, and which partitions of a consensus cluster can make progress.
- Evaluate a distributed design by combining models, tests and production observations within their proper scope.

## Partial failure changes the problem

Inside one process, a function call returns a result or raises an error. Across a network, a timeout leaves three possibilities: the remote action failed, it succeeded and the reply was lost, or it is still running. Messages can also be delayed, duplicated, reordered or lost. This is **partial failure**: some parts of the system work while others do not, and no part can be sure which.

Design state so that uncertainty is visible. A Meridian request can be `received` by the portal while its handoff is still `pending`. A timeout must never turn that state into “not submitted”; reconciliation establishes the remote outcome later.

Clocks are imperfect too. Timestamps from two machines can disagree even when both are healthy. Use a monotonic clock to measure elapsed time on one machine, and use versions or explicit ordering when correctness depends on sequence.

## Latency, throughput and concurrency

Three measures describe performance:

- **Latency** is the time one operation takes.
- **Throughput** is the number of operations completed per unit of time.
- **Concurrency** is the amount of work in progress at once.

A system can have high throughput and poor latency, by processing many slow operations at the same time.

**Little's law** links the three for a stable system: the average number of items in the system equals the average arrival rate multiplied by the average time each item spends there {REF:little}. In symbols, L = λW. For example, at Meridian's incident peak 20 submissions arrive per second. If each spends 0.4 seconds in the API, then on average 20 × 0.4 = 8 submissions are in progress. If each holds a database connection for that time, a pool of 8 connections would be fully used on average, with nothing left for bursts. Little's law gives averages; bursts and slow outliers need headroom on top.

When arrivals exceed capacity, a queue grows without limit. Suppose a worker completes 5 handoffs per second while 10 arrive per second. The backlog grows by 5 per second, or 18,000 in an hour. A bigger queue buys time, not capacity. The fixes are to add capacity, reduce the work per item, limit intake or change the service target.

## Tail latency and fan-out

A **percentile** summarises a latency distribution. The 95th percentile (p95) is the value at or below which 95 percent of measurements fall, using a stated measurement method. Averages hide the slow minority, and interactive users notice that minority.

Tail latency matters more as a request **fans out** to many components. Dean and Barroso show how rare slow responses from individual servers become common at the level of a whole request {REF:tail}. A simple model makes the effect concrete. Suppose a request calls 20 independent dependencies, and each finishes within its deadline with probability 0.99. The probability that all 20 finish in time is 0.99 to the power 20, which is about 0.8179. So about 18.21 percent of requests have at least one late dependency, although each dependency is late only 1 percent of the time. With 100 dependencies, 0.99 to the power 100 is about 0.366, and about 63 percent of requests are affected.

Independence is a strong assumption. Shared overload makes slow responses arrive together, and optional dependencies change the rule for completion. Use the model to spot the risk, then measure the real joint behaviour. Mitigations such as sending a second request to another replica cost capacity, and they must never duplicate unsafe actions such as payments or work orders.

Two further rules keep measurements honest:

- Do not add component p95 values and call the result an end-to-end p95. The combination depends on how the delays are correlated. Measure the whole journey and use component data to explain it.
- Separate queue waiting time from service time. A fast worker still produces long end-to-end delay if work waits in a queue, so watch the age of the oldest message as well as processing time.

## Resilience mechanisms

Four mechanisms protect a caller from a failing dependency:

- A **timeout** bounds how long the caller waits.
- A **retry** gives a temporary failure another chance, within the limits set in Chapter 10.
- A **circuit breaker** stops calls to a dependency that keeps failing, so callers fail fast, and later lets a few trial calls through to test recovery.
- A **bulkhead** reserves separate resources, such as connection pools or threads, for different dependencies, so that one failure cannot exhaust everything.

Nygard described the circuit breaker and bulkhead among his stability patterns for production software {REF:nygard}. Cloud architecture guides document the same circuit breaker and stress that it complements timeouts and sensible retries rather than replacing them {REF:circuit}.

FIGURE resilience | A dependency boundary combines a deadline, a capacity limit and a circuit breaker with controlled recovery.

{FIG:resilience} shows the breaker's three states. While **closed**, calls flow normally and failures are counted. When failures cross a threshold, the breaker **opens** and calls fail immediately. After a wait, it becomes **half-open** and allows a few trial calls: success closes it, and failure opens it again.

**Backpressure** stops a producer from overwhelming a consumer. It can slow intake, reject excess work with a clear response, or admit only the work that fits. An unlimited queue hides the problem: it consumes storage and delays the failure until recovery is very hard.

A fallback must preserve business meaning. Returning “request received” when nothing was stored is not graceful degradation; it is a false receipt. A safe fallback for Meridian lets customers view public service information while submission is unavailable, with an honest message about the unavailable action.

## Availability and correlated failure

When a request needs several dependencies in series, their availabilities multiply, provided failures are independent. For example, four required dependencies, each with availability 0.999, give 0.999 to the power 4, which is about 0.996006, or 99.6006 percent. Over a 30-day month of 43,200 minutes, that is about 172.5 minutes of expected unavailability, against 43.2 minutes for any one dependency.

Redundancy works the other way. Two independent replicas that each have availability 0.99 are both down with probability 0.01 × 0.01 = 0.0001, giving 99.99 percent. That calculation assumes the replicas fail independently, and real failures are often correlated:

- two instances in one zone share power, network and routing;
- two zones can receive the same faulty software release;
- every replica can depend on the same expired certificate or compromised credential.

Identify failure domains rather than counting boxes. A standby needs enough capacity, usable data, routing, permissions and a practised failover procedure. Recovery objectives must cover the whole business service, not only the database restart.

## Caching and replication

A **cache** stores the result of earlier work for reuse. Define its key, its expiry, how it is invalidated, and what happens when the cache itself fails. A slightly stale asset list may be acceptable for a few minutes; stale access permissions are far more serious.

A **cache stampede** happens when many callers find the same entry missing or expired at once and all recompute it together. Request coalescing, controlled refresh and staggered expiry times reduce the load. Avoid making the cache an unexamined single point of failure.

**Replication** keeps copies of data on several servers. It can add read capacity and availability, but replicas often lag behind the primary. A user sent to a lagging replica straight after a write may find the new record missing. The next section names the guarantee that prevents this.

## Consistency models

A **consistency model** states which results reads may return when data is replicated or accessed concurrently. Three models cover most architecture decisions:

- **Linearizability** makes a replicated object behave like a single copy. Each operation appears to take effect at one instant between its start and its end, so a read that starts after a write has completed sees that write or a later one.
- **Causal consistency** preserves cause and effect. If one update depends on another, every reader sees them in that order; unrelated updates may appear in different orders.
- **Eventual consistency** promises only that replicas converge once updates stop and communication succeeds.

Between these lie the **session guarantees** defined by Terry and colleagues for weakly consistent replicated data {REF:terry}. They promise consistency only within one client's session, which is often all a user needs:

- **Read your writes**: a session sees its own earlier writes.
- **Monotonic reads**: a session never sees data older than data it has already seen.
- **Writes follow reads**: a write is applied after the writes that the session had read before it.
- **Monotonic writes**: a session's writes are applied in the order the session made them.

For example, a Meridian customer submits a request and is taken straight to “My requests”, which reads from a replica that is two seconds behind. Without read your writes, the new request is missing and the customer submits again. The portal can return the commit position with the receipt and serve the list from a replica that has reached that position, or from the primary for a short time after each write. Aggregate reports, by contrast, can tolerate minutes of lag.

Choose a model per operation. A stock reservation may need linearizable coordination, while a notification counter can be eventually consistent.

The **CAP theorem**, proved by Gilbert and Lynch, concerns behaviour during a network partition {REF:cap}. Under its formal definitions, a system cannot guarantee both linearizable reads and writes and a response to every request while the network is partitioned. It does not mean “choose any two of three” in normal operation. Latency, durability and recovery need further reasoning, which the rest of this chapter supplies.

## Histories and linearizability

Herlihy and Wing define linearizability through histories {REF:linearizability}. A **history** records when each operation started, when it ended and what it returned. The history is linearizable if the operations can be placed in one sequential order that:

- respects real time: an operation that ended before another started comes first;
- obeys the object's sequential rules, such as “a read returns the last value written”.

This is a property of a single object. **Serializability** is a different property: complete transactions over many objects must be equivalent to some serial order, which need not respect real time. **Strict serializability** adds the real-time requirement.

### A register example

A register initially holds 0. Client A writes 1, starting at time 1 and finishing at time 3. Client B reads, starting at time 4 and finishing at time 5, and receives 0. A's write ended before B's read began, so any valid order puts the write first, and the read should then return 1. No valid order exists, so the history is not linearizable.

Change one fact: B's read starts at time 2, while the write is still in progress. The operations now overlap, and the order “read, then write” respects real time. Returning 0 is permitted. The value returned is the same in both cases; the timing of the intervals decides.

FIGURE histories | A stale read after a completed write differs from a read that overlaps the write.

{FIG:histories} draws both cases. The listing checks small histories by brute force: it tries every order, discards orders that contradict real time, and keeps those that obey the register rule.

~~~python
from dataclasses import dataclass
from itertools import permutations

@dataclass(frozen=True)
class Op:
    name: str
    kind: str    # "write" or "read"
    value: int   # the value written, or the value the read returned
    start: int   # time of invocation
    end: int     # time of response

def linearizations(history: list[Op], initial: int = 0) -> list[tuple[str, ...]]:
    """Return every sequential order that explains a completed register history."""
    before = {(a.name, b.name) for a in history for b in history if a.end < b.start}
    valid = []
    for order in permutations(history):
        position = {op.name: i for i, op in enumerate(order)}
        if any(position[a] > position[b] for a, b in before):
            continue  # this order contradicts real-time precedence
        state, legal = initial, True
        for op in order:
            if op.kind == "write":
                state = op.value
            elif op.value != state:
                legal = False
                break
        if legal:
            valid.append(tuple(op.name for op in order))
    return valid

W = Op("W", "write", 1, start=1, end=3)
histories = {
    "read after completed write": [W, Op("R", "read", 0, start=4, end=5)],
    "read overlaps the write": [W, Op("R", "read", 0, start=2, end=5)],
    "later read sees new value": [W, Op("R", "read", 1, start=4, end=5)],
}
for label, history in histories.items():
    print(f"{label}: {linearizations(history)}")
~~~

Running it prints:

~~~
read after completed write: []
read overlaps the write: [('R', 'W')]
later read sees new value: [('W', 'R')]
~~~

An empty list means no valid order: the first history violates linearizability. The checker handles completed operations only, and its running time grows factorially, so it suits teaching examples of a few operations.

### Collecting trustworthy histories

The reasoning needs trustworthy intervals. A test coordinator can establish that one operation finished before another began by waiting for the first reply before issuing the next call. Comparing timestamps from unsynchronised machines gives weaker evidence. Record request IDs and causal links as well as timestamps.

An unfinished operation adds uncertainty. If A's write times out, B may later read 1 without any violation, because the write may have taken effect although A never heard back. A timeout is an observation about the client's wait, not a rollback. That is why the checker above accepts completed operations only: treating a timed-out write as a definite failure would make it reject valid histories.

Linearizable objects do not make a multi-object workflow atomic. Suppose a payment record and an inventory record each offer linearizable updates. Two separate updates still leave an interval in which only one has changed. The missing property is atomic coordination of the business operation, which needs a transaction or a saga.

## Causality, consensus and quorums

Lamport defined the **happened-before** relation from three rules: order within one process, the sending of a message before its receipt, and transitivity {REF:lamport}. Events that are not related this way are **concurrent**. Logical clocks preserve happened-before order, but a smaller timestamp alone does not prove that one event caused another. In a portal incident, a later wall-clock time on a CRM event cannot by itself show which update depended on which. When the business needs that relationship, carry explicit event and predecessor identifiers.

**Consensus** lets a group of servers agree on a sequence of decisions, such as the entries of a replicated log, despite crashes and network faults. Raft divides the problem into leader election, log replication and safety rules {REF:raft}. A leader commits an entry from its current term once a majority of servers have stored it. A **majority quorum** of n voters is more than half of them: 2 of 3, 3 of 5.

Majority quorums work because any two majorities share at least one member. With five voters, two groups of three contain six memberships between them, but there are only five voters, so at least one voter is in both. That shared voter carries the committed history into any future majority. Intersection is necessary but not sufficient: a voter that forgets its durable vote, or an unsafe membership change, can still break agreement. Raft's voting restrictions and commit rule work with log replication to preserve the committed history.

### Which partitions make progress

With five voters, progress needs a connected group of at least three, as {FIG:quorum} shows:

- In a **3 | 2** partition, the side with three voters can elect a leader and keep committing. The side with two cannot commit, so it cannot make conflicting decisions.
- In a **2 | 2 | 1** partition, no group has three voters. Nothing new commits anywhere until enough connections return, although every committed entry stays safe.

FIGURE quorum | With five voters, the side holding three can commit in a 3 | 2 partition, while a 2 | 2 | 1 partition stops all commits.

Placement across failure domains decides which failures stop progress. Suppose two voters are in region A, two in region B and one in region C:

- If region C fails, A and B still hold four voters and continue.
- If region A is cut off, B and C hold three voters and continue.
- If A and B lose contact and C reaches only B, then B and C hold three voters and continue.
- If all three regions lose contact with each other, the groups are 2, 2 and 1, and no group can commit.

This analysis covers crashes and network faults. It does not cover a participant that lies, or an administrator who alters every replica. Nor does placement alone yield an availability figure; that also needs failure rates and recovery times.

> **Check your understanding.** How many of seven voters must be able to communicate for the cluster to commit? Four, because a majority of seven is more than three and a half. Any two groups of four share at least one voter.

### The consensus boundary

FIGURE consensus_boundary | The replicated order decision and the external payment sit inside different correctness boundaries.

A replicated log protects decisions inside its boundary, and nothing outside it ({FIG:consensus_boundary}). A committed order intent survives a leader change, but a payment request sent to an external provider is outside the cluster. After a payment timeout, the worker must reconcile with the provider. Its retry key must be meaningful to the provider, and the provider's retention of that key must cover the whole retry policy. A consensus cluster cannot extend the provider's idempotency window. In the same way, a read served by a follower may be stale unless the read protocol guarantees otherwise; membership of a cluster does not make every read current.

Two kinds of property describe any such design. **Safety** means that a bad outcome never happens, such as two conflicting committed decisions. **Liveness**, or progress, means that useful work eventually completes under stated conditions. A system that refuses every request is safe but useless; one that replies quickly with a false confirmation is fast but unsafe. State both properties and the conditions for recovery.

## Reason about partitions per operation

The CAP proof considers a single read/write object. During a partition, an isolated server cannot distinguish a history with an unseen remote write from a history without one. If it must answer, it may answer wrongly; if it must be right, it may have to wait {REF:cap}. The proof is about possible executions, not a label for a whole product.

Apply the reasoning to one operation at a time. Two warehouses each know that one unit of a product remains, and the link between them fails:

- If both promise the unit to different customers, the rule “never oversell” breaks.
- If one refuses or defers the reservation until it can reach the authority, the rule holds, and that operation loses availability.
- Showing an estimated stock level can continue on both sides, labelled as an estimate.

Viewing an estimate, accepting a tentative request and confirming a reservation are different operations with different answers.

A design can also change what each side needs to know. With 100 units, give warehouse A the right to sell 60 and warehouse B the right to sell 40. Each can sell from its own allowance during a partition and the global limit still holds, provided rights cannot be duplicated, each warehouse decrements its allowance atomically, and transfers between warehouses conserve the total. With a single unit, only one warehouse can hold the right. The impossibility result still applies; the design has moved the coordination to before the partition. Reallocating rights and recovering a lost warehouse need their own protocol.

## Test the failure model

A **load test** must state its workload: the request mix, data distribution, ramp-up, duration, concurrency, success criteria and dependencies. For example, a test that sends identical requests to a warm cache measures the cache, while an incident surge brings varied requests that miss it.

A **resilience test** deliberately exercises a defined failure, such as restarting the worker after it has sent a handoff but before it records the result. Write down what should happen, how you will observe it, and how you will restore the environment. Run such tests in isolated environments with test data.

Build the case for a distributed design in steps:

1. State the sequential rule: what may one successful command do?
2. Define the allowed concurrent histories, the durable commit point and the failure assumptions.
3. Construct adversarial traces: a reply lost after commit, a leader change during a write, a duplicate delivery, a policy change during a backlog.
4. Decide which production observation would distinguish a violation from a merely delayed result.

Each kind of evidence has a limited scope. A small exhaustive model, like the history checker, can find an invalid interleaving that a large load test misses, but it cannot show that the implementation follows the model. A load test finds a saturation point for one workload, but cannot prove that every history is safe. A published proof covers a defined algorithm, not a service whose configuration and client protocol differ from it. Combine them, and keep each conclusion within what it demonstrates.

## Key points

- Partial failure leaves outcomes uncertain; make the uncertainty visible in state and resolve it by reconciliation.
- Little's law, fan-out probabilities and availability products give quick estimates, but only under stated assumptions such as stability and independence.
- Timeouts, bounded retries, circuit breakers, bulkheads and backpressure protect callers; a fallback must never give a false confirmation.
- Choose a consistency model per operation; session guarantees such as read your writes often meet a user's need cheaply.
- Linearizability is judged on histories; majority quorums let only a side with more than half the voters commit, and consensus protects nothing outside its own boundary.
