# 4 Operating systems, networking and the request journey

## Learning objectives

After this chapter you should be able to:

- Explain what processes, virtual machines, containers and serverless functions share and what survives a restart.
- Trace a request through name resolution, transport, TLS and HTTP to the application.
- Calculate the size of IPv4 prefixes and plan non-overlapping subnets.
- Apply the end-to-end argument to decide where a correctness guarantee must sit.
- Diagnose a failed request one layer at a time.

## Start with a running process

A program on disk becomes a **process** when the operating system runs it. The process has its own memory, execution state, open files and operating system resources such as network sockets. **Threads** within one process share its memory, while separate processes normally have separate address spaces. Both models need coordination when work touches shared data.

CPU, memory, disk operations, network bandwidth and connection counts are different resources. For example, adding CPU does little for a service that spends most of its time waiting for a remote database. Adding workers can even make matters worse if each worker opens more database connections than the database can sustain.

Three runtime models package processes differently:

- A **virtual machine** runs a guest operating system on virtualised hardware.
- A **container** packages a process and its dependencies and shares the host's operating system kernel.
- A **serverless function** runs on infrastructure that the provider provisions and schedules for you.

All three need patching and resource management, at different boundaries. For each runtime, ask what persists across a restart. An application that writes uploaded files to a local temporary directory can lose them when the instance is replaced. When the business expects files to survive, store them in durable object storage or another explicitly persistent service.

## From a name to a connection

The **Domain Name System** (DNS) maps names to records through a distributed hierarchy {REF:dns}. Authoritative name servers hold the records for a zone. A resolver caches each answer until its time to live (TTL) expires. Three record types appear constantly:

- an **A record** gives an IPv4 address;
- an **AAAA record** gives an IPv6 address {REF:dns6};
- a **CNAME** points one name at another name.

DNS is separate from routing and from HTTP. That matters during a migration. If you change the portal's A record and the old answer had a TTL of one hour, some resolvers will keep sending clients to the old endpoint for up to an hour. Open connections can last even longer. Plan a transition period in which the old and new routes both behave safely.

> **In practice.** Lower the TTL of a record well before a planned change, at least one old TTL in advance, so that caches pick up the short value. Raise it again once the new endpoint is stable.

Four further terms describe how packets reach their destination:

- An **IP address** identifies a network interface within an addressing scheme.
- A **subnet** groups addresses that share a prefix.
- A **route** decides where a packet goes next.
- A **firewall policy** decides which traffic is allowed.

A correct route with a blocked port fails differently from a name that does not resolve, so diagnose them separately.

Prefix arithmetic is simple. An IPv4 address has 32 bits. A /24 prefix fixes 24 bits and leaves 8 for addresses, so it contains 2 to the power 8, or 256, addresses. A /16 leaves 16 bits, or 65,536 addresses, which is room for 256 separate /24 subnets. Fewer addresses are usable than the raw count: conventional networks reserve the first and last addresses of a subnet, and cloud providers reserve a few more under their own rules. Plan address space for growth and for connections to other networks, because overlapping ranges make routing between them difficult.

## Transport and encryption

**TCP** provides an ordered byte stream with retransmission and congestion control. It carries bytes; it knows nothing about service requests or business transactions. **UDP** sends individual datagrams without TCP's delivery guarantees. Protocols can build further behaviour on UDP: HTTP/3, for example, runs over QUIC, which uses UDP. Do not assume that every HTTP connection uses TCP.

**TLS** encrypts communication in transit and authenticates the endpoints according to its configuration {REF:tls}. On a typical website, the client validates the server's certificate and the two sides negotiate encryption keys. Mutual TLS also authenticates the client with a certificate. Encryption answers the question “who am I talking to, and can anyone else read it?” It does not decide whether a signed-in service agent may read a particular request.

A load balancer often terminates TLS and opens a second connection to the application. Draw these as separate segments and decide how the internal one is protected. A label saying “HTTPS” on the public edge describes that segment only; each connection behind it needs its own label.

## HTTP in an architecture

HTTP defines request and response semantics {REF:http}. A request carries a method, a target, headers and optional content. A response carries a status code, headers and optional content. The methods have defined meanings:

- `GET` retrieves a representation of a resource.
- `PUT` replaces the state of the target resource.
- `POST` asks the resource to process the enclosed content according to its own rules.

A method is **idempotent** when repeating an identical request has the same intended effect on the server as sending it once. `GET` and `PUT` are idempotent; `POST` is not. Idempotency concerns the effect, so two identical `PUT` requests may still return different response bodies.

An API timeout is an observation made by the caller. The server may still have committed the work. Retrying a `POST` can therefore create a duplicate unless the API contract provides duplicate protection, which Chapter 8 designs. A `200 OK` response is only as useful as the contract's statement of what it confirms.

A **content delivery network** (CDN) serves cached content from locations near users. The cache key and cache policy decide which responses are reused. Caching personalised service request data as if it were public content would disclose it to other users, so static assets and private API responses need deliberately different rules.

## End-to-end correctness

Saltzer, Reed and Clark's **end-to-end argument** says that some functions can be implemented completely and correctly only with knowledge held at the endpoints of a communication {REF:endtoend}. Lower layers can still help, for performance or reliability, but they cannot provide the full guarantee.

For example, TCP acknowledges bytes when they reach the receiving operating system. Whether the portal's database committed the submission, and whether the caller was authorised to make it, are facts that only the portal application knows. The portal's receipt contract must therefore define its own boundary: a receipt means the submission and its handoff record are committed to the database. The same reasoning applies to file uploads. A checksum calculated by the client and checked after the object is stored detects corruption anywhere on the path, including in components that each reported success.

The argument is about where a guarantee must sit. It does not tell you to remove lower-layer controls, which often make failures rarer and cheaper.

## A complete submission journey

Follow one submission from the customer's device:

1. The device resolves the portal's name and opens a TLS connection to the edge.
2. The edge serves the web interface and routes the API request to the application.
3. The application validates the input, checks that the caller may submit for this asset, and commits the submission with its handoff record.
4. The application returns a receipt with status `received`.
5. Later, a background worker reads the handoff record and delivers it to the CRM.

Attachments follow a separate path into object storage. A safe upload flow checks the allowed size and type, authorises the upload, verifies that it completed, and keeps unscanned files out of trusted use. The database stores a reference to the file and its processing state rather than the file bytes.

## Private networks and controlled access

A private address range does not make a workload trustworthy. Traffic can still arrive through network peering, a VPN, a compromised host or a misconfigured route. Combine network controls with identity, application authorisation and monitoring.

A VPN based on IPsec or TLS encrypts traffic between endpoints or networks. The term VPN also covers provider services such as BGP/MPLS VPNs, which separate traffic without encrypting it {REF:vpn}. Check which technology is in use and what protection it actually gives.

Keep the responsibilities of edge components distinct. A load balancer distributes traffic. An API gateway applies routing and policy at an interface. Many products combine both functions, but the design should still say which responsibility each component carries.

Outbound access needs the same care as inbound access: the runtime may need to reach the identity provider, a package repository and the CRM vendor. An egress restriction improves control, but it can break deployment or recovery if a required dependency was never listed. Some managed platforms implement these responsibilities without placing the service inside your subnet; keep the responsibility map and adapt the mechanism.

## Diagnose one layer at a time

When the Meridian portal fails, check each layer in order:

1. Does the name resolve to the expected address?
2. Can the client reach that address and port?
3. Does TLS validation succeed?
4. Does the HTTP request reach the application?
5. Does the application have a working database connection?
6. Which dependency used up the time budget?

Change one variable at a time, and record the symptom, hypothesis, test and result. Test the protocol and path that the application actually uses. A successful ping proves only that ICMP reaches the host, while the API needs HTTPS on port 443, which a firewall may treat quite differently. A blocked ping is equally inconclusive in the other direction.

## Key points

- Processes, threads, virtual machines, containers and functions differ in what they share and what survives a restart.
- Naming, routing, filtering, transport, encryption and HTTP semantics are separate layers that fail in different ways.
- Prefix arithmetic is powers of two; plan non-overlapping ranges and remember that routes and firewall rules are separate controls.
- The end-to-end argument places guarantees such as “the submission is stored” at the application endpoints.
- Diagnose layer by layer, testing the protocol and path that the application actually uses.
