# 16 DevOps, testing and controlled delivery

## Learning objectives

After this chapter you should be able to:

- Explain continuous integration, continuous delivery and continuous deployment, and design a pipeline that promotes one tested artefact.
- Design an expand, migrate and contract sequence for a schema change, with a recovery plan for each step.
- Compare rolling, blue-green and canary deployments and the role of feature flags.
- Calculate the DORA delivery metrics from a release log and interpret them.
- Evaluate a release's provenance against secure software development practices.

## Delivery is part of the architecture

A design that is hard to release safely builds up operational risk. The delivery path decides who can change production, which checks run, how artefacts are identified and how a failed change is undone. It deserves the same design attention as the running system.

Three terms are often confused:

- **Continuous integration** merges changes into a shared mainline often, and builds and tests every change automatically.
- **Continuous delivery** keeps the software releasable at any time, with production release as a controlled, low-effort step.
- **Continuous deployment** releases every change that passes the pipeline to production automatically.

Agree the definitions within the team, because organisations use the words differently. The goal is a repeatable path from a reviewed change to observed production behaviour. Automating a poorly understood manual process only produces its mistakes faster.

## A practical pipeline

A useful pipeline checks each source change, builds an immutable artefact, runs tests and security checks, deploys to a representative environment, verifies behaviour, and promotes the same artefact to production under agreed controls. {FIG:pipeline} shows the loop.

FIGURE pipeline | Delivery promotes a tested artefact and checks behaviour after release.

Promote the same built artefact through every environment. Rebuilding for production can pull in a different dependency set, so the tested artefact and the deployed artefact would differ. Supply environment-specific configuration through a controlled mechanism.

Protect the pipeline itself, because a compromised build identity may reach production. Limit its credentials, review third-party actions and build plugins, keep audit logs, and separate build permissions from deployment permissions where the risk justifies it.

## Test boundaries

Each kind of test answers a different question:

- **Unit tests** check deterministic domain behaviour, such as a status transition rule.
- **Integration tests** check real interactions with a database, queue or identity provider.
- **Contract tests** check that a provider and its consumers agree on requests, responses and errors.
- **End-to-end tests** check a few critical user journeys across the whole system.
- **Load, security and recovery tests** check the quality attributes that the requirements name.

A test environment must match production in the aspects that matter for the risk. For example, an identity test needs realistic token validation and permissions, while a recovery test needs realistic backup formats and access. Full production capacity is rarely necessary.

Coverage percentage shows which code ran during the tests under a chosen metric. Quality comes from meaningful assertions and from exercising the failure modes that matter, such as a timeout after a remote commit.

## Changing a database schema safely

Application code can be rolled back in seconds; data changes often cannot. The **expand and contract** pattern, also called parallel change, splits a breaking change into three phases so that every step stays compatible {REF:parallelchange}.

1. **Expand.** Add the new structure beside the old one. Existing code keeps working.
2. **Migrate.** Deploy code that writes both structures and reads the new one, then backfill existing rows and move every consumer across.
3. **Contract.** Remove the old structure once nothing uses it.

### Worked example: renaming the handoff status

An early version of Meridian stored a `status` column with the values `accepted` (stored locally), `synchronised` and `failed`. The team replaces it with a `handoff_state` column that uses the five agreed states: `pending`, `in_flight`, `confirmed`, `retry_due` and `manual_review`.

1. **Expand.** Add `handoff_state`, allowing nulls. The running version ignores it.
2. **Migrate.** Deploy a version that writes both columns and reads `handoff_state`, falling back to `status` when it is null. Backfill with an agreed mapping: `accepted` becomes `pending`, `synchronised` becomes `confirmed`, and `failed` becomes `manual_review`, because "failed" meant "stopped retrying and needs a person". Check the counts for each mapped value and inspect a sample of rows.
3. **Contract.** Drop `status` after a release cycle in which no deployed version reads it.

{FIG:schema} shows the sequence. During the compatibility interval, the old and new application versions both work against the expanded schema, so either can be deployed or rolled back. Before the contract step, confirm two things: no running or fallback version reads or writes the old column, and the team accepts that recovery from now on means rolling forward to a fixed version. Check the meaning as well as the row counts. Copying the wrong meaning perfectly is still a failed migration.

Before each release, decide how you would recover: roll back the code, roll forward with a fix, restore data, or reconcile. Rehearse the chosen path with realistic data volumes.

## Deployment strategies

| Strategy | How it works | Main benefit | Main constraint |
| --- | --- | --- | --- |
| Rolling | Replace instances a few at a time | No extra environment | Old and new versions run together |
| Blue-green | Run two environments; switch traffic at once | Fast switch back | Double capacity during release; shared data must suit both |
| Canary | Send a small share of traffic to the new version first | Real traffic finds defects early | Needs good metrics and enough traffic to compare |

Every strategy runs two versions at some point, so contracts and data must suit both. A canary that receives only low-risk traffic may miss a defect affecting another user group. A fast rollback helps only while the previous version still works with the current data and configuration.

**Feature flags** separate deployment from exposure: the code ships switched off and is enabled later, for example for one business unit first. Flags allow gradual rollout and an emergency off switch, but every flag doubles the states to test. Remove a flag once the rollout is complete.

## Supply chain, provenance and secure development

Know which source revision, dependencies, build process and configuration produced each running artefact. With that **provenance**, the team can find every service affected by a vulnerable library and rebuild it quickly.

A **software bill of materials** (SBOM) lists the components inside an artefact. Generate it from the actual build and keep it with the artefact. Signing an artefact shows who signed it and that it has not changed since; reviews and tests establish whether its contents are safe.

NIST's Secure Software Development Framework (SSDF) version 1.1, published as SP 800-218, describes practices for preparing the organisation, protecting the software, producing well-secured software and responding to vulnerabilities. It fits any development lifecycle and helps in supplier discussions {REF:ssdf}. A revision, SP 800-218 Revision 1 (SSDF version 1.2), was released as an initial public draft in December 2025; until it is final, version 1.1 is the current recommendation {REF:ssdf12}.

For each consequential release, link the claim to the artefact by recording:

- the source revision and dependency inventory;
- the build identity and image digest;
- the configuration revision and migration version;
- the test environment and the approval.

A signed image deployed with an unreviewed configuration leaves part of the production state unchecked.

Review any script that a privileged pipeline downloads. A convenient setup step can otherwise become a route around careful access controls.

## Delivery measurements

DORA, the DevOps Research and Assessment programme, describes five software delivery performance metrics {REF:dora}. It is unrelated to the EU's Digital Operational Resilience Act, which shares the acronym and regulates ICT risk in financial services. Three measure throughput:

- **Change lead time**: time from commit to running in production.
- **Deployment frequency**: how often deployments happen.
- **Failed deployment recovery time**: time to restore service after a deployment that needed urgent intervention.

Two measure instability:

- **Change fail rate**: the share of deployments that need urgent intervention, such as a rollback or hotfix.
- **Deployment rework rate**: the share of deployments that are unplanned and caused by a production incident.

### Worked example: one week of releases

The portal team records six deployments in one week.

| Deployment | Lead time | Urgent intervention needed? | Unplanned, incident-driven? | Recovery time |
| --- | --- | --- | --- | --- |
| D1 | 20 h | No | No | – |
| D2 | 26 h | Yes, hotfixed by D3 | No | 40 min |
| D3 | 6 h | No | Yes | – |
| D4 | 30 h | No | No | – |
| D5 | 22 h | Yes, rolled back | No | 70 min |
| D6 | 18 h | No | No | – |

- Deployment frequency is 6 per week.
- The median lead time is the middle of 6, 18, 20, 22, 26 and 30 hours: (20 + 22) / 2 = 21 hours.
- Change fail rate is 2 / 6 ≈ 33 percent.
- Deployment rework rate is 1 / 6 ≈ 17 percent.
- Failed deployment recovery time has a median of (40 + 70) / 2 = 55 minutes.

Six deployments make a small sample, so follow the trend over several months before drawing conclusions. Define each start and end event before measuring, and compare a service with its own past. The metrics describe a delivery system with shared dependencies, so they make poor individual productivity scores.

Connect each measure to an action. If lead time is long because reviews wait four days, faster build hardware will barely help. If failures come from configuration changes made outside the pipeline, bring that path into the pipeline.

## Worked release plan: a new CRM status

The CRM vendor announces a new case status, "Awaiting parts", before the portal's mapping is ready. The portal team first deploys a tolerant parser. It keeps the unknown value, shows customers the last mapped status, such as "In progress", and records the new value for investigation without exposing raw data.

After the business agrees what the new status means for customers, the team adds the mapping behind a feature flag, tests it and enables it. Treating every unknown value as an error would have stopped status updates for all customers; treating it silently as "In progress" forever would hide a meaningful change. The tolerant parser plus a business decision avoids both.

> **Common mistake.** Dropping a column in the same release that stops using it. If that release must be rolled back, the previous version fails at once because its column has gone. Contract only after a full release cycle has run without the old column being used.

## Key points

- The delivery pipeline is part of the architecture: build once, promote the same artefact, and protect the pipeline's own identity.
- Expand, migrate and contract keep every step of a schema change compatible; contract only after nothing uses the old structure.
- Rolling, blue-green and canary releases all run two versions at once, so contracts and data must suit both.
- Provenance links each release to its source, dependencies, build, configuration and approval; SSDF version 1.1 remains current while version 1.2 is in draft.
- DORA's five metrics guide improvement for a service over time when their start and end events are defined.
