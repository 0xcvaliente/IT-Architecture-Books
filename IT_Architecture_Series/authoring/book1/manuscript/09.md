# 9 Identity, authentication and authorisation

## Learning objectives

After this chapter you should be able to:

- Explain the difference between authentication and authorisation, and between ID tokens and access tokens.
- Trace the authorisation code flow with PKCE and the checks a resource server makes on each token.
- Design an access policy that derives every decision from trusted identity and the resource's stored attributes.
- Design tests that distinguish a full resource check from a tenant-only check.
- Evaluate token lifetime, session and revocation choices against a stated revocation target.

## Identity is a lifecycle

An **identity** represents a person, service, device or other **principal**. **Authentication** establishes who or what the principal is. **Authorisation** decides which action that principal may perform on which resource under current conditions.

A user account has a lifecycle: creation, verification, role assignment, role changes, suspension and removal. For example, a Meridian service agent who moves to another business unit should lose access to the old unit's requests the same day. A valid sign-in confirms identity; whether yesterday's permissions still apply is a separate check against current assignments.

Separate workforce identities, customer identities and workload identities when they have different owners and lifecycles. Using one directory for all three is a product choice. Using one permission model for all three is usually a design mistake.

## OAuth 2.0 and OpenID Connect

**OAuth 2.0** is a framework for delegated access to protected resources. **OpenID Connect** adds an identity layer on top of it {REF:oidc}. The two produce different tokens for different audiences:

- An **ID token** tells the client application who signed in. Its audience is the client.
- An **access token** lets the client call a protected API. Its audience is that API, the resource server.

Never use one in place of the other.

A browser-based application signs users in with the **authorisation code flow with PKCE** (Proof Key for Code Exchange). Before redirecting the user, the client creates a random secret, the code verifier, and sends only its hash, the code challenge. The identity provider returns a short-lived authorisation code to the registered redirect URI. To exchange the code for tokens, the client must present the original verifier. An attacker who intercepts the code alone cannot complete the exchange.

The OAuth security best current practice, RFC 9700, requires PKCE for public clients and recommends it for confidential clients {REF:oauth}. It forbids the resource owner password credentials grant, requires exact matching of redirect URIs, and recommends restricting each token's privileges and audience. Use a maintained library rather than implementing the protocol yourself.

## Token validation

A resource server must validate every token according to the issuer's contract. For a signed JSON Web Token (JWT), validation includes:

- verifying the signature with a trusted key and an allowed algorithm;
- checking the issuer;
- checking that the audience is this API;
- checking the validity times;
- checking the scopes or other claims the operation needs.

Decoding the JSON proves nothing. For example, a token whose payload says `"role": "admin"` means nothing until its signature, issuer and audience have been checked, because anyone can write JSON. An **opaque access token** carries no readable claims and is validated through introspection or another mechanism that the provider supports. Do not assume that every access token is a JWT.

Signing keys rotate as a matter of routine. Fetch trusted keys through the issuer's configured discovery endpoint and handle unavailable metadata carefully. Never trust a key location supplied inside the token being validated.

## Sessions and browsers

A server-side session keeps tokens out of browser-accessible storage and gives the browser a session cookie instead. Cookie attributes reduce some risks:

- `Secure` sends the cookie only over HTTPS;
- `HttpOnly` hides it from page scripts;
- `SameSite` limits when other sites can cause the browser to send it.

These attributes do not replace protection against cross-site request forgery or script injection. If tokens are held in the browser, a malicious script can steal them, so keep their lifetime short and their privileges narrow.

Logout, token expiry and account suspension are related but distinct. Ending a browser session may leave already issued access tokens valid until they expire. State the required revocation time and design around the provider's actual mechanisms.

## Authorisation: roles, attributes and the resource

**Role-based access control** (RBAC) grants permissions through roles such as service agent or administrator. It suits broad job responsibilities. **Attribute-based access control** (ABAC) evaluates attributes of the principal, the resource, the action and the context, such as the request's business unit or who submitted it. Meridian needs both. The service-agent role is necessary but insufficient: the agent must also be assigned to the request's business unit and authorised for the request's customer organisation.

Meridian's policy, written as rules a reviewer can check:

| Principal | Action | Permitted when |
| --- | --- | --- |
| Customer | Read a request | They submitted it, or hold an organisation-wide delegation for its tenant |
| Customer | Upload an attachment | They submitted the request and it is still open |
| Service agent | Read a request | Agent role, the request's business unit is assigned to them, and its tenant is in their authorised set |
| Work-order integration | Create ERP work orders | Only from a confirmed `ServiceCaseApproved` event |
| Support | View diagnostics | Correlation identifiers only; no request content by default |

The decision must come from trusted sources. A tenant identifier in the URL or request body is a claim about what the caller wants, not proof of what it may have. The service should:

1. authenticate the caller and obtain the principal from a validated token;
2. load the resource and read its actual tenant, business unit and submitter from the database;
3. load the principal's entitlements from server-side policy: role, business units, authorised customer organisations and delegations;
4. evaluate the rule for this action on this resource.

Otherwise a caller could choose the authority under which its own request is judged. OWASP ranks **broken object level authorisation** first among API security risks for exactly this reason {REF:apisec}: an API checks that the caller is signed in but never checks the specific object requested.

> **Common mistake.** Copying `tenant_id` from the request body into the database query and treating the result as authorised. The query then returns whatever tenant the caller asked for.

### The read rule in code

The listing expresses the read rule. A staff member holds a set of business units and a set of customer organisations, because one agent can serve several tenants.

~~~python
from dataclasses import dataclass

@dataclass(frozen=True)
class Principal:
    user_id: str
    role: str                         # "customer" or "service_agent"
    tenant: str | None = None         # a customer belongs to one tenant
    org_wide_read: bool = False       # explicit delegation for a customer
    units: frozenset[str] = frozenset()    # staff: assigned business units
    scopes: frozenset[str] = frozenset()   # staff: authorised tenants

@dataclass(frozen=True)
class ServiceRequest:
    tenant: str
    business_unit: str
    submitted_by: str

def can_read(p: Principal, r: ServiceRequest) -> bool:
    if p.role == "service_agent":
        return r.business_unit in p.units and r.tenant in p.scopes
    if p.role == "customer" and p.tenant == r.tenant:
        return r.submitted_by == p.user_id or p.org_wide_read
    return False

req = ServiceRequest(tenant="t-017", business_unit="north", submitted_by="q")
cases = {
    "submitter q": Principal("q", "customer", "t-017"),
    "colleague p": Principal("p", "customer", "t-017"),
    "p, delegated": Principal("p", "customer", "t-017", org_wide_read=True),
    "other tenant": Principal("x", "customer", "t-023", org_wide_read=True),
    "agent, in scope": Principal("a1", "service_agent", units=frozenset({"north"}),
                                 scopes=frozenset({"t-017", "t-023"})),
    "agent, wrong unit": Principal("a2", "service_agent", units=frozenset({"south"}),
                                   scopes=frozenset({"t-017"})),
}
for name, principal in cases.items():
    print(f"{name:18} {can_read(principal, req)}")
~~~

Running it prints:

~~~
submitter q        True
colleague p        False
p, delegated       True
other tenant       False
agent, in scope    True
agent, wrong unit  False
~~~

The second case is the important one. Customer p belongs to tenant t-017, the same tenant as the request, and holds a valid token. A tenant-only check would let p read q's request. The ownership rule refuses, and the delegation in the third case permits it. Staff rules are separate: a customer delegation never turns into a staff permission. In production the principal's fields come from validated tokens and server-side policy, and the request's fields come from the database, never from the caller's input.

Apply the check on every route that touches a request, including search, export, attachment download and background jobs. Row-level security, described in Chapter 6, adds a tenant guard inside the database, but the ownership and business-unit rules stay in the application.

## Asynchronous work and delegated authority

A background job acts later than the request that caused it. Decide which authority applies. Some actions need the current policy at execution time, so the worker checks the resource again before acting. Others may rely on an approval captured when the command was accepted; that is a distinct business rule. Record the approving identity, the decision, the policy version, the action and the resource with the command.

An ordinary access token copied into a queue makes a poor substitute for a deliberate delegation. Its lifetime may be shorter than the backlog, and its audience is the API rather than the worker. Give the worker its own workload identity and record on whose behalf it acts.

## Workload identity and secrets

Services need identities too, to call storage, queues and other APIs. Prefer short-lived credentials issued through the platform's **workload identity** mechanism. A long-lived shared secret copied into several deployments makes rotation and attribution hard.

Grant each workload only the actions it needs, on the resources it needs:

- the submission API writes request records but cannot manage infrastructure;
- the handoff worker sends handoffs to the CRM but cannot read analytics datasets;
- the work-order integration creates ERP work orders but cannot read customers' attachments.

Keep secrets in a secret management service, control access to it, and plan rotation and emergency revocation. Encrypting a secrets file achieves nothing if the decryption key sits beside it with the same access.

## Test the policy

A test plan should separate five failure cases:

1. invalid identity evidence, such as a bad signature or an expired token;
2. a valid identity without the needed permission;
3. a token issued for a different audience;
4. the correct tenant but the wrong owner, as with customer p above;
5. access removed after the token was issued.

Include allowed cases as well. A policy that denies every request passes all the negative tests while failing the business. For each rule, the architecture review should name the component that enforces it and explain how a route added next year will get the same enforcement.

## Key points

- Authentication establishes the principal; authorisation decides each action on each resource under current policy.
- ID tokens are for the client and access tokens are for an API; validate signature, issuer, audience, lifetime and claims.
- Use the authorisation code flow with PKCE through a maintained library.
- Derive every decision from validated identity, server-side entitlements and the resource's stored attributes, never from tenant identifiers supplied by the caller.
- Staff access needs a role, a business unit and an authorised set of customer organisations; test wrong-owner, wrong-audience and revoked-access cases as well as allowed ones.
