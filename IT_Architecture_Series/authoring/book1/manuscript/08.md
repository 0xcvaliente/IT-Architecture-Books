# 8 APIs and integration contracts

## Learning objectives

After this chapter you should be able to:

- Compare the four integration styles: file transfer, shared database, remote procedure invocation and messaging.
- Design a resource-oriented HTTP contract and explain which REST constraints it follows.
- Design an idempotency contract for a submission API, including scope, conflicts and retention.
- Evaluate a contract change for syntactic and semantic compatibility using OpenAPI, gRPC, AsyncAPI or a schema registry.
- Critique pagination, webhook and gateway designs for reliability and security.

## An API is an agreement

An **application programming interface** (API) defines how a consumer requests or receives behaviour from a provider. The contract covers more than field names:

- syntax: the structure of requests and responses;
- meaning: what a successful response confirms;
- permissions: who may call it, for which resources;
- errors, timing and operational limits;
- how the contract will change over time.

A JSON schema describes structure. It cannot explain what “received” means. For Meridian, `POST /service-requests` returns a receipt before the CRM has seen the request. The contract must say so plainly. A consumer that read the receipt as “the CRM has created the case” might tell the customer that an agent is already working on it.

## Four integration styles

Hohpe and Woolf describe four basic ways for applications to share data and behaviour {REF:eip}:

- **File transfer.** One application writes a file that another later reads.
- **Shared database.** Several applications read and write the same database.
- **Remote procedure invocation.** One application calls a function or endpoint of another and waits for the result.
- **Messaging.** Applications exchange messages through a channel, without waiting for each other.

{FIG:integration_styles} contrasts the styles, and each appears somewhere in a typical enterprise:

| Style | Meridian example | Main risk |
| --- | --- | --- |
| File transfer | ERP's nightly export of assets to analytics | Data is up to a day old |
| Shared database | The CRM reading portal tables directly | Any schema change breaks the other system |
| Remote procedure invocation | The portal reading entitlements through ERP's read API | The caller waits on the provider's availability |
| Messaging | The CRM's `ServiceCaseApproved` event reaching the work-order integration | Delayed, duplicated or out-of-order messages |

The styles trade timeliness against coupling. File transfer couples systems loosely but delivers stale data. A shared database is immediate but couples both systems to one schema and blurs who owns each fact; for that reason Meridian rejects it. Remote invocation gives fresh answers but makes the caller depend on the provider being up. Messaging decouples timing at the cost of asynchronous state, which Chapter 10 examines.

## Resources, representations and REST

Most of Meridian's APIs use HTTP in a resource-oriented style. A **resource** is anything the API names, such as a service request. A client works with **representations** of it, usually JSON. A submission resource needs a stable identifier, a state, and links or documented endpoints for the actions that follow. Keep internal database details out of the contract unless they are deliberately part of it.

~~~json
{
  "submission_id": "7f3a9c2e-4b1d-4c8a-9e5f-2d6b0a1c3e47",
  "status": "received",
  "received_at": "2026-10-05T09:14:03Z",
  "status_url": "/service-requests/7f3a9c2e-4b1d-4c8a-9e5f-2d6b0a1c3e47"
}
~~~

The `submission_id` is the UUID that the portal assigned when it stored the request, as in the Chapter 6 schema. Prose and figures in this book shorten it to its first eight characters, `7f3a9c2e`.

Choose the status code from what the response confirms:

- `201 Created` fits when the resource now exists, even if further work follows. Meridian's receipt qualifies: the request is durably stored, and the response's `Location` header can point to it.
- `202 Accepted` fits when the server has accepted work for processing but has not yet created the result. A report generated in the background is a typical case.

The queue inside the implementation does not decide the code; the resource contract does.

Fielding defined **REST** as an architectural style made of constraints {REF:rest}:

- client–server separation;
- stateless interaction, where each request carries everything needed to understand it;
- cacheable responses, labelled as such;
- a uniform interface: resources identified by URIs, manipulated through representations, with self-descriptive messages and hypermedia links that drive the application's state;
- a layered system, so clients cannot tell whether they reach the server directly or through intermediaries;
- optional code on demand.

JSON over HTTP alone does not make an API RESTful. Ask concrete questions instead. Does the response tell the client which transitions are allowed now? A closed request, for example, should not advertise an update link. Is caching behaviour explicit? The examples in this book are resource-oriented HTTP contracts and do not claim full REST conformance. A server-side browser session can be a sound identity design even though it departs from the stateless constraint. Assess the actual architecture rather than awarding a label.

Other API styles suit other needs. **RPC-style** APIs expose operations, such as `approveCase`, instead of resources. **GraphQL** lets clients choose the fields they receive in a single query. None is automatically better; compare consumer needs, caching, authorisation, query cost and support effort.

## Idempotency as a business guarantee

An operation is **idempotent** when repeating it has the same intended effect as performing it once. `POST` is not idempotent by default, so Meridian's submission API adds an idempotency contract. The browser creates a submission key when the customer opens the form and sends it in an `Idempotency-Key` header with every attempt. The server scopes the key to the tenant and the authenticated submitter:

| Situation | Server response |
| --- | --- |
| New key for this submitter | Store the request, assign a submission ID and return `201` with the receipt |
| Same key, same submitter, same payload | Return the original receipt; create nothing |
| Same key, same submitter, different payload | Reject with `422 Unprocessable Content` |
| Same key while the first attempt is still being processed | Reject with `409 Conflict`; the client retries later |
| No key on a submission | Reject with `400 Bad Request` |
| Same key from a different submitter | Treat it as a separate request, because each submitter has their own key space |

These status codes follow the IETF HTTP API working group's Idempotency-Key header draft {REF:idemkey}. Persist the key, the submitter, a hash of the relevant payload and the submission ID in the same transaction as the request itself, as in the Chapter 6 schema. The unique constraint on (`tenant_id`, `submitted_by`, `submission_key`) then decides concurrent attempts; an in-memory dictionary cannot. The key is not a credential. The service still authenticates and authorises every call, and takes the submitter from the verified identity rather than from the request.

Define what happens when a key expires. A retry that arrives after the server has forgotten the key looks new. Keep business identifiers and a reconciliation process that can detect long-delayed duplicates.

## Validation and compatibility

Validate syntax, types, ranges, allowed states and permissions at the service boundary. Treat every input as untrusted, including responses from internal systems. A request can pass schema validation and still ask for a transition that the business forbids.

Prefer compatible evolution. Two kinds of compatibility matter:

- **Syntactic compatibility**: old clients can still parse the new messages. Adding an optional field usually preserves it, although a strict client that rejects unknown fields can still break.
- **Semantic compatibility**: the same values still mean the same things. If `status` once meant “stored by the portal” and later means “confirmed by the CRM”, every client still parses it, but clients that act on it now behave wrongly.

Enumerations are a frequent trap. A client written when `status` had three values can fail on a fourth. State in the contract how clients must treat unknown values, such as displaying them as “in progress”.

Version a contract when a breaking change is unavoidable. Give consumers a migration path, measure who still uses the old version, and agree an end date. Keeping old versions forever has security and support costs.

## Describe contracts in machine-readable form

Machine-readable descriptions let tools generate documentation, client code and tests:

- **OpenAPI** describes HTTP APIs: paths, request and response schemas, authentication schemes and examples {REF:openapi}.
- **gRPC** defines services and messages in Protocol Buffers and generates client and server code. It runs over HTTP/2 and supports streaming in both directions, which suits internal service-to-service calls with strict contracts {REF:grpc,grpcabout}.
- **AsyncAPI** describes message-driven APIs: the channels, the operations on them and the message schemas, independent of the broker {REF:asyncapi}.
- A **schema registry** stores each version of a message schema and checks compatibility when a producer registers a new version {REF:schemareg}.

Registries commonly offer these compatibility modes:

- **Backward**: consumers using the new schema can read data written with the previous schema.
- **Forward**: consumers using the previous schema can read data written with the new schema.
- **Full**: both directions hold.

Transitive variants check against every earlier version, rather than only the latest one. For example, adding an optional field with a default value usually passes all three checks, while adding a required field without a default fails the backward check. A registry checks syntax. It cannot check semantic compatibility, and no description format can express every guarantee. Keep idempotency scope, ordering and the meaning of asynchronous completion in the contract's prose.

## Pagination, limits and deadlines

A list endpoint must define its order and pagination. **Offset pagination** (`?offset=40&limit=20`) is simple but can repeat or skip records when rows are inserted while a client pages through. **Cursor pagination** returns an opaque token that marks the last row seen; built on a stable sort key, it continues correctly as data changes.

Limit page size, payload size and expensive queries. Rate limits protect capacity, but consumers need a documented response, retry guidance and a way to tell throttling apart from invalid requests. An unbounded export endpoint can become an accidental denial of service.

Give every external call a timeout, and allocate one end-to-end deadline across all dependencies. For example, three attempts with a ten-second timeout each can take thirty seconds, which cannot fit inside a two-second response target.

## Webhooks

A **webhook** delivers an event to an HTTP endpoint that the consumer provides. The consumer should:

1. verify the signature, using the exact bytes and algorithm the provider specifies;
2. reject replays where the provider supplies a timestamp or nonce;
3. validate the payload;
4. store the event durably and acknowledge it;
5. process it later, deduplicating by event identifier, because providers retry.

Accepting a webhook and finishing the business processing are separate steps. Provide a review path for events that fail processing; silently dropping invalid messages makes reconciliation impossible. Keep secrets out of query strings, keep sensitive payloads out of logs, and rotate signing keys through a controlled process.

## Gateways and ownership

An **API gateway** handles routing, throttling, policy and some authentication checks. Business authorisation still belongs where the operation and the resource are understood. A gateway cannot know whether an agent's business unit and customer scopes cover a particular request unless the design supplies and verifies that context.

Give every contract an owner. Record the provider, consumers, data classification, expected volume, failure behaviour, change policy and escalation route. The code can be correct while the organisational contract is missing.

## Worked contract review: the CRM handoff

Meridian's design assumes that the CRM accepts the submission ID as an idempotency key (assumption A01 in Chapter 2). The contract review, backed by a duplicate-key test in the vendor sandbox, finds two relevant features:

- an idempotency key header, which the CRM honours for 24 hours, confirming A01 within that window;
- an `external_reference` field, which is searchable, but which the vendor does not promise to keep unique.

The retry policy must fit inside that window. The longest planned outage is thirty minutes, and the worker retries for up to six hours before moving a handoff to `manual_review`. Six hours is well inside 24, so every automatic retry is protected by the key. A handoff replayed manually after 24 hours is not protected. The runbook therefore requires a search on `external_reference` before any manual replay, and accepts a small residual risk that two people replay the same handoff at once. The review records that risk and its owner. The design never promises a stronger guarantee than the provider offers.

## Key points

- An API contract states meaning, permissions, errors, timing and change policy as well as structure.
- File transfer, shared database, remote procedure invocation and messaging trade timeliness against coupling.
- REST is a set of constraints; choose status codes from what the response confirms.
- An idempotency key, stored atomically with the result and scoped to the tenant and submitter, turns retries into safe operations within its retention window.
- OpenAPI, gRPC, AsyncAPI and schema registries make contracts checkable, but semantic compatibility still needs prose and review.
