# 21 Worked architecture: customer portal and enterprise integration

## Learning objectives

After this chapter you should be able to:

- Construct consistent container, component, sequence and deployment views of one system.
- Specify a durable submission contract and a handoff state model that every component uses identically.
- Trace the ERP work-order path and the ERP read model, and assign an owner to each business fact.
- Calculate the backlog and recovery time of a CRM outage from stated workload assumptions.
- Evaluate the release evidence and unresolved decisions for a first release.

## Start with ownership and the user promise

Meridian's business problem is the unreliable movement of equipment service requests between customers, service agents, the CRM and ERP. Duplicate entry creates conflicting records, and missing acknowledgements make customers submit again. A new web form alone cannot fix uncertain handoffs or unclear data ownership.

The first release makes a narrow promise. A receipt with status `received` means that the portal has durably stored the request and taken responsibility for its handoff. Approval, a technician visit, parts and repair all come later, from the systems that own them. What the customer sees follows the handoff state:

| Handoff state | Customer-visible status |
| --- | --- |
| `pending`, `in_flight` or `retry_due` | "Received" |
| Any of the above beyond the agreed delay | "Received, awaiting service team" |
| `confirmed` | The CRM's case status, for example "In progress" or "Resolved" |
| `manual_review` | "Received, awaiting service team" |

A delayed handoff is therefore shown honestly, and the portal never invents a CRM state it has not received.

The workload, staffing and targets come from the case brief at the start of the book:

- 600 customer organisations and 40 service agents in three business units.
- 100,000 requests a year, with an exceptional peak of 20 submissions per second for ten minutes.
- A receipt within one second for 95 percent of valid submissions, and 99.9 percent monthly receipt success.
- No loss of accepted requests during a thirty-minute CRM outage.

Each promise has its own indicator. Sign-in, uploads and status freshness are measured separately from receipt success.

Access follows the case policy. A customer reads the requests they submitted, and reads colleagues' requests only through an explicit organisation-wide delegation. A staff member needs the service-agent role, an assigned business unit and a set of authorised customer-organisation scopes. One agent may serve several tenants, so the policy checks the request's tenant against the agent's whole scope set.

## Who owns each fact

| Fact | Owner | Portal treatment | Conflict rule |
| --- | --- | --- | --- |
| Assets, contracts and service entitlements | ERP | Cached read model with source version and freshness | ERP wins; a stale copy is labelled or refreshed |
| Initial request and receipt | Portal | Durable record and idempotency result | Same key and payload return the same receipt |
| Service case and its progress | CRM, after confirmed handoff | Customer-facing status projection | Reject updates older than the stored source version |
| Work orders, scheduling and parts | ERP | Selected status for display | ERP owns scheduling and completion |
| Staff role, business unit and scopes | Workforce identity and access management | Evaluated on every request | Changes apply within the stated revocation bound |
| Credentials and sessions | Identity provider | Validated principal and bounded session | Follow the identity provider's revocation policy |

A local copy is never a second owner. The ERP read model records where each fact came from, which version it is and when it was refreshed, and the design states what happens when it is too old. For example, if entitlement cannot be confirmed while ERP is unavailable, the portal can still accept the request for later review. It shows a different message and promises no covered service until ERP confirms the entitlement.

## Container view

{FIG:containers} shows the runtime containers and their relationships. Solid arrows are synchronous calls or writes; dashed arrows are asynchronous events and status updates. The dashed boundary marks the Meridian solution, which the portal team runs. The identity provider takes part in sign-in and is omitted for clarity.

FIGURE containers | The portal owns receipts and a versioned ERP read model; approved CRM cases reach ERP only through the work-order integration.

Read the figure in three paths:

1. **Submission.** The browser calls the portal API over HTTPS. The API authenticates the principal, checks access, validates the request and, in one database transaction, stores the submission and an outbox handoff record. It then returns the receipt. Attachments go to object storage through an authorised upload and stay quarantined until scanning releases them.
2. **Handoff.** The handoff worker claims outbox records, creates the case in the CRM using the submission ID as the idempotency key, and records the result. The CRM later sends case status updates, which the portal projects for customers.
3. **ERP.** When a service agent approves a case, the CRM emits a `ServiceCaseApproved` event. The work-order integration, part of the Meridian solution and run by the portal team, consumes it and creates the ERP work order, using the service case ID as the idempotency key. Separately, a sync job reads asset, contract and entitlement facts, and selected work-order status, through ERP's read API and stores them in the versioned read model.

The portal never creates work orders itself. That keeps one path into ERP, owned by one team, with one idempotency rule.

No message broker is needed to make the design asynchronous. At this scale the worker can poll the outbox table. A broker could later add buffering or fan-out to several consumers, but it adds another durability and operating boundary; the outbox would still be needed, because the database and the broker cannot commit atomically together.

## Component view inside the portal API

FIGURE components | Components inside one portal API process separate policy, transaction and vendor concerns.

{FIG:components} breaks the portal API into code responsibilities, all inside one deployable process. The controller translates the HTTP contract. The policy component establishes the trusted principal: a customer with tenant and ownership facts, or an agent with a business unit and a set of customer-organisation scopes. The submission service enforces the workflow and opens a unit of work. Repositories store the request, the idempotency record and the outbox record in one transaction. The CRM adapter sits on the worker's path, so the receipt never waits for the CRM.

This split keeps two kinds of change apart. A new CRM field changes the adapter and its contract tests. A new rule about who may submit for an asset changes the policy and domain code and their tests.

The transaction protects one invariant: every accepted request has exactly one submission ID, one receipt result and an initial outbox record. A unique constraint on tenant, submitting user and submission key resolves concurrent retries with the same key, as in Chapter 6. The stored record also holds a digest of the canonical payload, so that reuse of a key with different content is rejected. File bytes follow their own staged workflow, because object storage sits outside the database transaction.

## The successful sequence

FIGURE acceptance | A successful receipt sequence ends at local durable acceptance.

In {FIG:acceptance}, the browser sends an authenticated request with an idempotency key and, if needed, an attachment reference. The API derives the principal's scope from trusted policy, validates the content and commits the submission, payload digest, receipt and outbox record together. Only after the commit does it reply. The response is `201 Created` for the new local resource:

~~~json
{
  "submission_id": "7f3a9c2e-4b1d-4c8a-9e5f-2d6b0a1c3e47",
  "status": "received",
  "handoff_state": "pending",
  "received_at": "2026-10-05T09:14:03Z",
  "status_url": "/service-requests/7f3a9c2e-4b1d-4c8a-9e5f-2d6b0a1c3e47"
}
~~~

This is the Chapter 8 receipt with one more field, `handoff_state`, which the portal's support pages use to show delivery progress; customers still see "Received". If the response is lost, the browser repeats the request with the same key and content and receives the same receipt, with the same submission ID. If it reuses the key with different content, the API answers `422 Unprocessable Content`, as in Chapter 8. If the browser invented a new key for each retry, the API could not recognise the repeat, so client behaviour belongs in the integration tests.

## The handoff state model

Every component that delivers work uses the five handoff states and transitions of Chapter 10, from `pending` through `in_flight` to `confirmed`, with `retry_due` and `manual_review` for failed attempts. A claim moves `pending` or `retry_due` to `in_flight` atomically. A lease limits how long a claim lasts, and a stale lease holder's late result is rejected by a version check. A lease reduces duplicate work but cannot make the remote call unique. Uniqueness comes from the idempotency key the CRM receives. The work-order integration uses the same five states for its deliveries to ERP.

## The uncertain-outcome sequence

FIGURE uncertain | Outside the idempotency window, a lost CRM response is reconciled by lookup before any repeat.

The hard case is a timeout. The CRM may have created the case before the response was lost, and the worker cannot tell this apart from a failure before creation. It keeps the same command identity and moves the record to `retry_due`. Because automatic retries end well inside the key window confirmed in Chapter 8, each one simply repeats the call with the same key.

A lookup is needed only when the key window may have passed, for example when an operator replays a handoff from `manual_review` a day later. {FIG:uncertain} shows that path: the worker queries the CRM by the submission ID stored as the external reference before it repeats anything. The vendor has not confirmed that external references are unique, so the release dossier carries a condition: verify that guarantee, or obtain business acceptance of manual reconciliation for late replays and the residual duplicate risk. A lookup can return three results:

- **Zero matches.** If the CRM's lookup is eventually consistent, this does not prove that no case exists; wait for the stated consistency window, then retry.
- **One match** whose identifiers and content agree: record the mapping and move to `confirmed`.
- **Several matches**: move to `manual_review`, resolve through a controlled duplicate process, and record the decision without deleting a legitimate record.

## The ERP work-order path

The ERP path repeats the same pattern one step later. The CRM delivers `ServiceCaseApproved` at least once, so the work-order integration can see the same event twice. It records each event in an inbox table keyed by the event ID, in the same transaction as its own delivery record. It then calls ERP with the service case ID as the idempotency key. A duplicate event finds the existing record and does nothing; a timeout leads to the same lookup-before-retry logic as the CRM handoff.

The approval stays valid while ERP is unavailable. The integration's delivery record waits in `retry_due`, and the customer continues to see the CRM's case status, such as "Approved, scheduling". Work-order status flows back to the portal through the read-model sync, labelled with its source version.

## Attachments and trust boundaries

Treat upload as a staged process: authorised intent, bounded upload, quarantine, scanning and controlled release. An uploaded object stays hidden from staff until scanning releases it, and metadata in the database records the scan result and access scope. Object names are never treated as proof of tenant or access.

For example, a request may be accepted while its attachment is still quarantined, and the interface shows the difference. Expired upload intents and orphaned objects need clean-up, and rejected files need a retention and investigation policy. Chapter 15 compares proxy and direct-download designs for releasing files.

Each boundary has its own threats. The API checks resource authorisation even when a gateway has validated the token. The worker holds only the CRM permissions its handoff needs. Recovery credentials for administrators are separate from workload identities, and scanning runs with restricted privileges because every uploaded file is untrusted.

## Deployment and failure domains

FIGURE deployment | Three zones each run one API replica, two zones also run a worker, and every runtime unit shares the managed database and the external dependencies.

{FIG:deployment} follows the sizing in Chapter 14. Load tests show that one API replica serves 12 submissions per second within the latency target, so the API runs one replica in each of three zones. If a zone fails, the two survivors serve 24 per second, above the peak of 20. Two workers run in different zones and claim outbox records with the conditional update from Chapter 6, so a zone failure delays handoffs by at most one lease period; the platform adds up to two more workers when the age of the oldest handoff grows. Every API replica and every worker connects to the same zone-redundant managed database. Verify its replication and failover behaviour, including client reconnection and the fate of in-flight transactions; a database drawn across three zones is a claim to test, not evidence.

Shared dependencies remain: identity, name resolution, database access, secrets, deployment configuration and the external CRM. Zones do not protect against a bad release deployed everywhere or a revoked credential used by every worker. Regional disaster recovery follows the pilot-light plan from Chapter 13.

An Azure implementation could evaluate Container Apps, Azure Database for PostgreSQL, Blob Storage, Key Vault and Azure Monitor. An AWS implementation could evaluate ECS with Fargate, RDS for PostgreSQL, S3, Secrets Manager and CloudWatch. Compare regional support, private connectivity, identity integration, recovery, scaling and cost before choosing.

## Capacity and recovery reasoning

### From annual volume to arrival rates

The annual average is 100,000 / (365 × 24 × 3,600) ≈ 0.0032 submissions per second, or about 11.4 an hour. The exceptional peak of 20 per second is about 6,300 times that average, which is why annual volume can never serve as a capacity specification. The peak lasts ten minutes and produces 20 × 600 = 12,000 submissions.

Ordinary demand is uneven too. Assume, for planning, that the busiest hour of a normal day carries ten times the annual hourly average: about 114 submissions an hour, or 0.0317 per second. Replace this assumption with measured data as soon as the portal runs.

### Modelling the thirty-minute CRM outage

Suppose the CRM is unavailable for thirty minutes during that busiest hour, and assume, pending the vendor's confirmation, that its quota allows 5 handoffs per second.

- Backlog at the end of the outage: 0.0317 × 1,800 ≈ 57 handoffs.
- Net drain rate after recovery: 5 − 0.0317 ≈ 4.97 per second.
- Ideal drain time: 57 / 4.97 ≈ 11.5 seconds.

At Meridian's normal volume, throughput is plainly not the constraint. The retry schedule is. Chapter 10's backoff doubles from 2 seconds up to a cap of 15 minutes. A handoff whose wait has reached the cap just before the CRM returns may therefore sit in `retry_due` for up to 15 minutes after recovery, nearly 80 times longer than the drain itself. The design therefore brings due times forward when a health probe shows that the CRM has recovered, and then delivers at a controlled rate within the quota.

Now take the rare stress case in which the outage overlaps the exceptional peak. The backlog becomes about 12,000 + 0.0317 × 1,200 ≈ 12,038 handoffs, and the ideal drain takes 12,038 / 4.97 ≈ 2,420 seconds, about 40 minutes. The one-minute freshness target cannot hold in that case. The design declares a separate recovery objective, shows "Received, awaiting service team", and asks the vendor whether a higher quota is available during recovery. Variable call times, retries and other consumers sharing the quota would lengthen both results.

### Storage at the peak

At the maximum attachment size, 12,000 files of 10 MB each come to 120,000 MB, or 120 GB in decimal units, before replicas, metadata or versions. This is a worst-case input, far above expected use. Estimate the real file-size distribution, attachment frequency, retention and scanning capacity before sizing storage and network links.

## Release evidence and unresolved decisions

A minimum release review needs:

- Scoped authorisation tests across API, export, search and attachments.
- Concurrent duplicate-key and payload-conflict tests.
- A lost-response test for both the CRM handoff and the ERP work-order path.
- Attachment state tests.
- A peak-load report and a thirty-minute CRM-outage exercise.
- A restore rehearsal and the pilot-light recovery test.

It also needs operational ownership: who investigates `manual_review` items, how customers are informed, and how every accepted receipt is reconciled.

Several questions remain open: the CRM's uniqueness guarantee and rate limits, entitlement freshness during ERP outages, the retention policy, the real workload shape, the exact recovery objectives and the cloud configuration. Each has an owner and a deadline. An architecture can carry open assumptions safely while they are visible and governed.

## Key points

- The receipt promises durable local responsibility; customers see "Received" until the CRM confirms, then the CRM's case status.
- One set of handoff states, `pending`, `in_flight`, `confirmed`, `retry_due` and `manual_review`, is used for every delivery, so nothing is silently lost.
- Approved cases reach ERP only through the work-order integration, keyed by service case ID; the portal reads ERP facts from a versioned read model.
- Derive arrival rates from the case and a stated busy-hour assumption; at normal volume the retry schedule, rather than throughput, dominates recovery after an outage.
- A complete design names its unresolved assumptions, their owners and the evidence that will close them.
