# 24 Worked architecture: cloud migration and modernisation

## Learning objectives

After this chapter you should be able to:

- Design operable transition states that keep one declared write authority for each business domain.
- Design reconciliation checks that go beyond row counts.
- Calculate a cutover timeline against a maintenance window, including the latest safe decision point.
- Distinguish routing rollback, application rollback, database restore and compensating business actions.
- Evaluate a migration plan's evidence gates and retirement steps.

## Modernisation is a business transition

Orion Modernisation replaces part of a legacy order and warehouse application. The legacy system runs on virtual machines with a relational database, scheduled file exchanges and several undocumented consumers. The first release moves customer order status and new order intake to a managed cloud runtime, while warehouse execution stays on the legacy system. The estate holds two million historical orders, three reporting teams depend on it, and the business has approved a thirty-minute maintenance window for the final write cutover.

The window is a local agreement, and the plan must show by rehearsal that the cutover fits it. A successful small import shows that the mapping works, while the full migration's duration has to be measured at full volume.

The business goals are supported operation, safer change and clearer integration ownership. Moving the same defects to new hosting achieves none of them, while rewriting every module before delivering any benefit delays learning and widens scope. Separate four kinds of change so that each risk can be judged on its own:

- **Hosting** changes, such as moving to a managed runtime.
- **Interface** changes, such as a new order API.
- **Data** changes, such as a new schema or new identifiers.
- **Process** changes, such as a new approval step.

## Discover the real dependency graph

Inventory every kind of dependency:

- entry points, scheduled jobs and file transfers;
- database readers and writers;
- identities, certificates and network paths;
- licences, retention obligations and support procedures.

Compare what people say in interviews with what logs and runtime observations show. For example, a spreadsheet export used once a quarter may be missing from a one-week observation, and a dormant recovery process can still be a critical dependency.

Classify each dependency by owner and consequence. A read-only reporting extract can often move on a different schedule from a warehouse job that writes order state. Shared database access deserves special attention, because it bypasses the application's intended boundary. Before migrating, find out whether any other job updates the same rows and what that means for the proposed source of truth.

Draw the current state as it is, and mark the uncertainties. Assign an owner and a verification task to each consequential unknown. The first deliverable may well be a dependency inventory and a recovery rehearsal, before any cloud deployment.

## Transition architectures

FIGURE migration | Four operable migration states with one declared write authority per domain.

{FIG:migration} shows four states, each operable on its own:

- **State A.** All order writes stay in the legacy system. The new application receives a read projection for testing, with no customer traffic and no authority.
- **State B.** Selected read-only status queries go to the new application; order writes remain with the legacy system.
- **State C.** After write fencing and final reconciliation, a defined cohort of orders, or a whole domain, moves its writes to the new system.
- **State D.** The replaced legacy responsibility is retired once evidence shows that nothing depends on it.

For each state, document routing, write authority, replication, identity, monitoring and recovery. A state in which engineers must remember which database to edit by hand is not controlled.

The routing seam follows the strangler fig pattern from Chapter 19. Route by a stable, server-side rule, such as migrated customer cohort or capability, and version that rule. An individual order never switches owner unpredictably; an order with work in progress keeps one owner throughout the relevant part of its lifecycle.

Where the new system must call the legacy one, Orion places an anti-corruption layer between them, as described in Chapter 19, so that the legacy model's quirks stay out of the new design.

## Data mapping as a semantic problem

Profile the source before transforming it. Look for duplicate business identifiers, nulls, invalid references, overloaded status fields, inconsistent time zones and historical exceptions. A mapping table states approved business meaning, which is more than renaming fields.

For example, suppose the legacy order status `X` means "cancelled" for web orders but "archived" for telephone orders. The mapping must use the order channel to decide, and the business owner must approve it:

| Legacy status | Condition | Target status | Notes |
| --- | --- | --- | --- |
| `X` | Channel = web | `cancelled` | Confirmed with order operations |
| `X` | Channel = phone | `completed` and archived | Archive flag kept as metadata |
| `H` | Any | `on_hold` | Hold reason copied unchanged |
| Blank | Created before 2015 | `completed` | Business owner approved; flagged for audit |

Separate lossless representation changes from semantic ones. Converting a date string into a timestamp adds false precision when the source never recorded a time of day. Splitting a free-text address into fields may need manual review. Keep source identifiers and enough migration provenance to explain how each target record was produced.

Declare the reconciliation boundary: the source snapshot or change position, the tables and aggregates included, the transformation version, and the excluded records with reasons. Then count records, compare key sets, check relationships and reconcile important totals at a suitable grain. A target with exactly two million rows can still be wrong if one valid row is missing and another duplicated.

## Copy, then catch up, without two masters

A common approach takes a consistent initial extract and then applies the changes that happened after it. The **source position**, such as a log sequence number, links the snapshot to the change stream, so that no change is missed or applied twice. An arbitrary file export combined with change capture started at some unrelated time gives no such guarantee.

While the legacy system remains authoritative, every target change comes from it through an idempotent, version-aware process. Track deletes and corrections as well as inserts. Monitor lag and failures per table and partition: a low average lag can hide one stalled table that matters for the cutover.

Avoid naive dual writes from the application. If the code writes to the legacy database and then to the cloud database, either write can fail after the other succeeds; reversing the order only reverses the inconsistency. A durable intent, change capture or another controlled replication method can bridge the transition under a stated contract. At any moment, each domain still has exactly one write authority.

## A concrete cutover argument

FIGURE cutover | A write fence and reconciliation gate separate reversible routing from new authoritative writes.

Before the window opens, confirm that the target has the capacity, identities, network access, monitoring and backups it needs, that the source positions are recorded, and that operators can reach both systems. Rehearse the whole procedure and time each step. During the window, follow {FIG:cutover}: fence the legacy writes, wait for in-flight work to reach the agreed boundary, capture the final position, apply the remaining changes and run the release reconciliation.

Only after those checks pass may routing send new authoritative writes to the target. Keep the legacy system protected from accidental writes. A maintenance banner in the user interface is not a write fence when integrations and scheduled jobs can still update the database; the fence must cover every known write path, and its effect must be checked.

### Worked example: fitting the window

A rehearsal measures the steps:

| Step | Minutes | Running total |
| --- | --- | --- |
| Establish the write fence | 4 | 4 |
| Drain and apply remaining changes | 9 | 13 |
| Critical reconciliation | 6 | 19 |
| Routing change and smoke tests | 3 | 22 |
| Go or no-go decision | 2 | 24 |

The plan takes 24 minutes, leaving 6 of the 30. That margin must also cover the way back. The rehearsal shows that lifting the fence and restoring legacy routing takes 4 minutes, so the **latest safe decision point** is minute 30 − 4 = 26. The planned decision at minute 24 leaves 2 minutes of margin for variation.

Set that latest decision point in the runbook. If reconciliation is still incomplete by then, the team restores the pre-cutover state while the legacy system is still authoritative. Name the person who decides and the evidence they need.

## Rollback after new writes is a different problem

Before the target accepts authoritative writes, routing back is straightforward, provided the source remains intact and current. Once new orders exist only in the target, switching routing back would hide or lose real business. Recovery must then keep those orders: replay or transform them into the legacy model if that is supported, or keep the target authoritative and fix the defect forward.

A semantic change may have no safe automatic reverse. A new target state may not exist in the legacy schema at all. The architecture must then choose explicitly between forward recovery, a compatible transition design, or a period during which new features stay disabled. "Rollback available" means little unless it covers data and business state as well as infrastructure.

Four recovery actions differ:

- **Routing rollback** sends traffic back to the old system.
- **Application rollback** redeploys the previous version of the code.
- **Database restore** returns data to an earlier point, removing every later transaction.
- **Compensating business actions** correct specific outcomes, such as cancelling a duplicate shipment.

A restore is never an ordinary undo. Recovery procedures state the acceptable loss, how missing transactions are found and who authorises the action.

## Security and operating readiness

Migration creates temporary copies, elevated transfer identities, staging environments and new access paths. Apply data classification and retention to all of them. A staging export with production data must not inherit a development sandbox's weaker access policy. Remove temporary privileges and transfers after the transition, and verify that they are gone.

Test the new operating model: deployment, incident response, restore, certificate rotation, vendor access and support escalation. An application that works only under a developer's administrator account is not ready for routine operation; the production service identity and operator identities need their own correctly separated permissions.

Costs often rise during coexistence, because both platforms, replication, extra support and temporary tooling all run at once. Include the overlap period and the retirement work in the business case. A licence saving appears only when the old service can be decommissioned under its contract.

## Evidence gates and retirement

Each state has a gate:

- **Gate A** needs a credible dependency inventory and a rehearsed recovery.
- **Gate B** needs a correct read projection and tested access controls.
- **Gate C** needs reconciled data, bounded lag, a verified write fence and a timed cutover rehearsal.
- **Gate D** needs stable operation over an agreed period, and evidence that old consumers, jobs and user groups have moved.

Retirement covers archiving or deletion decisions, disabled credentials, stopped scheduled jobs, removed routing, cancelled resources, updated documentation and confirmed ownership. Watch for missed dependencies through an approved decommissioning process. Keep the records needed for audit and recovery under the agreed lifecycle policy, rather than leaving an unsupported live system running indefinitely.

The strongest migration dossier explains every intermediate state and its failure response. The target diagram matters, but most of the risk lies on the path between the current and target states.

## Key points

- Migration is a business transition: separate hosting, interface, data and process changes and judge each risk on its own.
- Every transition state must be operable, with one declared write authority for each domain and a stable routing rule.
- A versioned, server-side routing rule moves functionality cohort by cohort, and an anti-corruption layer keeps the legacy model out of the new design.
- Reconcile key sets, relationships, values and totals within a declared boundary, because counts alone can hide errors.
- Plan the cutover so that the rehearsed rollback fits inside the window, and treat recovery after new writes as a business decision.
