# 13 Cloud architecture with Azure and AWS examples

## Learning objectives

After this chapter you should be able to:

- Explain the cloud service models and the responsibilities each leaves with the customer.
- Design an account or subscription structure that separates environments and teams.
- Map a vendor-neutral design to Azure and AWS services and list the differences to investigate.
- Compare disaster-recovery strategies against recovery objectives and cost.
- Evaluate the portability of a design and the credibility of its exit plan.

## Cloud as a service model

NIST defines cloud computing by five characteristics: on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service. It also defines three service models: infrastructure, platform and software as a service {REF:cloud}. The service model tells you who looks after which layer. Real products often sit between the categories, so read each service's contract.

With **infrastructure as a service** (IaaS), you rent virtual machines, disks and networks and manage the operating system yourself. With a **platform as a service** (PaaS), the provider runs the operating system, runtime or database engine, and you deploy code or data into it. With **software as a service** (SaaS), you configure and integrate a finished application, such as a purchased CRM.

| Layer | IaaS | PaaS | SaaS |
| --- | --- | --- | --- |
| Facilities, hardware and virtualisation | Provider | Provider | Provider |
| Operating system patching | Customer | Provider | Provider |
| Runtime or database engine | Customer | Provider | Provider |
| Application code and schema | Customer | Customer | Provider |
| Configuration, identities and access | Customer | Customer | Customer |
| Data classification, retention and use | Customer | Customer | Customer |

The last two rows never move to the provider. For example, when Meridian uses a managed PostgreSQL service, the provider patches the engine and runs the replicas. Meridian still designs the schema, grants access, decides who may read tenant data, sets the backup retention and tests restores.

A cloud decision weighs skills, operating model, compliance, integration, availability, cost and exit. Elasticity helps, but it still needs a capacity plan. Quotas, database connection limits and service configuration all cap what "scaling" can deliver.

## Organisation and isolation

An AWS account or an Azure subscription is an administrative, security and billing boundary. Use separate accounts or subscriptions for production and non-production work, so that a developer experiment cannot change production by accident. Set up identity, logging, policy, network layout and budget ownership before many teams start deploying.

A **landing zone** is a prepared foundation for workloads. It typically includes:

- An account or subscription structure, for example one production and one non-production subscription per workload.
- Baseline security policies, such as "no public storage buckets".
- Network connectivity to shared services and on-premises systems.
- Central audit logging that workload teams cannot delete.
- A standard deployment path with approved identities.

A good landing zone makes the approved path the easy path. Teams then reuse the controls instead of designing them again.

A **region** is a geographical location with one or more data centres. An **availability zone** is a separate failure domain inside a region, with its own power, cooling and networking. Service support, replication options and guarantees differ by service and region, so check the chosen service and region together.

## A neutral reference deployment

For Meridian, start with the responsibilities rather than products:

- A managed application runtime for the portal API and the handoff worker.
- An operational relational database for submissions and outbox records.
- Object storage for attachments.
- An identity service for customers and staff.
- Secret management and central telemetry.

Private dependencies sit behind controlled network access, and only the required interfaces are public. The API and worker can share a codebase while scaling separately. One database transaction records the submission and its outbox entry; the worker then delivers the handoff to the CRM. A scheduled analytics pipeline reads approved operational data through a controlled route.

At Meridian's scale this design needs neither Kubernetes nor an active-active multi-region database. Consider them when a measured requirement justifies their cost and operating effort.

Choose on required behaviour. For example, Service Bus and SQS both offer ordered delivery and duplicate detection as options, but they configure them differently and apply different limits. Before relying on either, write down the ordering and duplicate behaviour your design needs, then check that the selected options provide it.

## Identity and access in the platform

Keep workforce sign-in separate from workload permissions. Azure managed identities and AWS IAM roles let a workload obtain short-lived credentials from the platform, so nobody copies long-lived secrets into configuration. Their trust and assignment models differ. For each workload, state which service may use the identity and exactly what it may do.

Design administrative access separately. It needs strong authentication, the least privilege that works, approval for risky actions, an audit trail and a tested emergency process. A secure application gains little if an unrestricted production administrator account exists beside it.

Infrastructure policy can block some invalid deployments, such as a storage account with public access. Give every policy an owner and a documented exception route. A policy that every team must bypass to deliver work soon stops protecting anything.

## Regions, recovery objectives and disaster recovery

Zones and regions protect against different failures. Spreading API instances and a database across zones survives the loss of one data centre. A **regional disaster** needs a second region, together with usable copies of data, keys, identity configuration, DNS and operator access.

Two business targets drive the design:

- The **recovery time objective** (RTO) is the longest acceptable time to restore the service after a disaster.
- The **recovery point objective** (RPO) is the largest acceptable loss of data, measured back in time from the failure.

AWS describes four disaster-recovery strategies, ordered by recovery speed and cost {REF:awsdr}. Azure's guidance describes the same idea as cold and warm active-passive standby, and ties the choice to recovery targets and regular drills {REF:azuredr}. {FIG:dr_strategies} compares them.

FIGURE dr_strategies | Disaster-recovery strategies trade running cost in the recovery region for shorter recovery time and less data loss; the highlighted pilot light is the option Meridian chooses below.

Moving from left to right, more of the system runs in the recovery region before the disaster, so less has to be rebuilt during it. Backup and restore keeps only copies of data and rebuilds everything from infrastructure code; recovery takes hours. A pilot light keeps data replicated live but leaves the application switched off. A warm standby runs a smaller, working copy that only needs scaling up. Multi-site active/active serves traffic from every region all the time, so a failed region is simply routed around.

Replication alone protects against losing a site; it also copies corruption and accidental deletes within seconds. Every strategy therefore keeps point-in-time backups, and every strategy needs regular rehearsal. A recovery plan that has never been run is an assumption.

### Worked example: choosing Meridian's regional strategy

Meridian's business owner sets regional targets of RTO 4 hours and RPO 15 minutes. At 100,000 requests per year, an average 15-minute window contains about 100,000 / 8,760 / 4 = 2.9 requests. Each lost request breaks a receipt promise, so the recovery runbook includes a step to find the affected customers, for example from API access logs kept outside the database, and ask them to resubmit.

The platform team rehearses three options and estimates illustrative monthly costs for the recovery region:

| Option | Measured RPO | Measured RTO | Extra cost per month |
| --- | --- | --- | --- |
| Backup and restore, hourly copies | Up to 60 minutes | 5 hours | EUR 200 |
| Pilot light with database replica | Under 1 minute | 45 minutes | EUR 900 |
| Warm standby | Under 1 minute | 10 minutes | EUR 1,900 |

Backup and restore fails both targets. Pilot light meets both with margin, at EUR 10,800 a year. Warm standby also meets them, but it adds EUR 12,000 a year for a recovery speed the business has not asked for. The team chooses pilot light and records the rehearsal date, the measured times and the steps that took longest.

## Data placement and residency

Decide where authoritative data lives, how it is replicated and what happens when a region fails. An active-passive design keeps one writer and avoids write conflicts, but recovery must be tested. An active-active design serves users from several regions and must then resolve concurrent writes to the same record. Last-writer-wins by timestamp is simple but silently discards one update; data types designed to merge, known as conflict-free replicated data types, avoid that for counters and sets; and giving each record a home region avoids the conflict altogether. Chapter 12's partition reasoning shows why some such choice is unavoidable.

**Data residency** concerns where data is stored or processed. Sovereignty and lawful international transfer raise further legal questions. Choosing a European region is one input to a privacy assessment; the assessment itself still needs the privacy owner.

## Portability and lock-in

Every platform creates dependencies. Even virtual machines depend on networking, images, identity, monitoring and operating procedures. Managed services add platform-specific integration while removing maintenance work.

Identify which exit scenarios are credible, then test the important ones before they become urgent:

1. Can you export the data in a usable, documented form?
2. Can another system interpret the identifiers, relationships and attachments?
3. How long would migration take, and who would do it?
4. Which contracts and licences apply during the move?

Use abstractions selectively. A generic wrapper that hides every cloud feature imposes the limits of the weakest provider and still leaves migration work. Protect the business logic and data contracts, and accept documented platform choices where they add value.

## Worked choice: managed containers or virtual machines

Meridian compares a managed container runtime with virtual machines. The application has ordinary HTTP and worker workloads, no special kernel needs and a small operations team. A managed runtime removes operating system patching and supports separate scaling for the API and the worker.

The decision still depends on networking, runtime limits, observability, deployment controls and total cost. The team therefore runs a short proof of concept with private database access, a simulated CRM outage and a rollback. A "hello world" deployment shows only that the account works; the proof of concept shows that the design works.

> **Common mistake.** Treating zone redundancy as a disaster-recovery plan. Zones protect against a data-centre failure inside one region; a regional outage, a corrupted database or a deleted account needs a separate, rehearsed recovery path.

## Key points

- Start from responsibilities and guarantees, then choose services. Managed services shift maintenance work but leave data, access and configuration with the customer.
- Separate environments with accounts or subscriptions, and give teams a landing zone that makes the secure path easy.
- Service maps are vocabulary aids; check ordering, duplicate handling, limits and recovery for each selected option.
- Choose a disaster-recovery strategy from the business RTO and RPO, keep point-in-time backups, and rehearse the recovery.
- Portability comes from tested data export and clear contracts, rather than from hiding every platform feature.
