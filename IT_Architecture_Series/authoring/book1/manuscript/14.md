# 14 Containers, orchestration and infrastructure as code

## Learning objectives

After this chapter you should be able to:

- Explain what container images, orchestrators and infrastructure as code each provide.
- Calculate the replica count and utilisation limit that let a service survive the loss of one replica or zone.
- Design health checks and shutdown behaviour that keep durable work safe.
- Evaluate an infrastructure change plan for data loss, drift and recovery risk.

## Images and running containers

A **container image** packages application files and their dependencies. A running container is an instance of that image with its own runtime configuration and writable layer. Containers share the host's operating system kernel instead of carrying a full guest operating system, which makes them small and quick to start. Docker's introductory documentation explains this distinction {REF:docker}.

Keep images reproducible and easy to maintain:

- Start from a trusted base image and rebuild when it receives security updates.
- Pin dependency versions so two builds of the same commit produce the same contents.
- Deploy by **digest**, which identifies exact image content. A tag such as `latest` is a moving name.
- Keep secrets out of images, because layers and registries preserve them. Supply credentials at runtime through a controlled mechanism.

Run each container with the least privilege and filesystem access the workload needs. A container can still exhaust CPU, memory, disk or database connections, so set resource limits and test them. When memory runs out, the platform may stop the process abruptly. Business workflows must therefore tolerate interruption at any point.

## What orchestration adds

An **orchestrator** schedules workloads onto machines, watches their desired state, replaces failed instances and coordinates deployments and networking. Kubernetes provides APIs and controllers for this work {REF:k8s}. It keeps the declared number of copies running; the application still has to make each copy safe to run, stop and repeat.

The main Kubernetes objects map onto familiar responsibilities:

- A **Pod** is the smallest unit the scheduler places. It holds one or more closely related containers.
- A **Deployment** manages a set of identical Pods and rolls out new versions.
- A **Service** gives a stable network name for a changing set of Pods.
- ConfigMaps and Secrets supply runtime configuration.
- A **StatefulSet** gives Pods stable identities and storage. It helps run stateful software, but replication and backup remain the job of the software and its operators.

For a database, a managed data service is often the simpler choice, because the provider then runs replication, patching and backups.

## Health and readiness

Kubernetes distinguishes three probes. A **liveness** probe decides when to restart a container, for example one stuck in a deadlock. A **readiness** probe decides when a container may receive traffic. A **startup** probe gives a slow application time to initialise before the other probes begin {REF:probes}.

Design each probe around the question it answers. Suppose every API instance's liveness check queries the database. During a database outage, every check fails and the platform restarts every instance. The restarts add connection storms and start-up load just as the database recovers. The Kubernetes documentation warns that badly designed liveness probes can cause exactly this kind of cascading failure. A better design restarts a process only when the process itself is broken, and uses readiness to stop traffic when a dependency it needs is unavailable.

Shutdown needs the same care. When the platform stops an instance, it should stop accepting new work, finish or release in-flight work within a bounded grace period, and leave every unfinished task retryable. A worker acknowledges a task only after the durable result is recorded.

## Scaling and headroom

**Horizontal scaling** adds instances; **vertical scaling** gives an instance more CPU or memory. Both have limits. More API replicas open more database connections, and more workers can exceed a vendor's rate limit. Scale on a signal that tracks the real bottleneck: CPU for CPU-bound services, and queue age or backlog for workers, capped by what the downstream system accepts.

### N+1 headroom

Redundancy only helps if the survivors can carry the load. With n identical replicas sharing the work evenly, losing one leaves n − 1. Each replica must therefore run below (n − 1)/n of its capacity in normal operation.

- Two replicas must each stay below 1/2, or 50 percent.
- Three replicas must each stay below 2/3, about 67 percent.
- Four replicas must each stay below 3/4, or 75 percent.

Two replicas that each run at 90 percent cannot absorb the loss of one. The survivor would need 180 percent of its capacity, so it overloads, slows down and may fail too.

Zones follow the same rule. If replicas are spread evenly over z zones, losing a zone removes 1/z of the capacity. For example, suppose Meridian's API must handle the 20 requests per second peak, and load tests show that one replica serves 12 requests per second within the latency target. The listing finds the smallest even spread that survives the loss of one zone.

~~~python
def replicas_needed(peak_rps: float, per_replica_rps: float, zones: int) -> int:
    """Smallest even spread over the zones that survives losing one zone."""
    per_zone = 1
    while per_zone * (zones - 1) * per_replica_rps < peak_rps:
        per_zone += 1
    return per_zone * zones


for zones in (2, 3):
    n = replicas_needed(peak_rps=20, per_replica_rps=12, zones=zones)
    load = 20 / (n * 12)
    print(f"{zones} zones: {n} replicas, normal utilisation {load:.0%}")
~~~

~~~text
2 zones: 4 replicas, normal utilisation 42%
3 zones: 3 replicas, normal utilisation 56%
~~~

With two zones, each zone alone must carry the peak, so Meridian needs two replicas per zone. With three zones, one replica per zone suffices, because two surviving replicas serve 24 requests per second. Meridian chooses three zones, which needs one replica fewer, and Chapter 21 builds its deployment on that choice. The model assumes even load balancing and a measured per-replica capacity; confirm both with a test that removes a zone under load.

## Infrastructure as code

**Infrastructure as code** (IaC) describes infrastructure in versioned definition files and applies changes through automation. It makes environments repeatable, reviewable and comparable with what is actually deployed. A wrong definition is also repeated faithfully, so review matters as much as automation.

A safe change flow has five steps:

1. Validate the definition and run policy checks.
2. Produce a change plan that lists every resource to create, modify or destroy.
3. Review the consequential parts of the plan, especially replacements and deletions.
4. Apply the change through a controlled pipeline identity.
5. Check the result and record what was deployed.

Terraform keeps **state** that maps configuration to real resources and stores data needed for later operations. State can contain sensitive values. Protect its storage, access, versioning and recovery, and use locking where the backend supports it {REF:terraform}.

## Drift and destructive changes

**Drift** occurs when deployed resources differ from the definitions. An emergency manual change may be necessary, but it must then be written back into code or deliberately reversed. Otherwise the next automated run silently undoes it.

Treat replacement of stateful resources with special care. Replacing a stateless API instance is routine; replacing a production database can destroy data. Before applying such a plan, review backups, restore time, data migration, dependent systems and the recovery path.

Keep secret values out of definition files. A variable called `password` is still a secret wherever it is stored, and some tools hide values on screen while keeping them in state.

## Reading a deployment model

The neutral model below is a design sketch. It lists the responsibilities that a real manifest or template must express.

| Workload | Replicas and placement | Persistent state | Health and limits |
| --- | --- | --- | --- |
| API | Three, one per zone | Database and object storage | Readiness for useful traffic; bounded connections |
| Worker | Two in different zones, scaled to four on handoff age | Outbox and attempt history | Lease expiry; vendor rate limit |
| Database | Managed, zone-redundant | Durable records and backups | Capacity alerts; tested restore |
| Attachment scanning | Small isolated pool | Object processing state | Size limits; controlled release |

### Worked review: a risky scaling change

A proposed change raises worker replicas from two to eight and cuts the shutdown grace period from sixty seconds to five. Review it with four questions:

1. **Claims.** Do workers claim outbox rows atomically? If not, eight workers can pick up the same pending record.
2. **Leases.** Is the lease long enough for a slow CRM call, and does a stale lease holder's late result get rejected?
3. **Vendor limits.** Eight workers may exceed the CRM's rate limit, so throughput falls while throttling rises.
4. **Interruption.** With five seconds of grace, many calls will be cut off mid-flight. That is safe only if unfinished work stays durable and the retry uses the same idempotency key.

Test the interruption point directly, for example by stopping a worker after the CRM call and before the local update. The deployment tool accepts any setting; the review decides which settings are safe.

## Choosing the operating model

Kubernetes is valuable when a team needs its orchestration features and can run, or buy, a well-supported platform. It also brings cluster upgrades, network policy, access control and troubleshooting work. For Meridian, a managed container platform probably meets the first release's needs with less operating effort. Compare deployment control, scaling, networking, observability, security, team skills and total cost before deciding.

A platform team can provide a tested deployment path, common telemetry, identity integration and secure defaults. Application teams still own their application's behaviour, data use and recovery procedures.

## Key points

- Images package an application and its dependencies; deploy by digest and keep secrets out of images.
- Orchestration keeps the declared number of instances running; the application must still be safe to stop, restart and retry.
- Liveness restarts broken processes and readiness controls traffic. Keep dependency failures out of liveness checks.
- Each of n replicas must run below (n − 1)/n of capacity to survive one failure, and zone spreading needs the same check per zone.
- Infrastructure as code makes change repeatable and reviewable; protect state, reconcile drift and review destructive plans.
