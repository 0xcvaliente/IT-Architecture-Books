# 3 Business capabilities, value streams and requirements

## Learning objectives

After this chapter you should be able to:

- Distinguish a capability from a process, an application and an organisational unit.
- Build a two-level capability map and a value stream for a customer outcome.
- Construct a capability heat map that rates importance and effectiveness separately and records confidence.
- Translate a strategic objective into requirements that can be tested.

## What a capability is

A **business capability** is something the organisation is able to do to achieve a purpose, such as managing customer identity, scheduling technicians or reconciling financial records {REF:togafcap}. A capability describes what the organisation can do. It says nothing about how the work is done, which system supports it or who reports to whom.

Four related ideas are easy to confuse. The table uses Helios's service work to separate them.

| Concept | Question it answers | Helios example |
|---|---|---|
| Capability | What must we be able to do? | Entitlement checking |
| Process | How is the work done, step by step? | Look up contract, check asset, record decision |
| Application | Which software supports the work? | CRM North, ERP Core |
| Organisational unit | Who is accountable and where do people report? | Maintenance service desk |

The distinction matters because these things change at different rates. Helios could move entitlement checking from the service desk to a shared team, replace CRM North, and redesign the steps of the process, and the capability "entitlement checking" would still exist. That stability is what makes a capability map useful: it gives the board a structure for comparing investments that survives reorganisations and system changes.

A capability map is still a model. If Helios launched a new line of business, for example equipment leasing, it would need capabilities it does not have today, and the map would change.

## Building a capability map

A **capability map** arranges capabilities in a hierarchy. Level 1 groups them into broad domains; level 2 breaks each domain into capabilities that a single owner can be accountable for. Deeper levels are added only where a decision needs them.

Good maps follow a few rules:

- Name capabilities with nouns, such as "Order allocation", rather than verbs or project names.
- Keep organisation names out. "Retail order desk" is a unit; the capability it performs is order allocation.
- Avoid overlaps. Each piece of work should belong to exactly one capability at a given level.
- Give each level-2 capability one accountable owner, even when several units perform it.
- Choose a level of detail that suits the decision. "Run the business" is too broad to guide investment; "Call the case API" is too technical.

## Value streams

A capability map is static. A **value stream** shows how value reaches a stakeholder as a sequence of stages, from the trigger to the result the stakeholder wants {REF:togafvs}. Each stage draws on several capabilities, and one capability can support many value streams.

Helios's maintenance customers experience the value stream "Restore customer equipment". Its five stages, with times measured over one month of urgent requests, are shown below. Active time is when someone is working on the request; waiting time is when it sits in a queue.

| Stage | Main capabilities used | Active (days) | Waiting (days) |
|---|---|---|---|
| Request service | Service request intake, customer identity resolution | 0.1 | 0.4 |
| Confirm entitlement | Entitlement checking, account management | 0.1 | 2.4 |
| Schedule technician | Technician scheduling | 0.2 | 1.3 |
| Complete work | Field service delivery | 0.3 | 0.0 |
| Confirm and bill | Case coordination, billing | 0.1 | 1.6 |
| **Total** | | **0.8** | **5.7** |

The request takes 6.5 days from start to finish, but people work on it for only 0.8 days. The **flow efficiency**, active time divided by elapsed time, is 0.8 / 6.5 = 12.3%. The single largest delay is waiting for entitlement confirmation: 2.4 days, or 36.9% of the elapsed time.

A departmental view would miss this. The service desk processes its own queue quickly, and so does the contracts team; the delay sits in the handoff between them. If Helios cut the entitlement wait from 2.4 to 0.6 days, elapsed time would fall by 1.8 days to 4.7 days, a 27.7% reduction, without anyone working faster. The value stream therefore points to entitlement checking and case coordination as capabilities to investigate, which is what the heat map below also suggests.

Shared stages need a coordination mechanism. Where two units both touch a stage, name one person accountable for the whole value stream's outcome as well as an owner for each unit's part.

## Heat maps with evidence and confidence

A **capability heat map** adds ratings to the capability map. The most common mistake is to combine several dimensions into one colour. If a capability is shaded red, readers cannot tell whether it is important, failing, expensive or simply poorly understood.

Rate each dimension separately, with a defined scale:

- **Importance** to the current strategy: high if a board objective depends directly on it, medium if it supports one, low if it is a commodity.
- **Effectiveness** today, from 1 to 5: 1 means it fails often and staff rely on workarounds; 3 means adequate with known gaps; 5 means strong and measured.
- **Confidence** in the effectiveness rating: high when it rests on measured data, medium when it rests on consistent reports from several sources, low when it rests on opinion or a single source.

Record the basis for each rating. "Effectiveness 2: 14% of maintenance requests needed manual customer matching last quarter, from the service desk log" is useful. "Integration maturity 2" is not, because nobody can check it.

### Worked example: rating five Helios capabilities

| Capability | Importance, effectiveness and confidence | Basis |
|---|---|---|
| Customer identity resolution | High; 2 of 5; medium confidence | Duplicate customers found in samples from three units |
| Entitlement checking | High; 2 of 5; medium confidence | 2.4-day entitlement wait measured in the value stream over one month; accuracy of decisions not yet measured |
| Case coordination | High; 2 of 5; medium confidence | 1.6-day wait between completed work and billing in the value stream; failed handoffs in the service-credit records |
| Service request intake | High; 2 of 5; low confidence | Service desk reports duplicate and incomplete requests; no measurements |
| Technician scheduling | High; 4 of 5; high confidence | Scheduling system reports 96% of urgent visits booked within target |

Apply a simple rule. A capability is a **priority candidate** when its importance is high, its effectiveness is 2 or below, and confidence is at least medium. When confidence is low, the first action is to measure before investing.

Under this rule, customer identity resolution, entitlement checking and case coordination are priority candidates, which matches what the value stream showed. Entitlement checking has medium rather than high confidence because one month of waiting times shows the delay but not its cause, or whether the decisions themselves are correct. Service request intake is high in importance and probably weak, but the rating rests on reports alone, so the first step is a two-week sample of incoming requests. Technician scheduling is important and works well, so it needs protection during change rather than investment. The full map in {FIG:capability_map} shows one more priority candidate: group reporting, rated high in importance because consolidated reporting is a legal and board requirement (Chapter 4), with effectiveness 2 because units define the same measures differently.

The rule is a starting point for discussion. A low-importance capability with a legal obligation attached, such as retaining billing records, may still need urgent work. The value of the heat map is that it makes each judgement visible and open to challenge.

> **Common mistake.** Sending every weak capability into the largest transformation programme. A weak capability may need a quick control, a measurement exercise or simply better training. Match the action to the cause.

## From strategy to requirements

The board's objective "a coherent customer view" needs a user and a purpose before anyone can design for it. For example:

- A service agent needs to recognise the same customer across divisions, but should see only the cases they are authorised to see.
- Finance needs consolidated revenue per customer group, based on an agreed mapping of legal entities.
- Marketing may want cross-selling lists, which raises different questions about permitted use of data.

Each purpose leads to different requirements. A good enterprise requirement for the first purpose reads:

> **Requirement CV-1.** An authorised service agent can find a customer organisation by any division's identifier, see its governed group identifier and see the cross-division service history they are permitted to view, within five seconds. Links that have not been verified are shown as unverified.

This requirement is testable. It also implies several pieces of architecture: identifier mapping, an access policy, a named authority for each fact, a freshness target and a process for resolving ambiguous matches. It does not require one CRM.

Requirements need owners and acceptance tests. Some questions are policy decisions rather than design questions. Should a Retail agent see a Maintenance case for the same customer? The architect should raise that question with the accountable owners before anyone builds a cross-division data join. Being able to combine records technically does not grant permission to use them for every purpose.

The evidence is: 12% of supplier invoices needed manual matching last quarter, from the accounts-payable log; two audit comments on late payments; and no board objective that depends directly on it. Design a heat-map entry with importance, effectiveness and confidence ratings and the basis for each, and state the action the priority rule implies.

## Key points

- A capability is what the organisation can do. It is more stable than the processes, applications and units that deliver it, which makes it a good structure for investment decisions.
- Value streams show how stages and capabilities combine to deliver an outcome. Measuring waiting time as well as active time reveals the handoffs that departmental views miss.
- Heat maps should rate importance and effectiveness separately, define their scales, record the basis for each rating and show confidence.
- Strategic objectives become useful once they are rewritten as testable requirements with a named user, purpose, scope and owner.
